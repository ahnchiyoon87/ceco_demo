## 0. 한 문단 요약

V1 프로토타입을 기준선으로 고정한다. **OSI 승인 오픈소스이면서 비용이 0원인** 2025~2026년 최신 트렌드 후보 기술로 모듈을 하나씩 교체해 빠르게 구현(바이브 코딩)한다. 같은 시나리오·같은 측정으로 비교해 채택/유지를 결정한다. 이것을 3회전 돌려 **V1 → V2 → V3 진화 궤적**을 만든다. 궤적에는 세 가지가 버전마다 증거와 함께 남아야 한다: **기술선정**(무엇을 왜 골랐나), **온톨로지 개선**(AI가 답할 수 있는 질문이 어떻게 늘었나), **시나리오 개선**(테스트 상황이 어떻게 늘고 현실화됐나). 비중은 IoT·SCADA(L1~L6) 약 80%, AI(L7~L9) 약 20%. 기간은 5영업일. LLM API 호출 비용만 예외로 허용한다.

### 1.1 지시 요지
- 사전 스펙으로 설계를 평가하지 않는다. 후보를 **빠르게 실제 구현**해 각 모듈을 검증하고, 다른 접근 방법과 비교해 확정한다.

## 2. 선정 기준: 오픈소스·비용 0원·최신 트렌드

### 2.1 허용
- **OSI 승인 오픈소스 라이선스**: Apache-2.0, MIT, BSD, EPL/EDL, MPL, LGPL, GPL, AGPL, PostgreSQL License 등.

- copyleft(GPL/AGPL)는 **무수정 사용**이면 허용한다. 수정해서 네트워크로 제공할 경우 소스 공개 의무가 생기므로 `license-report.md`에 "제품화 시 검토" 표시를 남긴다.

### 2.2 제외
- 상용 제품, 체험판(기간·태그 수 제한), 유료 엔터프라이즈 기능이 필요한 것.
- **조건부 무료·소스 공개형**: BSL/BUSL, SSPL, Elastic License, TSL(Timescale License), RCL(Redpanda Community License), Confluent Community License, Commons Clause, Camunda License, 그리고 "MIT + 추가 제한" 같은 비표준 라이선스.
- **교육용·비상업·개인 전용 무료** 라이선스(회사 업무 프로토타입이고 제품화 가능성이 있음).

- 오픈 가중치 모델 중 가중치가 비상업 라이선스(CC-BY-NC 등)인 것.

## 3. 절대 규칙

1. **측정하지 않은 수치를 쓰지 않는다.** 미측정은 `NOT MEASURED`. 벤더 벤치마크를 로컬 측정처럼 쓰지 않는다.
2. **`harness/`, `scenarios/`, `gates/`는 후보 구현 작업 중 수정 금지.** 잘못됐다고 판단되면 `QUESTIONS.md`에 적고 그 항목만 멈춘다. 후보를 통과시키려고 시나리오·기대결과·판정기준을 바꾸면 그 실험은 무효다.
3. **한 실험에서 한 모듈만 교체한다.** 여러 모듈 동시 교체는 §13.2 클린시트 비교에서만 허용하며 "구조 비교"로 표시한다.
4. **안전 Gate와 라이선스·비용 Gate(G0~G9) 하나라도 실패하면 탈락.** 성능·트렌드로 상쇄하지 않는다.
5. **판정 기준은 결과를 보기 전에 확정한다.** 확정 후 변경 금지.
6. **실패·기각·보류 실험을 삭제하지 않는다.** 실패도 궤적이다.
7. **명령 송신 성공 ≠ 실제 상태 변경.** 항상 HTTP `/state`(seq 증가 포함)로 재확인한다.
8. **실제 설비에 연결하지 않는다.** 가상설비만 사용한다.
9. **컴포넌트를 제거하기 전에** 그것이 제공하던 기능과 대체 경로를 먼저 적는다. 대체 경로가 없으면 제거하지 않는다.
10. **`latest` 이미지 태그를 쓰지 않는다.** 모든 이미지는 버전 + digest로 고정하고 EXP 로그에 기록한다.
11. **버전·라이선스는 작업 당일 재확인한다.** 공식 릴리스 페이지와 저장소 LICENSE 파일을 직접 열어 확인하고, 확인 URL·날짜를 EXP 로그에 적는다. 이 문서의 `[재확인]` 표시는 특히 반드시 확인한다.
12. **혼동 금지**:
    - SCADA 조작(FUXA/Vue)과 관측(Grafana/Prometheus)은 다르다.
    - 알람, 원인 확정, 정지는 서로 다르다.
    - 알람 확인 버튼은 고장 복구가 아니다.
    - 그래프 DB 교체는 온톨로지 개선이 아니다.
    - 명령 성공과 상태 변경은 다르다.
13. **AI 경로에서 Modbus에 직접 쓰는 코드를 추가하지 않는다.** 설비 명령은 §4.3의 C1·C2·C3 경로로만 나간다.

## 4. V1 시스템 정확한 이해

이 절과 V1 실제 코드가 다르면 **코드가 맞다**. 차이는 `harness/V1_FACTS.md`에 기록한다.

### 4.1 L1 가상 공정
- 교육·실습용 **물리모델 시뮬레이터**다. 그림만 움직이는 화면이 아니다. 명령이 반영되고, 물리모델이 다음 센서값을 계산한다.
- 공정 흐름(재료 이동 방향):
  - 원료탱크 **TK-101**(레벨) → 공급펌프 **P-101**(운전·유량·모터전류) → 반응기 **R-101**(레벨·온도·압력·pH) → 배출밸브 **CV-101**(개도·실제 유량).
  - R-101 안에서 교반기 **M-101**(운전·전류·진동)이 섞고, 재킷/히터 **HX-101**이 가열한다.
- 재킷온도와 내부온도는 따로 측정한다. 열전달에 지연이 있다.
- 밸브 개도와 실제 유량은 비례하지 않는다. 개도 50%가 유량 절반을 뜻하지 않는다.
- 냉각 장치는 없다. 목표 온도를 낮춰도 온도가 즉시 내려가지 않는다.
- 대표 태그: **TT-101** 반응기 온도, **PT-101** 반응기 압력, **IT-102** 교반기 전류, **VT-101** 교반기 진동. 계측 태그는 **12개**다.
- 데이터 단위: 설비명, 태그, 시각, 값, 품질이 함께 다닌다.
- Modbus TCP:
  - 코일 = 기동/정지(1 운전, 0 정지).
  - 레지스터 = 설정값(펌프 속도, 밸브 개도, 목표 온도).
  - 온도는 ×10 스케일이다(72℃ → 720). Vue는 72를 입력받아 720으로 변환해 보낸다. FUXA는 720을 직접 입력한다.
- HTTP `/state`: 새 seq와 운전 상태를 돌려준다. 명령 후 상태 확인에 쓴다.
- 고압 인터록(압력이 높으면 정해진 동작을 막거나 멈춤)과 이상 주입 기능이 있다.

### 4.2 데이터 경로 (L2~L6)
```
가상설비 ─Modbus─▶ EdgeX(device-modbus 폴링 → 이벤트 처리 → MQTT export)
        ─MQTT(edgex/telemetry)─▶ EMQX ─▶ Telegraf#1(수집: MQTT→Kafka 형식 변환) ─▶ Kafka raw
Kafka raw ├▶ Flink 규칙 작업 (상·하한 / Z-Score / CEP 시간·순서 패턴)
          ├▶ Flink ONNX 작업 (전처리 → Autoencoder 이상 점수)      ※ 두 작업은 raw를 각각 병렬로 읽음(직렬 아님)
          └▶ Telegraf#2(저장: Kafka→InfluxDB)                     ※ 원본 저장은 Flink를 거치지 않음
Flink ─▶ Kafka clean / score / alerts
Kafka clean/score ─▶ Telegraf#2 ─▶ InfluxDB
Kafka alerts ├▶ Telegraf#3(알람 중계: Kafka→MQTT scada/hmi/latest-alert) ─▶ EMQX ─▶ FUXA 최근 알람
             └▶ 알람 접수 워커 ─▶ 사건 등록(중복 관측 결합) ─▶ PostgreSQL
InfluxDB ─▶ Grafana (공정 이력)
Prometheus(EMQX·Kafka·Flink 등 운영 지표) ─▶ Grafana, Alertmanager(운영 경보·그룹·억제, 설비 정지 경로 아님)
```
- **Telegraf는 한 도구를 3가지 설정으로 쓴다**: #1 수집, #2 저장, #3 알람 중계.
- raw/alerts/clean/score는 같은 Kafka 안의 별도 토픽이다.
- Kafka는 보관 기간·용량 정책이 있으므로 영구 보관소가 아니다.
- 알람은 "이 조건이 관측됐으니 확인이 필요하다"는 뜻이다. 원인 확정이나 정지 명령이 아니다.

### 4.3 제어 경로 3개 (서로 분리)
| 경로 | 흐름 | 검사 주체 |
|---|---|---|
| **C1** FUXA 직접 조작 | FUXA ─Modbus TCP─▶ 가상설비 (FUXA가 직접 계측·조작) | FUXA |
| **C2** Vue 통합 대시보드 직접 조작 | 브라우저 → API → 백엔드 직접 제어 기능: 입력 범위·기동 조건 확인 → Modbus 명령 → `/state` 재확인·요청값 비교 → 업무 DB 기록. 새로고침 후에도 조작 이력 조회 가능 | 백엔드 |
| **C3** AI 제안 승인 조치 | 알람 → 사건 → 사람이 분석 시작 → Agent(조회 도구, LiteLLM) → 근거·불확실성·대응안 → LangGraph 검토 대기 → 담당자 승인/반려 → 승인 시 Pilot이 **조건 재검사** → Modbus 정지 명령 → `/state` 확인 → PostgreSQL 기록. 반려 시 명령 없음. "점검 요청" 승인은 업무만 기록 | Pilot |

- **AI가 화면 버튼을 대신 누르는 경로는 없다.** Grafana·Alertmanager는 제어 경로가 아니다.

### 4.4 AI 레이어 (L7~L9)
- **L7**:
  - 원본 문서·절차(버전·출처 포함)
  - Neo4j 지식그래프(설비↔센서↔문서 소속·적용 관계)
  - 지식 후보 검토 파이프라인(원본 등록 → 관계 후보 → 출처 검토 후 그래프 게시)
  - 근거 조회(그래프/시계열/현재 상태)
- **L8**:
  - 알람 접수 워커
  - 조회 도구(알람/센서/문서, 실제 호출 기록 저장)
  - 업무 Agent(원인 확정과 관측 사실을 구분)
  - LiteLLM(GCP 모델 호출 중계)
- **L9**:
  - LangGraph(조사 → 검토 대기 → 실행, 저장된 상태로 재개. BPMN 모양으로 표시만 하며 BPMN 엔진은 아님)
  - Pilot
  - Vue

## 5. 용어: 기술선정·온톨로지·시나리오·궤적

### 5.1 최적 기술선정
모듈별로 후보를 실제로 구현하고, 같은 시나리오·같은 측정으로 비교해 §10 규칙으로 고른 결과다.

### 5.2 온톨로지와 온톨로지 개선
- **온톨로지** = 이 공정에 **무엇이 있고**, 그것들이 **서로 어떤 관계**이며, **어떤 규칙**이 있는지를 정해 둔 것이다.
  - 종류: 설비, 부품, 센서, 관측값, 문서, 알람, 사건, 조치, 승인…
  - 관계: "M-101은 R-101의 부품", "VT-101은 M-101의 진동을 측정", "이 절차서는 M-101에 적용"
  - 규칙: "PT-101이 높으면 기동 차단(인터록)"
- **스키마와의 관계**: 온톨로지는 "무엇을 어떤 의미로 표현할지"에 대한 설계다. 스키마는 그것을 DB에 실제로 만든 형태(노드·관계·속성 종류)다. 온톨로지를 바꾸면 스키마가 따라 바뀐다.
- **온톨로지 개선 ≠ 성능 개선.** DB를 더 빠른 것으로 바꾸는 건 기술 교체다.
- **온톨로지 개선 = AI가 근거와 함께 답할 수 있는 질문이 늘도록 개념·관계·규칙을 보강하는 것.**
- **측정**: 미리 정한 질문 목록(Competency Question, CQ) 중 몇 개에 근거와 함께 답하는지 센다. 예: V1 3개 → V2 8개 → V3 11개.
- **확장 근거**: 답하지 못한 질문만이 확장의 근거다. "있으면 좋겠다"는 이유로는 추가하지 않는다.

### 5.3 시나리오와 시나리오 개선
- **시나리오** = 테스트 상황 하나다. 전제·입력(주입)·기대결과·금지행동·판정방법을 갖는다.
- **시나리오 개선** = 앞 회전에서 드러난 실패 유형과 현실 조건(순서 뒤바뀜, 지연, 재시작, 단절, 승인 후 조건 변화, 실제 데이터 노이즈)을 반영해 시나리오를 추가하고 현실화하는 것이다.
- **기존 시나리오의 기대결과는 바꾸지 않는다.** 추가만 한다.

### 5.4 궤적
V1 → V2 → V3로 가면서 **기술·온톨로지·시나리오가 각각 무엇이 왜 바뀌었고 그 결과가 어땠는지**의 기록이다. 세 가지가 서로 맞물린 모습을 보여야 한다. 예:
> 회전 1 시나리오 S04~S09에서 알람이 탐지됐지만, AI는 CQ04 "이 알람의 근거는?"에 답하지 못했다 → 온톨로지 V2에 Alarm·Observation·Evidence 관계를 추가했다 → CQ 응답 3→8개로 늘었다 → 회전 2에서는 이를 검증하는 시나리오 S25b(근거 추적)를 추가했다.

## 9. 하니스 — 계약·주입·측정·시나리오·Gate (Day 1 오전, 후보 구현보다 먼저)

### 9.1 인터페이스 계약

### 9.2 이상 주입 / 리플레이
- **1순위**: 가상설비 자체의 이상 주입 기능을 API로 호출한다(실제 경로 전체를 거침).
- **2순위**: 고정 데이터 파일을 **이벤트 시간 그대로** MQTT 또는 Kafka raw에 재생한다(L4 단독 비교용). 순서 뒤섞기, 지연, 중복, 누락 주입을 지원한다.
- 고정 시드와 데이터 체크섬을 `data/checksums.txt`에 기록한다.
- 회전 2에서 **SKAB**(펌프·밸브 테스트베드 이상 벤치마크: 전류·진동·압력·온도 포함)를 IT-102/VT-101/PT-101/TT-101로 매핑해 추가한다. 추가 전에 SKAB의 라이선스·이용 조건을 확인해 `LICENSES.md`에 적는다. SWaT/WADI는 신청·연구 약관 기반이라 사용하지 않는다.

### 9.3 가상설비 장애 훅 (V1에 없으면 하니스 쪽에 추가)
- `write_fail`: Modbus write 오류 응답
- `ack_no_change`: write 성공 응답, 실제 상태는 변화 없음
- `interlock_on`: 고압 인터록 조건 강제
- `state_timeout`: `/state` 응답 지연
- **모든 Modbus write를 로그로 남긴다**(경로 C1/C2/C3, 주소, 값, 시각, 결과). Gate 판정의 근거가 된다.

### 9.4 장애 주입 도구 (모두 오픈소스, 버전 고정)
- `docker compose kill/stop/start`: 프로세스 재시작, DB 다운
- **Toxiproxy**(MIT `[재확인]`): Modbus TCP·MQTT·Kafka·PostgreSQL 앞단의 지연·단절 주입
- **Pumba**(Apache-2.0 `[재확인]`): 컨테이너 kill, netem
- Chaos Mesh는 Kubernetes 전용이라 사용하지 않는다.

## 10. 판정 규칙 (결과 보기 전 확정, 🔧 I7)

후보는 아래를 **모두** 만족하면 채택한다.

1. **G9 라이선스·비용 통과** (필수)

3. 시나리오 정답 수 ≥ 기준선
4. **비열등**: p95 지연 악화 ≤ 20%, 메모리 악화 ≤ 30%, 유실·중복 증가 0
5. 아래 중 **하나 이상**:
   - (a) **트렌드·지속성 우위**: 트렌드 판정이 기준선보다 좋음, 또는 라이선스·보안·유지보수 리스크가 명확히 감소(근거 필수)
   - (b) **복잡도 감소**: 컨테이너 수 또는 설정·코드 LOC 20% 이상 감소
   - (c) **성능 개선**: p95 지연 또는 메모리 20% 이상 개선
6. 조건을 만족하는 후보가 여럿이면 (b)(c) 개선폭이 큰 쪽을 택한다. 같으면 트렌드 판정이 앞선 쪽을 택한다.

- 기준선이 G9를 통과하지 못하면(예: BSL 컴포넌트), 그 모듈은 **G9를 통과하는 후보 중 1~4를 만족하는 최선안**으로 반드시 교체한다. 5는 요구하지 않는다.
- 조건을 만족하는 후보가 없으면 기준선을 유지하고 그 사실을 궤적에 기록한다. **유지도 결과다.**

### 11.1 [EXP-110대] L4 패턴탐지 — CEP 결론 (최우선)

**문헌 사실 (결론 아님, 실측 전 배경)**
- 독립 CEP 엔진(Esper·Siddhi·TIBCO·Apama류)은 신규 채택 신호가 약하다. 즉 제품 범주로서는 쇠퇴했다.
- CEP **기능**은 Flink에 흡수되어 유지 중이다:
  - Flink 2.2.1(2026-05-15)과 2.1.3(2026-06-14)이 릴리스됐다.
  - 안정판 문서가 SQL `MATCH_RECOGNIZE`와 비표준 확장 `WITHIN` 절을 유지하고 있다.
  - 상용 관리형 Flink도 CEP SQL을 제공한다.
- **Flink SQL의 한계**(ASF Jira FLINK-33428, 해결 여부 `[재확인]`): DataStream CEP API는 next·notNext·followedBy·followedByAny·notFollowedBy를 지원한다. SQL은 사실상 **next(엄격 연속)만** 지원하고 notFollowedBy는 없다.
- 따라서 "중간에 다른 이벤트가 끼어도 N초 내 진동 상승"(S04)을 SQL로 하려면 filler 우회(`PATTERN (I X*? V) WITHIN INTERVAL 'N' SECOND`)가 필요하며, 동작은 검증해야 한다.

| EXP | 후보 | 구현 요점 | 핵심 관찰 |
|---|---|---|---|
| EXP-111 | Flink **2.2.1** DataStream CEP (기준선 로직을 2.2.1로 올린 것. V1이 1.x면 버전만 올린 변형도 함께 기록) | `begin(I).where(전류↑).followedBy(V).where(진동↑).within(N s)`, 이벤트타임 + 워터마크, late는 side output | 기준 동작 |
| EXP-112 | Flink 2.2.1 **SQL MATCH_RECOGNIZE** | `PARTITION BY 설비 ORDER BY 이벤트시각 MEASURES … PATTERN (I X*? V) WITHIN INTERVAL 'N' SECOND`. Z-Score는 `OVER (RANGE INTERVAL …)` | S04(중간 이벤트), S06 경계 |
| EXP-113 | **Python 스트림 서비스** (Quix Streams(Apache-2.0) 또는 순수 asyncio + 설비별 상태 머신 `{IDLE, I_RISEN(t0)}`, `t−t0 ≤ N`이면 발화) | 상·하한, Z-Score 롤링, 패턴을 한 서비스로 처리. 상태·오프셋은 로컬 상태저장소 또는 PostgreSQL | late·재시작 정확성을 직접 구현해야 함 → S07·S09 |

## 14. 온톨로지 진화 절차

### 14.1 원칙
- **DB는 바꾸지 않는다**(Neo4j Community 유지). 이번 과제는 모델 품질이다.
- **확장 근거 = 답하지 못한 CQ.** CQ 결과 없이 요소를 추가하지 않는다.
- 설비 계층은 ISA-95 명명(site/area/line/unit/equipment)을 따른다.
- 관측은 W3C **SOSA/SSN** 방식(센서 · 관측값 · 관측 대상 · 시각 · 품질)으로 표현한다.
- 출처·파생은 W3C **PROV-O** 방식(`wasGeneratedBy`, `wasDerivedFrom`, `wasAttributedTo`)으로 표현한다. 모두 무료 공개 표준이다.
- **관측 노드는 추가만 하고 수정하지 않는다.** AI 추론 노드에는 AgentRun 링크를 필수로 단다(관측 사실과 AI 추론 분리, CAP-17).

### 19.4 병렬 작업 방식
- 후보마다 `git worktree add ../cand-<id> exp/<id>`로 독립 작업트리를 만든다. 같은 회전의 후보는 모두 **같은 기준 커밋**에서 출발한다.
- 후보 에이전트 세션에는 이 문서, `harness/SCHEMA.md`, 교체 대상 모듈의 기준선 코드·설정, 후보의 공식 문서만 준다.
- 완료 조건: `make gates && make scenarios && make measure && make license`가 끝까지 도는 것이다. 통과 여부와 무관하게 결과가 나와야 한다.
- 구현은 병렬로 해도 되지만, **측정은 한 번에 하나씩** 같은 머신 조건에서 한다.
