## ① 현업 주류 구조 한 장

근거가 여러 표준·독립 출처에서 겹치는 것만 넣었다. 자세한 근거는 §4-1~4-3.

**구역:** OT(L0–L3) │ 산업 DMZ(L3.5) │ IT(L4–5·클라우드). IT → OT 직접 경로 없음. OT와 DMZ 사이는 OT 쪽이 먼저 연결을 연다. 안전계장은 제어망과도 따로 둔다. (NIST SP 800-82r3, CISA Defense in Depth 2016, CISA 외 AI-OT 지침 2025)

**층 (아래 → 위)**

| 층 | 역할 | 구역 |
|---|---|---|
| 현장 장치 | 센서·구동기 | OT L0 |
| 제어기(PLC·DCS) + 안전계장(SIS, 별도) | 제어 루프, **인터록, 운전 모드, 명령 수용 결정** | OT L1 |
| SCADA·HMI | 현재값, 운전원 조작, **공정 알람(ISA-18.2)** | OT L2 |
| 엣지 연결·프로토콜 변환 | Modbus·OPC UA 등 → 공통 형식, 끊기면 저장 후 전달 | OT L2–L3 |
| 사이트 브로커(UNS) | ISA-95 계층 토픽으로 "지금 상태"를 모음. 이력·명령 통로는 아님 | OT L2–L3 |
| 맥락화·설비 모델(DataOps) | 설비 계층·종류별 모델·스키마 | 엣지~사이트 |
| 사이트 히스토리언 / 복제 히스토리언 | 이력 정본(OT L3), 기업용 사본(DMZ) | OT L3 / DMZ |
| DMZ 중계 | 복제, 검증 통로, 점프 서버 | DMZ |
| 이벤트 스트리밍 장부 | 보관·재생·다중 소비·스키마 계약 (MQTT 뒤에 붙음) | DMZ~IT |
| 스트림 처리·탐지 | ML 탐지는 주로 L1–L3, 중앙 분석은 IT | OT·IT |
| 플랫폼 감시 | 서버·망·서비스 지표, 로그 | 각 구역 → 중앙 |
| 분석·AI(지식 그래프·LLM 에이전트) | 원인 분석·권고. **OT 밖, 읽기 전용** | IT |
| MES·CMMS·ERP·업무 흐름 | 작업 지시, 변경 관리, 승인 | L3–L4 |

**길**

- 데이터 ↑: 제어기 → 엣지(변화 시 보고) → 사이트 브로커 → (DMZ 복제) → 스트리밍 장부·히스토리언 → 분석·AI. OT가 밀어낸다(push).
- 명령 ↓ (운전원): HMI → 제어기. IT를 거치지 않는다.
- 명령 ↓ (바깥 요청): 사람 승인(기존 변경 관리) → **검증 통로 하나** → 제어기가 최종 판단(NAMUR NE 178). 브로커 명령은 retain 금지(Sparkplug). 쓰기 결과는 응답·상태로 되돌려 준다.
- 알람: 공정 알람은 제어기·SCADA → 운전원(대응이 필요한 것만). AI 경고는 HMI 화면에 통합하되 오경보 관리. 플랫폼 경보는 인프라 담당으로 따로.
- 확장: 층은 그대로, **설비 계층 이름 + 토픽 체계 + 설비 종류별 모델 + 엣지 노드 추가**로 흡수. 통신 차이는 엣지에서 끝낸다.

## ② 우리 베이스 권장 구조 한 장 (판단 — 근거는 §4-5)

**구역(도커 망):** `ot-net` │ `dmz`(두 망에 붙는 중계 컨테이너만) │ `it-net`. IT 컨테이너는 `ot-net`에 붙지 않는다.

| # | 층 | 망 | 핵심 규칙 |
|---|---|---|---|
| B0 | 가상 설비(여러 대, Modbus → 이후 OPC UA 추가) | ot | 제어기 외 쓰기 금지 |
| B1 | soft-PLC 제어기 | ot | 인터록·운전 모드·명령 수용 판단·ACK |
| B2 | 엣지 연결(EdgeX) | ot | 설비 정의는 자산 레지스트리에서 생성 |
| B3 | 사이트 브로커(UNS, 1개) | ot | ISA-95 계층 토픽, ACL, 명령 retain 금지 |
| B4 | SCADA/HMI(FUXA) | ot | 데이터는 UNS에서, 조작은 `cmd` → 제어기. IT가 멈춰도 동작 |
| B5 | DMZ 중계 3종 | dmz | 상향 복제 / 명령 게이트웨이(검증 한 곳) / 감시 수집 |
| B6 | Kafka 장부 | it | 토픽은 데이터 종류별, 키는 자산 ID |
| B7 | Flink 탐지 | it | 규칙·모델을 설비 종류 단위로 적용 |
| B8–B9 | 공정 이력 정본 + 대시보드 | it | 원본 보존, 정본 한 곳 |
| B10 | 플랫폼 감시 | it(+dmz 수집) | 공정 알람과 분리 |
| B11 | 자산 레지스트리 + 온톨로지 | it | **설비 계층·태그·종류 모델의 정본 하나** → B2·B3·B6·B7·지식 그래프가 공유 |
| B12 | AI 에이전트 | it | 읽기 전용 도구, 명령 권한 없음 |
| B13 | 승인·업무 흐름 | it | 승인 → Kafka 명령 → B5 → B3 → B1 → ACK 대조 → 재관측 → 기록 |

**길:** 데이터 B0→B1→B2→B3→B5→B6→{B7,B8}→B9·B12 / 수동 명령 B4→B3→B2→B1→B0 / AI 경유 명령 B12→사람 승인(B13)→Kafka→B5→B3→B2→B1→B0 / 되읽기 B1 ACK→B3→B5→B6→B13 / 공정 알람 B7→{B13, B5→B4 표시} / 플랫폼 경보 →B10.

**지금 우리 구조에서 바꿀 다섯 가지:** ① 망 3구역 ② soft-PLC 층 신설 ③ 쓰기 길 3개 → 수동 1 + 검증 통로 1 (AI의 Modbus 직접 쓰기, FUXA 직접 쓰기 제거) ④ 되읽기를 HTTP `/state`에서 제어기 ACK·상태 토픽으로 ⑤ 자산 레지스트리를 정본으로 두고 토픽·키·규칙·온톨로지가 같은 ID를 씀.

## §4-1. 2026 현업 주류 구조를 독립적으로 그린다

이 절은 우리 구조와 v3를 보지 않고 쓴다. 표준 문서와 여러 출처가 겹치는 곳을 "주류"로 본다.
벤더 한 곳만 말한 것은 주류 근거로 쓰지 않는다.

### 1-A. 뼈대가 되는 기준 틀 네 가지

현업 구조 그림은 대부분 아래 네 틀 위에 그려진다. 이 넷은 서로 경쟁하지 않는다. 역할이 다르다.

### 1-B. 망 구분 — OT / DMZ / IT

여러 공공 표준이 같은 말을 한다.

1. **기업망과 OT망 사이에 DMZ를 둔다. 직접 통신을 막는다.**
   - NIST SP 800-82r3 §1 보안 목표: "DMZ 망 구조와 방화벽으로 기업망과 OT망 사이에 트래픽이 직접 지나가지 않게 한다." 인증 수단·계정도 기업망과 OT망이 따로 쓴다. 가장 중요한 통신은 가장 안전한 층에서 일어나게 여러 층 구조를 쓴다. [표준] (확인 2026-09-29)
   - NIST SP 800-82r3 §5.4.1: "기업 층과 운영 관리 층 사이의 모든 통신은 DMZ 안의 서비스를 거쳐야 한다." 인접 층 사이에는 허가된 통신만 지나가게 들어오는 규칙과 나가는 규칙을 모두 정한다. [표준]
   - NIST SP 800-82r3 §5.4.2(IIoT 포함 예): IIoT 장치는 별도 망 구획에 두고, IIoT 플랫폼 층의 통신은 DMZ 경계 방화벽을 거쳐 DMZ 서버나 기업망으로 간다. [표준]
2. **단방향 장치(데이터 다이오드)는 방화벽의 대안이다.** NIST는 "L2와 L3 사이의 단방향 게이트웨이가 L3~5의 사고로부터 L0~2를 보호할 수 있다"고 쓴다. [표준] NIST SP 800-82r3 §5.2.3.1 박스.
3. **AI는 OT 밖에서, 밀어내기(push)로 받은 데이터를 쓴다.** CISA 외 공동 지침: "데이터를 OT망 밖으로 밀어내어 AI가 쓰게 하고, AI가 OT망에 지속적으로 접근하지 않게 하는 push 기반 구조를 권한다." "필요한 특징값이나 요약을 OT 밖으로 옮기는 push 방식 또는 브로커 방식을 우선한다. 업무망으로 넘어가야 하면 단방향 전송과 감사되는 중간 버퍼를 쓴다." 새 원격 접속 경로는 기존 DMZ나 점프 호스트를 거친다. [표준] p.15, p.20
4. **보안 구획은 기능 층과 1:1이 아니다.** 62443의 zone은 위험 평가로 정한다. NIST도 "관리 권한, 신뢰 수준, 기능 중요도, 데이터 흐름, 위치" 등으로 나눌 수 있다고 쓴다. 즉 Purdue 층 번호는 출발점이고, 실제 경계는 공장마다 다르다. [표준] NIST §5.2.3.1

5. **DMZ에는 기업이 보는 것(히스토리언 복제 등)을 두고, 연결은 OT 쪽이 먼저 연다.** CISA(당시 DHS ICS-CERT) 권고 Defense in Depth(2016) §2.4.2: "기업이 접근하는 구성요소를 DMZ에 두면 기업망에서 제어망으로 가는 직접 경로가 필요 없다. 모든 경로는 DMZ에서 끝난다." "방화벽 규칙이 제어망 장치가 먼저 연 연결만 허용하면" DMZ가 뚫렸을 때의 위험이 줄어든다. "DMZ 없는 2구역 구성은 겨우 허용되는 수준이다. 가장 안전하고 확장 가능한 구조는 DMZ를 하나 이상 둔 3구역 이상이다." 히스토리언, 복제 서버, 보안 서버 등을 기능별로 여러 DMZ에 나눌 수 있다. 안전계장(SIS)은 별도 망에 두는 것이 이상적이다. [표준] https://www.cisa.gov/sites/default/files/recommended_practices/NCCIC_ICS-CERT_Defense_in_Depth_2016_S508C.pdf (본문 추출해 §2.4.1–2.4.2 읽음, 확인 2026-09-29)
6. **벤더 참조 구성도 같은 모양이다.** Microsoft Azure IoT Operations의 계층망 자습서(2026-08 갱신)는 Purdue L2·L3·L4에 각각 클러스터를 두고 "인접 층끼리만 통신"(L2↔L3, L3↔L4 허용, L2↔L4 차단, L2/L3→인터넷 차단)하게 한다. L2 브로커 → L3 브로커 → L4 프록시로 데이터가 층마다 올라간다. [벤더] https://learn.microsoft.com/en-us/azure/iot-operations/end-to-end-tutorials/tutorial-layered-network-private-connectivity (확인 2026-09-29)

**주류 모양(판단, 위 표준 출처의 공통점):** OT 안(L0–L2, L3 운영 영역) / 산업 DMZ(L3.5: 복제 히스토리언, 중계 서버, 점프 서버, 패치 서버) / IT(L4–5, 클라우드). OT → DMZ는 OT가 먼저 연결을 연다. IT → OT 직접 경로는 없다. 안전계장은 제어망과도 따로 둔다.

### 1-C. 공정 제어 영역을 건드리지 않는 "두 번째 길" — NAMUR NOA

화학·제약 업계 사용자 단체 NAMUR의 NOA는 "감시·최적화(M+O)"를 위한 데이터 길을 기존 제어 구조와 따로 낸다.
- NE 175: 핵심 공정 제어(CPC), 공장 단위 감시·최적화(psM+O), 중앙 M+O 세 영역 사이 정보 흐름을 정의한다. "자동화 시스템에 영향이 없도록 두 번째 통신 채널로" 데이터를 보낸다. 기본은 읽기 전용이다(이 "읽기 전용" 표현은 NE 178 관련 논문 초록에서 봄: https://www.researchgate.net/publication/388623847 (검색 발췌)). [표준·업계 권고] https://www.namur.net/en/work-areas-and-project-groups/focus-topics/namur-open-architecture.html (확인 2026-09-29)
- NE 176(정보 모델), NE 177(보안 게이트웨이), NE 179(집계 서버)가 받친다. [표준·업계 권고] 같은 출처
- **NE 178 Verification of Request(2025-03-10 발행):** 바깥 M+O 앱이 설비에 쓰기를 요청할 때 IT/OT 경계를 안전하게 넘게 하는 검증 개념이다. 최종 권한은 CPC에 남는다. 요청자에게 처리 상태를 되돌려 주지만 공장 내부 정보는 드러내지 않는다. [표준·업계 권고] https://www.namur.net/en/publications/news-archive/ne178-namur-open-architecture-verification-of-request-is-newly-published.html (확인 2026-09-29)

→ 현업(적어도 공정 산업)은 **"읽기는 넓게, 쓰기는 좁은 검증 통로 하나로, 최종 결정은 제어 계층이"** 라는 원칙을 표준 문서로 굳혀 가고 있다.

**층 구성에서 확인한 핵심 세 가지:**
1. **SCADA·HMI는 원래 OT 안에서 제어기를 직접 읽고 쓴다.** NIST의 SCADA 설명은 제어 센터가 현장 장치에서 정보를 모으고, HMI에 표시하고, 중앙 알람을 맡는 구조다. [표준] 한편 Sparkplug는 SCADA/HMI를 MQTT "Host Application"으로 두고, 명령도 브로커를 통해 NCMD/DCMD로 보내게 정의한다. [재단] → **현업에는 두 방식이 모두 있다.** "SCADA가 PLC를 직접 폴링"하는 고전 방식과 "SCADA가 UNS 브로커의 한 구독자"인 방식이다. 둘 다 SCADA는 OT 안에 있다.
2. **UNS는 제품이 아니라 설계 방식이다. 히스토리언도, 명령 통로도 아니다.** IT/OT Insider: "UNS는 (1) 정리된 중앙 데이터 브로커, (2) 사업 전체의 데이터를 맥락과 함께, (3) 지금 상태로 보여준다." "MQTT = UNS는 틀렸다." "UNS는 히스토리언을 대체하지 않는다. 장기 저장을 제공하지 않는다." [독립] https://itotinsider.substack.com/p/the-unified-namespace-uns-demystified (확인 2026-09-29). 요청·응답 방식(명령 같은)은 MQTT 5로 표현은 되지만 브로커 대부분이 거기에 맞춰 최적화돼 있지 않아 별도 API 층을 흔히 둔다는 설명도 있다. [벤더] Synadia https://www.synadia.com/blog/what-a-unified-namespace-requires (검색 발췌)
3. **ML은 OT 가까이, LLM·에이전트는 OT 밖.** CISA 등 9개 기관이 이 배치를 표로 적었다. [표준] p.5–6

### 1-E. 길 목록 — 데이터·명령·알람이 가는 길

**데이터(위로) — 주류**
- D1. 제어기 → 엣지 게이트웨이(OPC UA·Modbus 등으로 읽음, 변화 시 보고) → 사이트 브로커(UNS 토픽) → (DMZ 중계·복제) → 중앙 스트리밍/클라우드. [재단] Sparkplug: "값이 바뀔 때만 보낸다(Report by Exception). 주기 발행은 원칙적으로 쓰지 않는다." / [벤더] Azure: L2 커넥터 → L2 브로커 → L3 브로커 → L4 프록시
- D2. 제어기 → SCADA(직접 폴링 또는 브로커 구독) → 화면. [표준] NIST §2
- D3. SCADA/브로커 → 사이트 히스토리언(OT L3) → DMZ 복제 히스토리언 → 기업 사용자. [표준] CISA DiD 2016
- 공통 원칙: OT에서 밖으로 **밀어낸다(push)**. 바깥이 OT 안으로 들어와 끌어가지 않는다. [표준] CISA AI-OT p.15, p.20

**명령(아래로) — 주류**
- C1. 운전원 → SCADA/HMI(OT 안) → 제어기. 가장 기본 경로. [표준] NIST §2
- C2. 바깥(최적화·AI·업무 시스템)의 쓰기 요청 → **검증 통로 하나**(보안 게이트웨이·요청 검증) → 제어 영역. 최종 수용 여부는 제어 영역이 정한다. [표준·업계 권고] NAMUR NE 178(2025)
- C3. 브로커 경유 명령은 **남겨 두지 않는다.** Sparkplug는 NCMD·DCMD를 "QoS 0, retain=false로 발행해야 한다(MUST)"고 정한다. [재단] Sparkplug 3.0 tck-id-topics-ncmd-mqtt / dcmd-mqtt
- C4. 벤더 참조에서도 쓰기는 **자산 단위 요청 토픽 + 요청/응답 짝(상관 ID) + 성공/실패 응답 발행**으로 만든다. Azure OPC UA 커넥터는 쓰기 전에 "요청의 모든 데이터 포인트가 대상 데이터셋에 있는지 확인"하고, 결과를 응답으로 내며, 바뀐 값을 원래 데이터 토픽으로 다시 낸다. [벤더] https://learn.microsoft.com/en-us/azure/iot-operations/discover-manage-assets/overview-opc-ua-connector (확인 2026-09-29)
- C5. AI가 제어를 직접 바꾸는 것은 제한한다. "사람이 개입하지 않는 AI의 OT 능동 제어를 제한하라." "AI·LLM은 거의 확실히 OT의 안전 결정을 내리는 데 쓰이면 안 된다." [표준] CISA AI-OT p.8, p.16

**알람 — 주류**
- A1. 공정 알람은 **제어기·SCADA가 만들고 SCADA 화면에서 운전원이 처리**한다(중앙 알람). [표준] NIST §2
- A2. 알람의 정의: "운전원에게 설비 고장, 공정 이탈, 이상 상태를 알리고 **대응을 요구하는** 소리·화면 수단". 대응이 필요 없으면 알람이 아니다. 알람마다 원인·결과·조치·대응 시간을 문서로 정한다(합리화). 권장 부하는 운전원 1명당 10분에 약 1건(최대 약 2건). [표준] ISA-18.2 / IEC 62682 — ISA 페이지 https://www.isa.org/standards-and-publications/isa-standards/isa-18-series-of-standards 와 Control Engineering 해설(Yokogawa 저자, 2013) https://www.yokogawa.com/us/library/resources/media-publications/implementing-alarm-management-per-the-ansi-isa-182-standard-control-engineering/ (확인 2026-09-29, 해설 기사는 [벤더] 저자)
- A3. 분석·AI가 만든 경고는 운전원 화면으로 들어가되 오경보를 줄여야 한다. CISA 지침은 AI의 "알람 오류가 인지 부하를 늘린다"를 위험으로 꼽고, AI 감시 화면을 "기존 HMI 화면에 통합"하길 권한다. [표준] p.8, p.19
- A4. 플랫폼(서버·망) 경보는 보안·운영 담당의 감시 체계(중앙 로깅·SIEM)로 간다. 공정 알람과 목적이 다르다. [표준] NIST §5.2.3.2 / 판단: 둘을 같은 알람 목록에 섞으면 ISA-18.2의 "대응이 필요한 것만 알람" 원칙이 깨진다.

## §4-3. AI·분석이 SCADA에 붙는 현업 방식

### 3-A. 배치 — 어디에 붙나

| 원칙 | 내용 | 근거 |
|---|---|---|
| 층에 따라 AI 종류가 다르다 | ML 예측·이상 탐지는 L1–L3(PLC·엣지의 경량 모델, SCADA 데이터 분석, 히스토리언 데이터로 예지정비). LLM·에이전트는 L4–5에서 "OT망에서 내보낸 데이터"로. | [표준] CISA 외 9개 기관, AI-OT 지침(2025-12-03) 표1 p.5–6 |
| AI는 OT에 계속 붙어 있지 않는다 | push 방식·브로커 방식을 우선. 업무망으로 넘길 때 단방향 전송과 감사되는 중간 버퍼. "AI 시스템이 OT로 들어가는 상시 공격 경로가 되지 않게." | [표준] 같은 지침 p.15, p.20 |
| AI 감시 예시는 "읽기 전용" | 지침의 감시 예시는 "OT 데이터 출력에 읽기 전용 접근을 가진, 데이터 영역의 예지정비 시스템"이다. | [표준] p.19 |
| 실패하면 기존 방식으로 | "AI 기능이 들어간 모든 공정에 전통 자동화나 수동으로 되돌아가는 failsafe를 둔다." 성능이 기준 아래로 떨어지면 비AI 시스템으로 돌아가는 기준값을 정한다. | [표준] p.15, p.18 |

### 3-B. 흐름 — 알람 → 원인 분석 → 사람 승인 → 명령 실행

현업 근거로 확인한 흐름(각 단계 근거):

1. **탐지·알람:** 제어기·SCADA의 공정 알람(A1) 또는 L2–L3 ML 이상 탐지(3-A). 운전원에게 가는 것은 "대응이 필요한 것"만(ISA-18.2).
2. **원인 분석(권고):** AI는 권고를 만든다. 결정은 사람이 한다. 권고에는 판단 과정 설명이 붙어야 한다. "운전원이 AI 출력에 판단 과정의 명확한 문서를 요구하라." [표준] CISA p.11
3. **사람 승인:** "수동적 AI는 권고를 **기존 변경 관리 절차**에 넣어" 사람이 결정한다. [표준] CISA p.18–19
4. **명령 실행:** 능동 제어는 제한한다. 해야 한다면 "안전 한계값, 대체 센서, 상태 변화로 사람 개입 지점을 추가"한다. 바깥 요청은 검증 통로를 거치고 최종 권한은 제어 영역(NE 178). [표준] CISA p.16, p.19 / [표준·업계 권고] NAMUR
5. **기록:** "AI 입력과 출력을 로그로 남긴다." "로그의 AI 신원은 일반 기계·사용자 식별자와 구별되게." 알려진 정상 상태(known good state)를 정해 둔다. [표준] CISA p.18–19

→ 판단: 현업 흐름은 **"AI는 IT 쪽에서 읽고 권고 → 사람이 기존 절차(작업 지시·변경 관리)로 결정 → 실행은 OT의 기존 제어 경로(운전원·SCADA 또는 검증 통로)"** 이다. AI 코드가 제어기에 직접 쓰는 형태를 권하는 표준 문서는 찾지 못했다.

| AI 권한 | 명령 권한 없음, 도구 읽기 전용 | 조치 코드가 직접 씀 | v3 |
| 되읽기 | status 토픽 → Kafka → BPMN 대조 | HTTP /state | v3 |
| 승인 흐름 | BPMN 엔진 | Vue + backend(Process-GPT 미연결) | 둘 다 현업 방식(업무 흐름 엔진·변경 관리) 범위 |
| 실제 구축·실행 | 의뢰서: "실제로 구축·실행" (이번에 검증 안 함) | 가상 설비 한 사례 시연(C) | — |

### 5-B. 길 목록

- **데이터(위로):** B0 → B1 → B2 → B3(UNS) → B5 복제 → B6 → {B7 탐지, B8 저장} → B9·B12. SCADA(B4)는 B3에서 구독. OT 쪽이 밀어낸다.
- **명령(아래로), 수동:** 운전원 → B4 → B3 `cmd` → B2 → B1(검사) → B0. IT를 거치지 않는다.
- **명령(아래로), AI 권고 경유:** B12 제안 → 사람 승인(B13) → Kafka 명령 토픽 → B5 게이트웨이(스키마·화이트리스트·모드·중복) → B3 `cmd` → B2 → B1(최종 검사) → B0.
- **결과 확인:** B1 status/ACK → B3 → B5 복제 → B6 → B13이 명령 ID로 대조. 시뮬레이터 HTTP `/state`는 쓰지 않는다(디버그용으로만).
- **공정 알람:** B1·B4 자체 알람(운전원) + B7 alerts → {B12·B13 사건 접수, B5 경유 B4 표시(표시 전용)}.
- **플랫폼 경보:** 각 구역 지표 → B10 → 인프라 담당. 사건(B13)으로 들어가지 않는다.

### 5-C. 한 대 PC 교육용에서 줄여도 되는 것 / 줄이면 현업과 달라지는 것

| 줄여도 되는 것 (학생에게 "실제는 이렇다"고 한 줄 설명) | 줄이면 현업과 달라지는 것 (지켜야 함) |
|---|---|
| 물리 방화벽 → 도커 망 3개(ot/dmz/it)와 이중 연결 컨테이너로 흉내 | IT 쪽 코드(AI·업무)가 설비·제어기에 **직접** 쓰는 것 |
| 데이터 다이오드·방화벽의 연결 방향 강제 → 규칙을 문서·구성으로 표시 | 제어기(인터록·모드·명령 수용) 층을 없애고 설비가 아무 쓰기나 받는 것 |
| 이중화(브로커·Kafka·DB 1대씩) | 망 구분이 **전혀** 없는 것(IT 장애 시 OT가 계속 도는지 보여줄 수 없음) |
| 안전계장(SIS) → 설명만 | 공정 알람과 플랫폼 경보를 한 목록에 섞는 것 |
| 실제 PLC → soft-PLC | 위 층 코드가 레지스터 주소·설비 이름을 직접 아는 것(확장 때 다시 짜야 함) |
| DMZ를 기능별 여러 개 → 1개 | 명령 메시지를 retain으로 남기는 것 |
| 스키마 레지스트리 → JSON Schema 파일 + 검사 | HMI가 IT(Kafka·Flink) 장애 때 멈추는 것 |
| OT 사이트 히스토리언 → HMI 자체 단기 추세 (정본은 IT라고 명시) | AI 제안이 사람 승인 없이 실행되는 것 |
| 사이트 여러 개 → 1개(단, 토픽·키에 site 자리는 남김) | 되읽기를 제어 경로 밖의 시뮬레이터 전용 API로만 하는 것 |
| MES·CMMS → 작업 지시 표 하나 | 원본 없이 가공값만 저장하는 것 |

## 확인 못 한 것

1. **UNS 도입률.** Deloitte 2025 설문에 UNS 문항이 없다. UNS 시장 규모 보고서(FMI 등)는 방법을 확인 못 해 쓰지 않았다.
2. **이름이 공개된 제조사의 UNS 공장 구조.** 찾은 사례는 벤더 게시물이거나 제조사가 아니었다(예: 전력회사). 공장 안 층 구성(브로커·히스토리언 위치)은 VW·Mercedes·BMW 공개 자료에서도 확인 못 함.
3. **ISA-112 Part 1의 "기능 아키텍처 모델" 층 이름.** 유료 본문.
4. **IEC 62443-3-2 원문 문장.** 목차와 해설만 봄(검색 발췌).
5. **IEC 61511 11.2.4 원문 문장.** 해설 발췌만 봄.
6. **명령 만료·중복 명령 거부를 요구하는 산업 표준 문장.** MQTT 5의 수단만 확인. 만료 시 브로커 동작 문장도 원문으로 못 읽음.
7. **원격 권한 모드(LOCAL/REMOTE) 이름의 표준.** PackML 모드 개념까지만 확인.
8. **프로토콜별 점유율(Modbus 등).** HMS 상세 보고서가 신청형이라 못 봄.
9. **OPC UA Companion Specification 개수.** 재단 페이지에 숫자가 없고, 숫자를 적은 곳은 2차 사이트였다.
10. **Mercedes-Benz MO360 원문.** 403으로 막힘(검색 발췌만).
11. **지식 그래프·에이전트의 현장 운영 비율.** 독립 설문 수치 없음. 학술 검토(37편)와 벤더 발표만 있음.
12. **Kai Waehner 글의 소속 표기.** 페이지에서 확인 못 해 "벤더 성향"으로만 표시.
13. **우리 MQTT 토픽 이름 체계.** B·C 문서에 없다. 코드는 이번 범위(문헌 조사)에서 열지 않았다.
14. **권장 구조의 메모리 합계.** 실행·측정하지 않았다(docker 금지 조건).
15. **이벤트 시간(PLC·DAQ 기준) 관련 표준 근거.** 이번에 찾지 않았다.
