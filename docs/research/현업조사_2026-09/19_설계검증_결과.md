> 정정 내역: 원본 보고서에서 두 곳을 바꿨다. ① 1절 집계 표의 "G 추천 18" 줄 ② 6절 끝 "G 추천 18 판정표". 원본은 이 18개 가운데 8개를 "근거 못 찾음"으로 적었는데, 실제로는 2차 조사가 검색 한도(18회) 때문에 다시 찾지 않은 것이었다. 17번 조사에 이미 근거가 있으므로, 근거 강도와 "숫자는 현장 결정" 여부로 다시 표기했다. 나머지 내용은 원본 그대로다.
>
> 받는 쪽에 알림: C4·C6·업무 서비스·위험 Top 5는 문장만 고쳐서 끝나지 않는다. 설계를 바꿀지 결정이 필요하다.

**한 줄 결론:** 구조의 뼈대(세 구역, OT가 먼저 연결, PLC가 마지막에 검사)는 2026 공공 지침 원문으로 반박되지 않았다. 그러나 다음 세 주장은 원문과 현행 제품 문서로 반박된다.
- "현업도 브로커 두 개, 하나로는 안 된다"
- "게이트웨이는 제품이 없어서 직접 짰다"
- "지침은 분석·업무 시스템이 명령하지 않는다고 했다"(그러면서 REMOTE_AUTO에서 자동 수용)

청중에게 한 말과, 직접 만든 부품 두 개(게이트웨이, 업무 서비스)를 고쳐야 한다.

## 요약
- **맞는 것**
  - 2026 연결성 원칙(NCSC-UK 주도, CISA·FBI·BSI 등 공동, "Secure Connectivity Principles for Operational Technology", 2026-01-14, 8개 원칙) 원문을 처음부터 끝까지 다시 읽었다.
  - 세 구역(C1), OT가 먼저 연결(C2, p.11), 경계와 PLC 앞의 스키마 검사(p.17)는 원문 그대로다.
  - 라우터 iptables는 지침의 최소선(p.26 ACL "minimum", p.27 stateful)을 넘는다.
- **틀린 것**
  - "브로커 두 개가 필수"는 틀리다(C4). Cirrus Link는 DMZ에 브로커 하나를 두라고 권장한다.
  - 게이트웨이 "무료 제품 없음"도 틀리다(C6, 1회차 부분에서 이번에 틀림으로 바뀜). Node-RED mqtt out은 `msg.messageExpiryInterval`을 지원한다. Bento는 2026-09 main에 MQTT 5 출력(`message_expiry_interval`)이 병합됐다(아직 릴리스 전).
  - 업무 서비스(알람 묶기·억제)는 이미 운영 중인 Alertmanager를 두고 직접 짰다. HANDOFF 자체 원칙 위반이다(②).
- **가장 위험한 것(분류 ②)**
  - p.19 "unidirectional … strong authentication"과 p.22 "uni-directional"을 적용하지 않았다.
  - REMOTE_AUTO 자동 수용이 p.25 "observe and analyse, not command or alter operations"와 충돌한다. NAMUR NE 178은 이와 반대되는 근거라서 조건부로 방어할 수는 있다.
  - FUXA를 "보기 무인증"으로 켜 두었다. FUXA는 2026년에 무인증 RCE급 권고가 연달아 나왔다.
  - KISA "엣지·MES를 Industrial DMZ로"는 원문을 확인하지 못했다. KISA 인용으로 쓰면 안 된다(③).

## 2. 주장별 판정 (C1~C10)

### C1 세 구역, IT·OT는 DMZ에서만 만남 — **맞음 / ①** (1회차와 같음)
- **근거:** 2026 p.19 "External connections for data exchange between OT and IT should be brokered through a DMZ" / 2026 p.25 "These controls should reside in a separate network segment, often called a DMZ."
- **반대 근거:** 우리 구현은 망 세 개를 라우터 컨테이너 하나가 잇는다. "DMZ에서만 만남"을 망 구성이 아니라 ACL이 강제한다(반박은 아니지만 조건).
- **고칠 문장:** "세 구역으로 나누고 IT와 OT는 DMZ에서만 만나게 하라는 것은 2026 공공 지침이 권하는 목표입니다. 우리는 라우터 규칙으로 흉내 냈습니다."

### C2 OT 쪽이 먼저 밖으로 연결 — **맞음 / ①** (1회차와 같음)
- **근거:** 2026 p.11 "All connections with the OT environment should be initiated as outbound connections from within the OT environment."
- **반대 근거:** CISA 2016 p.20은 주 위험을 "application traffic permitted from the DMZ to the control network"로 본다. 우리 브리지 in(DMZ 요청 토픽→OT)은 연결 방향은 맞지만 데이터는 DMZ→OT로 흐른다. 그림에서 "연결을 연 쪽"과 "데이터 방향"을 구분해야 한다(7절).
- **조사 오류:** 12:17·12:106은 "OT가 먼저 연다"를 NIST 근거로 사실처럼 적었다. NIST 800-82r3에는 원격접근 항목의 "should consider" 목록에만 있다(PDF p.140). 근거를 2026 p.11로 바꿔야 한다.

### C3 IT는 DMZ 히스토리언 사본만 조회 — **부분 / ②** (1회차와 같음)
- **근거:** 2026 p.19 "replicate the OT historian to a historian instance in the DMZ via a unidirectional, secure transfer mechanism … IT systems should query the DMZ historian via a secure HTTP-based API with strong authentication"
- **다르게 한 점**
  - ① 사본은 OT 히스토리언 복제가 아니라 DMZ 브로커 스트림을 따로 적재한 것이다.
  - ② TLS·강한 인증이 없다.
  - ③ IT Bento는 히스토리언이 아니라 DMZ 브로커를 실시간으로 구독한다.
- **고칠 문장:** "지침은 'DMZ 히스토리언을 강한 인증 HTTPS API로 조회'를 권합니다. 우리는 인증·암호화를 뺐고, IT가 DMZ 브로커도 직접 구독합니다(교육용 축소)."

### C4 "현업 MQTT도 두 개, 하나로 합치면 안 된다" — **틀림 / ③** (1회차와 같음)
- **반대 근거(원문, 검색 요약만):** Cirrus Link(MQTT 공동 창시자 회사)
  - "The MQTT Servers should be set up in a DMZ and behind a firewall that only allows two inbound ports for connection: 8883 and 443."
  - "Sparkplug pushes the contextualized data up from level 3 to … level 3.5, the DMZ zone, as a secure outbound connection."
  - 즉 DMZ 단일 브로커도 현업 주류 설계다.
- **보강 근거(두 개 방식도 실재):** HiveMQ Edge README "Connect any number of bridges to transport Edge data upstream … build a flexible Unified Namespace"
- **우리 설계를 살리는 진짜 근거:** "현업은 두 개"가 아니다.
  - 2026 p.31 "OT systems that provide critical functions should, where possible, be designed to facilitate isolation, allowing them to function independently of external dependencies"
  - 2026 p.7 "could a business system outage cause an OT process to shut down?"
  - FUXA가 UNS를 구독하므로, DMZ 단일 브로커면 DMZ가 끊길 때 OT 화면이 멈춘다. 55초 끊김 실험이 이 근거의 실측이다.
- **조사 오류:** 16:26 O5를 p.19로 근거한 것은 틀렸다(p.19에 브리지 언급 없음). 14:23 "브로커 1개" 권고는 Cirrus Link 방식으로는 근거가 있지만, HMI가 UNS를 쓰는 우리 구조에서는 p.31 때문에 약하다(부분).
- **고칠 문장:** "현업에는 DMZ 브로커 하나에 공장 쪽이 밖으로 접속하는 방식(Cirrus Link)과, 공장 브로커에서 브리지로 올리는 방식(HiveMQ Edge)이 둘 다 있습니다. 우리는 OT 화면이 DMZ 없이도 돌아가야 한다는 지침(p.31 격리) 때문에 두 번째를 골랐습니다."

### C5 요청만, 게이트웨이 형식 검사 → OT 수용 결정 → PLC 마지막 검사, 응답 두 겹 — **부분 / ①+②** (1회차와 같음)
- **근거**
  - 2026 p.17 "Schemas should be used to inspect and verify protocols and data payloads at key trust boundaries. These boundaries may exist between networks (for example the OT/IT boundary) or between services (for example in front of SCADA control software or a programmable logic controller)."
  - OPC 10031-4 §6.2.1.4 StoreAndStart: "receives a new job order and stores the new job order in local storage, and start it as soon as the Job Order receiver is ready to start". §6.2.1.1 "Calling the Start Method switches the state from NotAllowedToStart to AllowedToStart" — Store 후 Start 흉내는 원문과 맞다(검색 요약만).
  - NAMUR NE 178 공지: "The ability for information (change requests) to be communicated automatically from the 'outside' psM+O back into the OT CPC"
- **반대 근거:** 2026 p.25 "monitoring, analytics, and business systems do not have direct control capabilities over OT assets. These systems should be designed to observe and analyse, not command or alter operations." REMOTE_AUTO 자동 수용은 이 문장의 "alter operations"에 해당한다.
- **방어:** NE 178(2025-03-10판 발행, DIN Media 목록)은 검증을 거친 자동 반영을 명시적으로 허용한다. 두 문서가 충돌하므로 "지침대로"가 아니라 "NE 178 쪽을 택했다"고 밝혀야 한다.
- **조사 오류:** 18:31 "Part 112"는 틀린 명칭이다. OPC 10031-4 "Part 4: Job Control"이 맞다.

### C6 게이트웨이 직접 제작, "이 역할만 하는 무료 제품 없음" — **틀림 / ④** (1회차 부분 → **틀림**)
- **반대 근거 ① Node-RED:** MQTT Out 노드 도움말(FlowFuse가 Node-RED 코어 도움말을 옮겨 둔 페이지, 보조 출처) "msg.messageExpiryInterval (number) – expiry time, in seconds". http in·http response는 코어 노드다. 이미 스택에 있는 제품 계열로 두 요구를 모두 채울 수 있다.
- **반대 근거 ② Bento PR #991(2026-09 병합):** "Output — the 3.1.1 fields plus the MQTT 5 publish properties (content_type, response_topic, correlation_data, message_expiry_interval, payload_format_indicator)". 사용자 실측 ①(만료 표시 불가)의 원인은 "Bento's mqtt components speak MQTT 3.1.1 only"였고, 이 PR로 해소됐다. 단 실험 컴포넌트이고, 최신 태그 릴리스 v1.21.2(2026-09-11)가 PR 병합보다 앞선다. latest 금지 원칙상 태그 릴리스를 기다려야 한다.
- **반대 근거 ③ Bento 문서:** "It's possible to route the result of any Bento processing pipeline directly back to an input with a sync_response output". 실측 ②(즉시 거부 응답)가 제품 한계인지 설정 문제인지는 다시 시험해야 한다.
- **2026 지침도 불리:** p.15 "Each additional connection, especially if implemented in an ad hoc or bespoke manner, introduces potential vulnerabilities" / p.16 "Connectivity should be robust and reusable, minimising the need for bespoke solutions"
- **고칠 문장:** "게이트웨이는 처음에 Bento로 안 돼서 직접 짰습니다. 지금은 Node-RED나 새 Bento로도 할 수 있어 교체를 시험 중입니다. 현업은 이 자리에 L7 방화벽이나 교차 도메인 장비(상용)를 둡니다."

### C7 Grafana·Prometheus는 IT층, HMI는 OT층, "대시보드는 DMZ 사본(p.19)" — **부분 / ③** (1회차와 같음)
- p.19에는 대시보드라는 단어가 없다(전문 확인). 게다가 우리 Grafana는 IT InfluxDB(분석 결과)를 보므로, "DMZ 사본을 본다"는 말은 우리 구현과도 다르다.
- HMI를 OT에 둔 것은 p.19 "Industrial control protocols … should be restricted to isolated OT network segments"와 맞다.
- **고칠 문장:** "대시보드 위치는 지침에 없습니다. 우리 판단으로 IT에 두었습니다."

### C8 칸별 무료 대체 — **부분 / ②** (1회차와 같음)
- **FUXA 2026 권고(GitHub Advisory, 검색 요약만)**
  - CVE-2026-25938 "Unauthenticated Remote Code Execution in Node-RED Integration" 9.5 Critical(1.2.11에서 수정)
  - CVE-2026-43945·43947 8.9 High(1.3.1에서 수정)
  - CVE-2026-67443 9.2(1.3.2 이하, 1.3.3에서 수정. "/api/heartbeat" guest 토큰으로 Node-RED 편집기 접근)
  - 1.3.4는 이들을 피하지만, 반년 사이 무인증 RCE급 권고가 반복되는 제품이다.
- 15번이 Rapid SCADA 6을 "더 튼튼"이라 적어 놓고, 보고서에서 FUXA를 "유일한 공정 화면"이라 말한 것은 모순이다.
- **고칠 문장:** "FUXA는 공식 도커 이미지가 있어 골랐습니다. 근거 겹침만 보면 Rapid SCADA 6이 더 튼튼하다는 조사도 있습니다."

### C9 원본에서 바꾼 이유 — **맞음 / ①** (1회차와 같음, 이번 회차 EMQX 재검색 없음)
- 추가: Bento mqtt가 3.1.1 전용이었다는 사실(PR #991 원문)은 "브리지를 Mosquitto에 맡긴" 선택을 뒷받침한다.

### C10 구역마다 Prometheus, OT --agent → DMZ, IT /federate — **부분 / ④** (1회차와 같음)
- 방향은 p.11과 맞다.
- 17:626이 G5 근거로 든 p.29는 "Ensure all connectivity is logged and monitored"일 뿐, 구역 배치나 방향을 말하지 않는다(전문 확인).
- 14:235 "DMZ Prometheus가 OT를 스크랩"은 DMZ→OT 신규 연결이라 p.11 위반이다(틀림).

|---|---|---|---|---|

**UMH 문장 판정**
- UMH: "we strongly recommend NOT using it to intervene in the production process, e.g., process control or ensuring safety mechanisms". 이유는 "not designed to ensure the safety … guaranteed time-sensitive reactions"다.
- 즉 제어 루프와 안전 기능을 Node-RED에 두지 말라는 말이지, 검증된 설정값을 PLC에 전달하는 것 자체를 금지하는 말이 아니다.
- HiveMQ도 엣지에서 PLC로 쓰는 기능(남향 쓰기)을 제품 기능으로 팔면서 "strongly recommends testing southbound communications against a non-production environment"라고만 경고한다.
- 따라서 이 문장은 수신기·엣지 쓰기 구조에 대한 **조건부 반대 근거**다. 조건은 두 가지다.
  - ① 인터록·범위·되읽기를 PLC가 가질 것 — 우리는 충족.
  - ② Node-RED에 시간 보장이 필요한 제어를 두지 않을 것 — 충족.
- 2026 p.23 "OT gateway devices … high-value targets"에 따라 엣지 Node-RED의 패치와 편집기 잠금이 필요하다.

**"현업도 직접 짜는 것" 네 가지:** PLC 프로그램, Flink 탐지 규칙·잡, AI 학습 코드는 모두 맞음(제품이 규칙 작성을 전제로 함). 가상설비는 교육용이라 해당 없음(맞음).

## 4. 설계 자체 위험 Top 5

1. **단방향 아님 + TLS·강한 인증 없음(②)**
   - p.19 "via a unidirectional, secure transfer mechanism … strong authentication", p.22 "Where possible, establish outbound only uni-directional connectivity", p.21 MFA.
   - 우리 브리지는 한 연결로 양방향이고, DMZ InfluxDB에는 TLS·강한 인증이 없다.
   - 교육용 축소라고 명시하지 않으면 "지침대로"는 거짓이다.
2. **REMOTE_AUTO 자동 수용 vs p.25(②, NE 178로 조건부 방어)**
   - IT에 사람 승인자가 있으므로 AI-in-OT 지침(CISA·ASD ACSC 주 저자, "Principles for the Secure Integration of Artificial Intelligence in Operational Technology", 2025-12-03)의 human-in-the-loop 취지는 충족한다(NSA 발표 요약 "Incorporate a human-in-the-loop into critical decisions". CISA 원문 PDF는 봇 차단으로 못 읽음).
   - 그러나 p.25 문구와는 충돌한다.
3. **FUXA 보기 무인증 + host.docker.internal 우회(②)**
   - GitHub Advisory Database에서 2026년 FUXA 무인증 RCE 권고를 번호로 최소 4건 확인했다.
     - CVE-2026-25893: heartbeat refresh API로 관리자 JWT 발급, 1.2.10에서 수정
     - CVE-2026-25895: 업로드 API 임의 파일 쓰기
     - CVE-2026-25938: Node-RED 통합
     - CVE-2026-43947: 스크립트 테스트 모드 권한 우회, 1.3.1에서 수정
   - 모두 인증 경로 결함이다. "보기 무인증"을 끄는 것은 비용이 들지 않는 개선이다.
4. **외부 시스템을 AI 하나로 좁힘(②/③)**
   - p.15는 연결 주체로 "business systems, billing platforms, and external vendors"를 든다. p.16은 "Connectivity should be robust and reusable"을 권한다.
   - AI 전용으로 설계한 요청 길은 00번 의뢰서 §9와 어긋난다.
   - 필드(job_order_id·work_master_id)는 ISA-95라 MES도 쓸 수 있다. "요청자 종류" 필드를 추가하고 MES 흉내 요청자를 하나 두면 해소된다.
5. **근거로 포장된 우리 판단(③)**
   - KISA "엣지·MES를 Industrial DMZ로"는 원문을 확인하지 못했다. 보조 자료(AhnLab)는 MES를 Level 3에, 히스토리언·RTDB를 Level 3.5에 둔다.
   - CPwE "All data is transient; the IDMZ does not permanently store data"는 2026 p.19의 DMZ 히스토리언과 충돌한다. DMZ에 7일 저장하는 것은 2026 쪽을 택한 것이라고 밝혀야 한다.

**"지침이 권하는 원칙 / 우리 구현 / 교육용 축소" 구분법:** 모든 설계 문장 끝에 꼬리표를 하나씩 붙인다. 꼬리표가 없는 문장은 쓰지 않고, 인용할 때 should·may·if를 빼지 않는다.
- [지침 권고: 문서·쪽, should/may 그대로]
- [현업 사례: 회사명]
- [우리 판단]
- [교육용 축소: 무엇을 뺐고 현업은 무엇을 쓰는지]

**그림 표기법:** 선마다 두 가지를 따로 그린다.
- ① 연결을 연 쪽: 선 시작점에 "●"
- ② 데이터 흐름: 화살표 머리
- 예: OT 허브 ●──▶ DMZ(데이터) / OT 허브 ●◀── DMZ(요청: 연결은 OT가 열었지만 데이터는 안으로 들어옴)
- 요청이 들어오는 선은 색을 달리하고 "검사 3겹" 표시를 붙인다. 그러면 p.11(연결 방향)과 CISA 2016의 "DMZ→제어망 애플리케이션 트래픽" 위험을 한 그림에서 함께 보여 줄 수 있다.
