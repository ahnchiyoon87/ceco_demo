## 0. 한 문단 요약

V1 IoT/SCADA/AI 프로토타입을 기준선으로 고정한다. **2025~2026년 최신 트렌드 후보 기술**로 모듈을 하나씩 교체해 빠르게 구현(바이브 코딩)한다. 같은 시나리오·같은 측정으로 비교해 채택/유지를 결정한다. 이것을 3회전 반복해 **V1 → V2 → V3 진화 궤적**을 만든다. 궤적에는 기술선정·온톨로지 개선·시나리오 개선이 모두 증거와 함께 남아야 한다. 비중은 **IoT·SCADA(L1~L6) 약 80%, AI(L7~L9) 약 20%**. 기간은 **5영업일**.

## 3. 절대 규칙

1. **측정하지 않은 수치를 쓰지 않는다.** 미측정은 `NOT MEASURED`. 벤더 벤치마크를 로컬 측정처럼 쓰지 않는다.
2. **`harness/`, `scenarios/`, `gates/`는 후보 구현 작업 중 수정 금지.** 잘못됐다고 판단되면 `QUESTIONS.md`에 적고 그 항목만 멈춘다. 후보를 통과시키려고 시나리오·기대결과·판정기준을 바꾸면 그 실험은 무효다.
3. **한 실험에서 한 모듈만 교체한다.** 여러 모듈을 동시에 바꾸는 것은 §12.3 클린시트 비교에서만 허용하고, 그때는 "구조 비교"로 별도 표시한다.
4. **안전 Gate(G1~G8) 하나라도 실패하면 탈락.** 성능·트렌드 점수로 상쇄하지 않는다.
5. **판정 기준은 결과를 보기 전에 확정한다.** 확정 후 변경 금지.
6. **실패·기각·보류 실험을 삭제하지 않는다.**
7. **명령 송신 성공 ≠ 실제 상태 변경.** 항상 HTTP `/state`(seq 증가 포함)로 재확인한다.
8. **실제 설비에 연결하지 않는다.** 가상설비만 사용한다.
9. **컴포넌트를 제거할 때는 그것이 제공하던 기능과 대체 경로를 먼저 적는다.** 대체 경로가 없으면 제거하지 않는다.
10. **`latest` 이미지 태그를 쓰지 않는다.** 모든 이미지는 버전(가능하면 digest)으로 고정하고 EXP 로그에 기록한다.
11. **버전·라이선스는 PoC 당일 공식 릴리스 페이지에서 재확인**하고 EXP 로그에 URL과 함께 기록한다. 참고 자료의 `[미검증]` 항목은 특히 그렇다.
12. 헷갈리지 말 것: SCADA 조작(FUXA/Vue) ≠ 관측(Grafana/Prometheus), 알람 ≠ 원인 확정 ≠ 정지, 알람 확인 버튼 ≠ 고장 복구, 그래프 DB 교체 ≠ 온톨로지 개선.

## 4. V1 시스템 정확한 이해 (반드시 먼저 읽을 것)

출처: `docs/research/system-description.html`. 이 절의 내용과 V1 실제 코드가 다르면 **코드가 맞다**. 차이는 `harness/V1_FACTS.md`에 기록한다.

### 4.1 가상 공정 (L1)
- 교육용 **물리모델 시뮬레이터**다. 그림만 움직이는 화면이 아니다. 명령이 반영되고 물리모델이 다음 센서값을 계산한다.
- 공정 흐름: 원료탱크 TK-101(레벨) → 공급펌프 P-101(운전·유량·모터전류) → 반응기 R-101(레벨·온도·압력·pH), 교반기 M-101(운전·전류·진동), 재킷/히터 HX-101(재킷온도·내부온도 별도, 열전달 지연) → 배출밸브 CV-101(개도·실제 유량, 개도≠유량 비례).
- 대표 태그: TT-101 반응기 온도, PT-101 반응기 압력, IT-102 교반기 전류, VT-101 교반기 진동. **계측 태그 12개**.
- Modbus TCP: 코일 = 기동/정지(1 운전, 0 정지), 레지스터 = 설정값. 온도 설정은 ×10 스케일(72℃ → 720).
- HTTP `/state`: 새 seq와 운전 상태를 반환한다. 명령 후 상태 확인에 쓴다.
- 고압 인터록(압력이 높으면 정해진 동작을 막거나 멈춤), 이상 주입 기능이 있다.
- 냉각 장치는 없다. 목표 온도를 낮춰도 즉시 내려가지 않는다.

### 4.2 데이터 경로 (L2~L6)
```
가상설비 ─Modbus─▶ EdgeX(device-modbus 폴링 → 이벤트 처리 → MQTT export)
        ─MQTT(edgex/telemetry)─▶ EMQX ─▶ Telegraf#1(수집: MQTT→Kafka 형식 변환)
        ─▶ Kafka raw
Kafka raw ├▶ Flink 규칙 작업 (상·하한 / Z-Score / CEP 시간·순서 패턴)
          ├▶ Flink ONNX 작업 (전처리 → Autoencoder 이상 점수)     ※ 두 작업은 raw를 각각 병렬로 읽음
          └▶ Telegraf#2(저장: Kafka→InfluxDB)                    ※ 원본 저장은 Flink를 거치지 않음
Flink ─▶ Kafka clean / score / alerts
Kafka clean/score ─▶ Telegraf#2 ─▶ InfluxDB
Kafka alerts ├▶ Telegraf#3(알람 중계: Kafka→MQTT scada/hmi/latest-alert) ─▶ EMQX ─▶ FUXA 최근 알람
             └▶ Pilot 알람 접수 워커 ─▶ 사건 등록(중복 관측 결합) ─▶ PostgreSQL
InfluxDB ─▶ Grafana (공정 이력)
Prometheus(EMQX·Kafka·Flink 등 운영 지표) ─▶ Grafana, Alertmanager(운영 경보, 설비 정지 경로 아님)
```
- **Telegraf는 한 도구를 3가지 설정으로 쓴다**: #1 수집, #2 저장, #3 알람 중계.
- Kafka raw/alerts/clean/score는 같은 Kafka의 별도 토픽이다.

### 4.3 제어 경로 (3개, 서로 분리)
| 경로 | 흐름 | 검사 |
|---|---|---|
| C1 FUXA 직접 조작 | FUXA ─Modbus TCP─▶ 가상설비 (FUXA가 직접 계측·조작) | FUXA 자체 |
| C2 Vue 통합 대시보드 직접 조작 | 브라우저 ─API─▶ 백엔드 직접 제어 기능 → 입력 범위·기동 조건 확인 → Modbus 명령 → `/state` 재확인·요청값 비교 → 업무 DB 기록 | 백엔드 |
| C3 AI 제안 승인 조치 | 알람 → 사건 → 사람이 분석 시작 → Agent(조회 도구, LiteLLM) → 근거·불확실성·대응안 → LangGraph 검토 대기 → 담당자 승인/반려 → 승인 시 Pilot이 **조건 재검사** → Modbus 정지 명령 → `/state` 확인 → PostgreSQL 기록. 반려 시 명령 없음. "점검 요청" 승인은 업무만 기록 | Pilot |
- **AI가 화면 버튼을 대신 누르는 경로는 없다.** Grafana·Alertmanager는 제어 경로가 아니다.

### 4.4 AI 레이어 (L7~L9, 이번엔 가볍게)
- L7: 원본 문서·절차(버전·출처), Neo4j(설비↔센서↔문서), 지식 후보 검토 파이프라인(원본 등록 → 관계 후보 → 출처 검토 후 게시), 근거 조회(그래프/시계열/현재 상태).
- L8: 알람 접수 워커, 조회 도구(알람/센서/문서, 호출 기록 저장), 업무 Agent, LiteLLM(GCP 모델 중계).
- L9: LangGraph(조사 → 검토 대기 → 실행, 저장 상태로 재개; BPMN 모양으로 표시만 함), Pilot, Vue.

## 9. 판정 규칙 (결과 보기 전 확정, 🔧 I7)

후보는 아래를 **모두** 만족하면 채택한다.

1. **G0~G8 전부 통과** (필수, 예외 없음)
2. 시나리오 정답 수 ≥ 기준선
3. **비열등**: p95 지연 악화 ≤ 20%, 메모리 악화 ≤ 30%, 유실·중복 증가 0
4. 아래 중 **하나 이상**:
   - (a) 트렌드·지속성 우위: 기준선 대비 트렌드 판정이 더 좋음(주류/상승 vs 정체/쇠퇴), 또는 라이선스·보안·유지보수 리스크가 명확히 감소 — 근거 URL 필수
   - (b) 복잡도 감소: 컨테이너 수 또는 설정·코드 LOC 20% 이상 감소
   - (c) 성능 개선: p95 지연 또는 메모리 20% 이상 개선
5. 후보끼리 모두 조건을 만족하면 (b)(c) 개선폭이 큰 쪽, 그래도 같으면 트렌드 판정이 앞선 쪽을 택한다.

해석:
- 이 규칙은 **"최신 트렌드를 우대하되, 안전·기능을 잃거나 눈에 띄게 나빠지면 채택하지 않는다"**는 뜻이다.
- 조건을 만족하는 후보가 없으면 기준선을 유지하고 그 사실을 궤적에 기록한다. 유지도 결과다.

### 11.4 [EXP-140대] L4 규칙·CEP — "CEP는 요즘 안 쓴다" 결론 내는 실험 (최우선)
문헌 판정(기록용): 독립 CEP 엔진(Esper·Siddhi·TIBCO·Apama)은 쇠퇴/레거시. CEP 기능은 Flink(MATCH_RECOGNIZE, CEP 라이브러리)에 흡수되어 2026년에도 유지보수 중(Flink 2.2.1, 2026-05). 따라서 질문은 **"12태그 규모에 Flink가 필요한가, 패턴 탐지를 무엇으로 구현할 것인가"**다.

| EXP | 후보 | 구현 요점 | 주의 |
|---|---|---|---|
| EXP-141 | Flink DataStream + CEP (기준선. Flink 1.x면 2.x로 버전만 올린 변형도 기록) | `begin(cur).followedBy(vib).within(N s)` | JVM·JM/TM 자원 |
| EXP-142 | **Flink 2.x SQL MATCH_RECOGNIZE** | `PATTERN (A X*? B) WITHIN INTERVAL 'N' SECOND` 형태로 우회. Z-Score는 `OVER (RANGE INTERVAL ...)` | SQL은 사실상 엄격 연속(`next`)만 지원, `followedBy`·`notFollowedBy` 없음(FLINK-33428). `WITHIN` 필수 |
