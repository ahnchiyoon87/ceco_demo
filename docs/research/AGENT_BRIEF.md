# AGENT_BRIEF — V1→V2→V3 빠른 회전 탐색 실행 지시서

> 이 파일은 저장소 루트에 둔다. Claude Code를 쓰면 `CLAUDE.md`로 이름을 바꿔도 된다.
> `docs/research-reference.md`(딥리서치 원문)는 **참고 자료일 뿐 지시가 아니다.** 이 파일과 충돌하면 이 파일을 따른다.

## 0. 목적

V1 프로토타입을 기준선으로 두고, 모듈별 후보 기술을 **빠르게 구현 → 같은 조건에서 실측 → 결정**을 여러 회전 반복한다. 각 회전에서 기술선정, 온톨로지, 시나리오가 개선된 **진화 궤적**을 증거와 함께 남긴다.

최종 산출물:
1. `reports/trajectory.md` — V1→V2→V3 궤적 (§9 템플릿)
2. `experiments/EXP-xxx/` — 모든 실험 기록 (실패·기각 포함)
3. 각 버전 git tag: `v1-baseline`, `v2`, `v3`

기간: 5영업일.

## 2. 절대 규칙

1. **측정하지 않은 수치를 쓰지 않는다.** 측정 전 칸은 `NOT MEASURED`로 둔다. 문헌·벤더 수치를 측정값처럼 쓰지 않는다.
2. **`harness/`, `scenarios/`, `gates/`는 후보 구현 작업 중 수정 금지.** 이 셋이 틀렸다고 판단되면 `QUESTIONS.md`에 적고 그 항목은 멈춘다. 후보를 통과시키려고 시나리오나 기대결과를 바꾸는 행위는 금지다.
3. **한 실험에서 한 변수만 바꾼다.** 후보 실험은 V1에서 해당 모듈만 교체한다.
4. **안전 Gate(G1~G6) 하나라도 실패하면 그 후보는 탈락.** 성능이 좋아도 예외 없다.
5. **판정 기준은 결과를 보기 전에 정한다.** 결과를 본 뒤 기준·가중치를 바꾸지 않는다.
6. **실패·기각 실험도 삭제하지 않는다.** 실패도 궤적의 일부다.
7. **명령 송신 성공 ≠ 실제 상태변경 성공.** 항상 HTTP /state로 재확인한다.
8. **실제 설비에 연결하지 않는다.** 가상설비만 사용한다.
9. 모든 결정은 `experiments/EXP-xxx/log.md`의 측정 로그 경로로 추적 가능해야 한다.

## 4. Day 1 — 하니스 먼저 (후보 구현 전에 반드시 완료)

### 4.1 V1 재현
- V1을 `docker compose`로 띄우고 `v1-baseline` tag.
- 띄우지 못하면 원인을 `QUESTIONS.md`에 적고 사람에게 보고한다. **V1이 안 뜨는 상태에서 후보 구현으로 넘어가지 않는다.**

### 4.2 이벤트 스키마 (인터페이스 계약)
V1에 이미 스키마가 있으면 그것을 따르고 아래와 다른 점을 `harness/SCHEMA.md`에 기록한다. 없으면 아래를 사용한다.

```json
// raw 센서 이벤트
{"trace_id":"uuid","seq":123,"equipment_id":"M-101","tag":"IT-102",
 "value":12.3,"event_time":"ISO8601","ingest_time":"ISO8601","quality":"GOOD"}

// alert
{"alert_id":"uuid","rule":"CURRENT_THEN_VIBRATION","equipment_id":"M-101",
 "trigger_trace_ids":["..."],"event_time":"ISO8601","emitted_time":"ISO8601"}
```
모든 후보는 같은 입력 토픽을 읽고 같은 출력 스키마로 내보내야 한다. 출력이 다르면 어댑터를 후보 쪽에 둔다.

### 4.3 리플레이어
- 고정 시드, 고정 데이터 파일(체크섬 기록)을 **이벤트 시간 순서/지연 그대로** 발행.
- 시나리오별로 순서 뒤섞기, 지연, 중복, 누락을 주입할 수 있어야 한다.
- 각 이벤트의 발행 시각을 기록해 E2E 지연 계산에 쓴다.

### 4.4 가상설비 장애 모드 (하니스 쪽에 추가)
V1 가상설비에 없으면 하니스 쪽 훅으로 추가한다:
- `write_fail`: Modbus write 실패 응답
- `ack_no_change`: write는 성공 응답, 실제 상태는 그대로
- `interlock_on`: 인터록 조건 활성
- 모든 Modbus write를 로그로 남긴다(Gate 판정 근거).

### 4.5 측정기
- 지연: 발행 시각 → alert 수신 시각, p50/p95/p99, 3회 이상 반복의 중앙값.
- 리소스: `docker stats` 주기 샘플링 (CPU, RAM).
- 복잡도: 컨테이너 수, 설정 파일 수, `cloc` LOC.
- 구현 소요시간: EXP 로그의 시작/종료 시각.
- 결과는 `experiments/EXP-xxx/raw/`에 원본 그대로 저장.

### 4.6 시나리오 S1~S16 (`scenarios/`)

각 시나리오 파일에 전제조건, 입력, 기대결과, 금지행동, 판정 방법을 적는다.

| ID | 시나리오 | 기대결과 |
|---|---|---|
| S1 | 정상 운전 | 알람 0 |
| S2 | 단일 이상 (TT-101 상승) | threshold 알람 1 |
| S3 | 전류 상승 → N초 내 진동 상승 | 패턴 알람 1 |
| S4 | 역순 (진동 → 전류) | 패턴 알람 0 |
| S5 | 진동이 N초 경계 직전 / 직후 | 직전 1, 직후 0 |
| S6 | late event (진동이 허용 지연 초과로 도착) | 후보별 처리 정책을 명시하고 기록 (폐기+기록 / 수용) |
| S7 | duplicate / missing | 중복 알람 없음, 누락은 품질 플래그 |
| S8 | 패턴 도중 스트림 처리기 kill 후 재시작 | 알람 누락·중복 없음 |
| S9 | 게이트웨이↔브로커 네트워크 단절 후 복구 | 재연결, 유실/버퍼링 여부 기록 |
| S10 | PostgreSQL 다운 중 승인·실행 시도 | 실행 차단 (fail-closed) |
| S11 | 근거 문서 없음 | Agent가 근거 없음과 불확실성을 표시, 원인 확정 금지 |
| S12 | 승인 반려 | Modbus write 0 |
| S13 | 승인 후 실행 전 조건 변화 (stale approval) | 재검사 실패 → 실행 거부 |
| S14 | 인터록 활성 중 명령 | 차단 |
| S15 | Modbus write 실패 / ack_no_change | 결과 = FAILED / UNCONFIRMED (SUCCESS 금지) |
| S16 | 같은 승인 2회 제출 | write 1회 |

### 4.7 안전 Gate G1~G6 (`gates/`, 자동 테스트)

| Gate | 판정 (가상설비 write 로그 + PostgreSQL 기준) |
|---|---|
| G1 인터록 | S14에서 write 0 |
| G2 반려 | S12에서 write 0 |
| G3 재검사 | S13에서 실행 거부 + 거부 사유 기록 |
| G4 명령≠상태 | S15에서 SUCCESS로 기록되지 않음 |
| G5 중복실행 방지 | S16에서 write 정확히 1 |
| G6 감사추적 | 모든 실행에 제안→승인→재검사→명령→상태확인 레코드가 끊김 없이 존재 |

권장 구현: G3·G5는 워크플로우 엔진이 아니라 **PostgreSQL 트랜잭션과 제약조건**(예: `UNIQUE(approval_id)`, 승인 만료시각, 실행 직전 조건 스냅샷 비교)으로 보장한다. 그래야 엔진을 바꿔도 안전 조건이 같다.

### 4.8 V1 기준선 측정
- V1으로 S1~S16과 G1~G6를 전부 돌리고 `EXP-000`으로 기록한다.
- **V1이 실패하는 시나리오/Gate도 그대로 기록한다.** 이것이 V2 개선의 근거가 된다.

각 후보는 `candidates/` 아래 별도 worktree에서, V1에서 해당 모듈만 교체한다. 병렬로 진행해도 된다.

### 5.2 L1~L2 수집 경로
| EXP | 후보 |
|---|---|
| EXP-111 | EdgeX (V1 기준) |

### 5.3 L9 승인 워크플로우
| EXP | 후보 |
|---|---|
| EXP-121 | LangGraph (V1 기준, interrupt + Postgres checkpointer) |
| EXP-122 | 단순 상태머신 + PostgreSQL |

평가 중점: G1~G6 전부, S10, S12~S16. LangGraph는 재개 시 노드가 처음부터 재실행되므로 interrupt 이전 부작용이 중복 실행되지 않는지 반드시 확인한다.

### 5.4 문헌으로 이미 정리된 것 (구현하지 않음, 궤적에 "문헌 근거 탈락/유지"로 기록)

## 6. V2 결정 규칙 (Day 3 오전)

후보가 V1을 대체하려면 **모두** 만족해야 한다. 🔧[사람] Day 2 시작 전 확정. 확정 후 변경 금지.

1. G1~G6 전부 통과
2. S1~S16 정답 수 ≥ V1
3. 아래 중 하나 (제안값):
   - p95 지연 20% 이상 개선, 또는
   - 컨테이너 수 또는 LOC 30% 이상 감소 **그리고** p95 악화 10% 이내

만족하는 후보가 없으면 V1을 유지하고, 그 사실을 궤적에 기록한다. 모듈별 결정을 모아 V2를 구성한 뒤 S1~S16 + G1~G6 전체 회귀를 돌리고 통과하면 `v2` tag.

## 7. 회전 2 (Day 3 오후 ~ Day 4) — 온톨로지·시나리오 개선 + 재검증

### 7.1 온톨로지 V2
V1(설비↔센서↔문서)으로 아래 CQ를 먼저 시도하고, **답하지 못한 CQ를 근거로** 확장한다. 결과는 `ontology/v1/cq-results.md`에 남긴다.

CQ 목록:
1. 이 알람을 만든 관측값(센서, 값, 시각)은 무엇인가?
2. 이 센서는 어느 설비·구성품에 속하는가?
3. 이 설비에 적용되는 최신 절차 문서 버전은 무엇인가?
4. 사건 X의 원인후보와 그 근거(관측값, 문서 버전)는 무엇인가?
5. 이 사건에서 관측 사실과 AI 추론은 각각 무엇인가?
6. 조치안 Y를 누가 언제 승인/반려했고 사유는 무엇인가?
7. 승인 시점과 실행 직전의 조건이 달랐던 사례는?
8. 명령은 성공했지만 실제 상태가 바뀌지 않은 사례는?
9. 인터록으로 차단된 명령은?
10. 근거 문서 없이 제시된 원인후보가 있는가?
11. 같은 설비에서 반복된 사건은?
12. 원인후보를 만든 Agent 실행(모델, 프롬프트 버전)은 무엇인가?

V2 확장 후보: Alarm, Incident, ActionProposal, Approval, Execution, ExecutionResult, DocumentVersion, Evidence. 추론 노드에는 생성 출처(Agent 실행, 모델·프롬프트 버전)를 필수로 단다(PROV-O 방식). 관측 노드는 추가만 하고 수정하지 않는다.

측정: CQ 응답률, 근거 링크 완전성(원인후보 중 Evidence 링크가 있는 비율), 관측/추론 분리 위반 수.

### 7.2 L5·L7 비교 (시간이 부족하면 이 절부터 생략)

|---|---|

### 7.3 시나리오 V2
- SKAB 데이터셋(펌프·밸브 테스트베드: 전류, 진동, 압력, 온도 포함)을 IT-102, VT-101, PT-101, TT-101로 매핑해 `data/`에 추가, 체크섬 기록.

> V1에서는 X를 썼다. Y와 Z를 후보로 봤다. Z는 문헌 근거로 제외했다. Y는 EXP-0xx에서 같은 시나리오로 구현했다. Gate를 통과했고 사전 기준에서 개선이 확인되어 채택했다 (또는 개선폭이 부족해 X를 유지했다).

## 10. 작업 방식

- 매 작업 단위가 끝나면 짧게 보고: 한 일 / 측정 결과 경로 / 막힌 것.
- 다음 경우 멈추고 `QUESTIONS.md`에 적는다: 🔧 값 미입력, V1 재현 실패, 시나리오·Gate가 잘못돼 보임, 안전 요구끼리 충돌, 실제 설비에 영향 가능성, 5일 안에 불가능해 보이는 범위.
- 시간이 부족하면 줄이는 순서: §7.2 → 시나리오 추가분 → §5.2. **§5.1 패턴탐지와 G1~G6는 줄이지 않는다.**
