## 1. 준비 (시연 10분 전)

Windows에서는 저장소 루트의 `Start-Booth.cmd`를 실행한다. Docker Desktop 기동, 이미지 빌드, 서비스 준비를 기다린 다음 **실제 공정값·센서 이력·Flink 4개 작업**까지 확인한다. 이미 빌드한 상태에서는 `Start-Booth.cmd -SkipBuild`, 서비스 변경 없이 상태만 확인하려면 `Start-Booth.cmd -VerifyOnly`를 쓴다. 화면은 http://localhost:38180 이다.

컨테이너가 healthy여도 센서 전달이 누락될 수 있다. 기동 도구는 데이터 경로가 준비되지 않으면 OT 허브를 한 번 재기동하고 다시 검사하며, 그래도 준비되지 않으면 실패를 표시한다. 전체 초기화나 DB 삭제는 하지 않는다. 정비 완주 검증은 아래 시나리오 실행으로 따로 확인한다.

최신 더빙판은 `docs/video/ceco-booth-5min-dub-anchiyoon-v5.mp4` 또는 같은 이름의 `.avi`를 전체 화면으로 재생한다. **4분 41초·안치윤v5 한국어 내레이션·72px 중앙 자막 50개**다. 일반인용으로 윤문한 40개 음성 구간을 기존 화면 시각에 맞췄다. 원본 문서 → 자료 등록 → 관계 후보와 검토·게시 → 온톨로지 → 이상 감지·분석 → 담당자 승인 → 현장 정비 → 30초 회복 확인 → 보고서로 이어진다. 긴 대기를 편집한 원본의 마우스·스크롤·센서 회복 시점은 유지하며, 자막은 하단 남색 전용 영역에 한 겹만 표시한다. 기존 무음 MP4/AVI는 보관했다. 대본은 `docs/video/ceco-booth-5min-dub-script.txt`, SRT는 `docs/video/subtitles/`에 있으므로 별도 자막을 다시 추가하지 않는다. 음성 인식 대조·MP4/AVI 전체 디코딩·핵심 화면 자막 검토를 완료했다. 제작 근거는 `experiments/DUB-20261016/verification.json`이다.

| 재생 시각 | 흐름 |
|---|---|
| 0:00–1:24 | 원본 문서 · 자료 등록 · 관계 후보 · 검토·게시 · 온톨로지 |
| 1:24–2:21 | 정상 설비 · 이상 발생과 센서 변화 · 감지·접수 |

다시 제작할 때는 `pip install -r video/requirements.txt`, `python -m playwright install chromium`으로 녹화 도구를 준비하고, 실제 스택에서 `python video/booth.py`를 실행한다. 다른 시나리오 시험과 동시에 실행하지 않는다. 물리 시나리오를 다시 돌리지 않고 기존 녹화만 편집하려면 `python video/booth.py --render experiments/BOOTH-20261013/natural-final/timeline.json`을 쓴다. `python video/check.py`는 전체 디코딩, 1920×1080·281초, 브라우저 처음/끝 재생을 확인하고 검토용 미리보기 이미지를 만든다.

온톨로지는 HYD 원격 main(6f350503)의 지식 지도를 기준으로 고정된 종류별 열과 선택 연결 강조를 적용했다. 지도 아래에서 연결 근거를 따라가며 원본 속성만 필요할 때 펼친다.

직접 조작할 주소는 **http://localhost:38180 하나**다. 설비 상태와 이상 처리 과정을 같은 화면에서 확인한다.

1. 상황에서 「냉각 계통 · 냉각수 필터 막힘」을 선택하고 「이상 발생」을 누른다.
2. 새 경보가 접수되면 사건이 자동으로 선택된다. 분석과 대응안 작성은 자동 진행한다. 분석을 시작하거나 새로고침하는 버튼은 누르지 않는다.
3. 항상 펼쳐진 전체 흐름도에서 감지 → 원인 분석 → 담당자 검토 → 승인·반려 → 정비 → 복구 확인의 위치를 본다. 근거 부족 경로도 표시한다. 그림은 실제 저장 상태를 표현하며 BPM 엔진이나 단계를 실행하는 버튼이 아니다.
4. 승인 대기에 도착하면 예상 원인과 권장 정비, 승인 시 영향을 확인한다. 검토 의견을 입력하고 「정비 승인」 또는 「반려」를 누른다.
5. 승인하면 정비 진행, 현장 소견, 정상 조건 유지 시간과 복구 결과가 같은 화면에서 갱신된다. 정상 조건을 30초 이상 유지해야 복구 완료다. 결과 기록은 자동 저장된다.

왼쪽 메뉴에는 「운영 현황」·「온톨로지」·「문서·지식」·「처리 이력」을 항상 표시한다. 운영 현황은 설비와 처리 과정을 나란히 보여준다. 원인 분석 중에는 실제 조회 도구와 지금 하는 일을 한두 줄로 자동 갱신한다. 분석 결과와 원인 후보·정비 대안·보고서는 「판단 근거와 정비 결과 자세히 보기」에서 확인한다. 메뉴를 이동해도 진행 중인 사건과 입력한 검토 의견은 유지한다. 모델명, 내부 사건 식별자, 원시 상태와 수동 분석 버튼은 기본 화면에 표시하지 않는다. 기한 만료·중단·연결 실패 때만 재분석이나 다시 연결 같은 필요한 조치를 표시한다. 새 사건을 기다리는 동안에도 조회는 계속된다.

추가 운전 조작은 같은 포털의 「설비 제어 패널」에서 한다. 아이디·비밀번호 입력 없이 운전원으로 연결된다. REMOTE_AUTO에서 승인된 정비가 자동으로 진행된다. 고압 시나리오처럼 사람이 인터록을 해제해야 하면 진행 화면에 필요한 조작을 표시한다. `python tests/tools/open_hands_on.py`는 일반 포털 창 하나를 연다.

반복 시연을 취소할 때만 「상황을 취소하고 다시 시작」을 펼쳐 「이상 초기화」를 누른다. 초기화와 정비 복구는 다르다. 정비·회복 확인 중에는 새 이상과 초기화가 차단된다. 다음 시연 전에는 정상 센서값과 조용한 경보 상태를 확인한다.

| 할 일 | 방법 | 확인 |
|---|---|---|
| 기동 | `make up` (감시 부품 없이 22개, 약 3 GB). `make`가 없는 PC는 `docker compose up -d --build` | `docker compose ps` 전부 healthy · 첫 기동은 학습기 때문에 약 5분 |
| 메모리 | 다른 Docker 스택(hyd 등)은 끄고 시연한다 | PC 여유 2 GB 이상. 두 스택을 함께 켜면 PC 여유가 0.4 GB 까지 떨어진 실측이 있다 |
| 운전 모드 | FUXA → 운전 모드 **REMOTE_AUTO** | REMOTE_MANUAL 이면 정비 단계마다 FUXA "받은 요청"에서 수락해야 한다(그것도 시연 가능) |
| 초기화 | 포털 **상황을 취소하고 다시 시작** → **이상 초기화** | 반응기 목표 온도 부근 · 냉각수 30 m³/h · 진동 약 2 mm/s · 압력 두 계기 일치 |
| 조용해질 때까지 | 초기화 뒤 30~40초 기다린다 | 직전 회복의 급변 신호가 다음 사건에 섞이지 않게(사건 묶음 간격 30초) |

| 화면 | 주소 | 용도 |
|---|---|---|
| 단일 포털 | http://localhost:38180 | 설비 상태·이상 발생·전체 흐름도·검토 의견·승인·정비·복구 결과 |
| FUXA | 포털의 **설비 제어 패널** | 운전원 조작·운전 모드·인터록 리셋(시나리오 3) |

## 2. 시나리오별 흐름

### 시나리오 1 — 반응기 온도 상승(냉각수 계통)
1. 포털 설비에서 "냉각수 필터 막힘" 선택 → "이상 발생". 수 초 안에 반응기 온도가 95 °C 상한을 넘는다.
2. AI 화면에 "반응기 온도 상승 · 냉각 계통" 사건 → 약 1~1.5분 뒤 조치 카드.
3. 카드에서 짚을 것: 원인 판단 표(유량 2.5 m³/h·차압 1.7 bar·냉각수 온도차 41 °C → 스트레이너 지지, 나머지 반박), 대안 손익표(온라인 전환 −25만원 1위, "감속 버티기"는 규칙으로 제외), 뒤집힘 조건.
4. 승인 → 정비팀이 예비 바스켓 전환·막힌 바스켓 세척(소견 "이물 다량") → 온도 107 → 70 °C, 30초 유지 → 작업 보고서.

**변형(재킷 스케일)** — 같은 온도 상승인데 유량·차압은 정상, 냉각수 온도차 3 °C. AI 가 스트레이너를 반박하고 **정지 후 화학 세정**을 고른다(온라인 전환은 "원인과 맞지 않음"). 펌프 정지 → 정비 모드(LOTO) → 세정 → 해제 → 재기동 → 110 → 68 °C. 보고서에 예상 정지 2.4 h 대비 실제 3.7 h(설비 시간) 차이가 그대로 나온다.

### 시나리오 2 — 교반기 진동(회전기계)
1. 포털 설비 "교반기 베어링 마모" → "이상 발생": 전류가 먼저 상한을 넘고 진동이 뒤따른다(CEP 경보).
2. 카드: 첫 경보 시점에 전류 13.7 A·진동 2.2 mm/s(전류가 먼저) → 베어링 지지·축 정렬 반박. 권고 "배치 끝까지 운전 후 교체"(−449만원) vs "지금 교체"(−496만원). 뒤집힘: 고착 위험 비용률 90→135, 배치 폐기 손실 210→157.5, 남은 배치 1.5→2.25 h 이면 "지금 교체".
3. **반려 시연**: "고착 위험이 더 크다, 지금 멈추는 안으로" 사유로 반려 → 「현재 상태로 다시 분석」 → 새 카드가 사유대로 "지금 교체"를 고르고 1위와의 차이(약 45만원)를 밝힌다 → 승인 → 정지·LOTO·베어링 교체("외륜 박리·윤활 탄화")·재기동.

**변형(축 정렬 불량)** — 진동만 크게, 전류는 상한 아래, CEP 없음 → 정렬 지지·베어링 반박 → "배치 후 정렬"(−247만원, 1위). 배치 대기(설비 1.5 h = 실제 9초) → 정지·LOTO·정렬("편차 0.45 → 0.02 mm")·재기동.

### 시나리오 3 — 반응기 고압·인터록(계기·배출)
1. 포털 설비 "압력계 오지시" → "이상 발생": 지시 6.8 barg 로 **인터록이 펌프를 멈춘다**. 독립 계기 PT-102 는 3.2 barg.
2. 카드: 첫 경보 때 PT-101 6.41 vs PT-102 5.20 barg(차 1.2 bar) → 드리프트 지지. "인터록 우회 재기동"(−25.5만원)은 손익 1위지만 **규정으로 제외**, 교정안(−57.8만원) 선택.
3. 승인 → 정비팀 비교 교정(소견 "+3.6 bar 편차, 교정") → **운전원이 FUXA 에서 인터록 리셋**(AI 는 리셋할 수 없다, 화면에 "운전원 조치 필요") → 펌프 재기동 → 두 계기 일치·공급 재개 30초 → 보고서.

**변형(배출 밸브 고착)** — 실제 고압(두 계기 7.53/7.50 barg). 펌프가 멈추면 현재값은 곧 정상처럼 보이므로 AI 는 트립 전 값(배출 0.93 < 공급 3.76 m³/h·액위 79 %)으로 밸브 고착을 지지하고, "순간 과압"은 트립이 가린 것이라 반박 → 밸브 분해 정비("스템 고착, 실제 개도 15 %") → 운전원 리셋 → 재기동.

## 3. 실패 가지(해피패스가 아님을 보이는 법)
- **원인을 틀리면**: 정비팀이 "부품 정상, 교체 안 함" 소견을 내고 계획이 멈춘다(원인 불일치). 이때 정비 모드를 켠 뒤라면 정비팀이 **중단 정리**(분해 부위 복구·LOTO 해제, 설비는 정지 인계)를 하고 끝낸다 → 보고서 → "AI 분석"을 다시 누르면 같은 사건의 소견을 근거로 다른 대안을 고른다(이미 멈춘 설비라 "배치 후" 대안은 규칙으로 제외). 시험 도구 `python tests/e2e/maintenance_scenarios.py s2m` 이 이 가지를 재현한다(시험용 대응안으로 일부러 틀린 계획을 승인).
- **규칙**: 손익 1위라도 규정(인터록 우회·상한 초과 운전·진동 영역 D·예비품 없음)에 걸리면 제외된다.
- **사실값이 바뀌면**: `enterprise.fact`(예: 베어링 재고 0)를 바꾸면 같은 사건에서 다른 권고가 나온다.

## 4. 문제가 생기면
| 증상 | 확인 | 대처 |
|---|---|---|
| 카드가 안 나옴 | AI 화면 "AI 처리 과정" 실패 표시 | "AI 분석" 버튼으로 다시. 실패 사유가 화면에 남는다 |
| 승인 뒤 단계가 "실패" | 단계 사유(모드·정비 모드·인터록) | 운전 모드 REMOTE_AUTO 확인. 결과 불명확한 명령은 다시 보내지 않는다(설계) |
| 시나리오 3 이 "운전원 조치 대기" | FUXA 인터록 상태 | FUXA 에서 인터록 리셋(압력이 5.2 barg 아래일 때만 받는다) |
| 다음 시나리오가 이전 사건에 붙음 | 사건 목록 | 초기화 뒤 30~40초 기다린 다음 버튼 |
| 사건 목록에 흐린 사건이 많음 | "참고 신호 숨기기" | 한계 이탈 없이 통계 급변만 있는 사건(회복·재기동 과도기)이다. 기본으로 숨긴다. AI 는 이런 사건을 자동 분석하지 않는다 |
| 예상 대비 실적 차이가 큼 | 보고서 KPI 표 | 정상이다. 단계마다 작업 요청이 수 초 걸리고 배속(600) 때문에 설비 시간으로는 길어진다. 숨기지 않고 실측대로 보인다 |
