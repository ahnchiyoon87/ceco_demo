탐지 통합 체계
분산 산업용 IoT 파이프라인의 데이터 흐름 및 타당성 평가
현대 제조 공정 및 스마트 팩토리 환경에서는 수만 개의 센서 노드와 프로그래머블 로직
컨트롤러(PLC)에서 방출되는 고빈도 시계열 데이터를 지연 없이 수집하고, 실시간 스트림 분석
및 이상 탐지를 거쳐 영구 저장소와 운영 인터페이스로 전달하는 고신뢰성 파이프라인이
필수적이다1. 센서 네트워크에서 발생한 계측 신호가 MQTT 프로토콜을 통해 수집되고, IoT
미들웨어 및 Apache Kafka 분산 이벤트 스트리밍 백본을 거쳐 분산 스트림 처리 엔진, 시계열
데이터베이스(TSDB), 그리고 최종 HMI/SCADA 대시보드로 전달되는 구조는 엔터프라이즈 IIoT
참조 모델(Reference Architecture)의 표준적 접근법에 완벽히 부합한다3.
이러한 다계층 파이프라인 구성의 타당성은 계층 간 관심사 분리(Separation of Concerns)와
장애 격리(Fault Isolation)라는 분산 컴퓨팅의 핵심 원칙에 기반한다5. 현장 에지 레벨의 경량
네트워크 연결 관리 및 이종 프로토콜 표준화는 전용 수집 계층이 담당하고, 전사 단위의 데이터
내결함성 보장과 고가용성 버퍼링은 Kafka가 전담함으로써 물리적 계측 계층의 불안정성이
상위 분석 및 스토리지 시스템으로 전파되는 현상을 원천적으로 차단한다7.

IoT 미들웨어의 본질적 역할과 메시징 백본 직접 연계의
경계 분석
센서 네트워크에서 송출되는 MQTT 메시지를 엔터프라이즈 파이프라인으로 유입시킬 때, IoT
미들웨어를 경유하는 방식과 Apache Kafka로 직접 파이프라인을 연결하는 방식 사이에는
뚜렷한 기능적·운영적 차이가 존재한다24.
IoT 미들웨어는 단순한 패킷 포워더가 아니며, 물리적 산업 필드 계층과 IT 엔터프라이즈 시스템
간의 구조적 불일치를 해소하는 추상화 계층으로 작동한다3. 산업 현장은 센서 제조사 및 설비
연식에 따라 Modbus-RTU, Modbus-TCP, OPC-UA, BACnet, CAN 등 이종 프로토콜이 난립해
있다3. IoT 미들웨어(예: EdgeX Foundry의 Device Service)는 이러한 산업용 필드버스 신호를
단일화된 JSON 또는 Protocol Buffers 형태의 시맨틱 데이터 모델로 정규화하는 작업을
수행한다26. 또한 디바이스의 상호 인증(mTLS, 토큰 기반 검증), 등록 라이프사이클 관리, 센서의
캘리브레이션 계수 및 물리적 설치 좌표와 같은 디지털 트윈 메타데이터를 유지 관리한다10.
결정적으로, 센서나 PLC 레지스터에 특정 제어 값을 주입하는 사우스바운드(Southbound)
양방향 제어 경로를 수립하고 유지하는 주체는 Kafka가 아닌 IoT 미들웨어다27.
반면, 현장 센서들이 이미 균일한 스펙을 갖추고 표준화된 MQTT 토픽으로 데이터를 자율
발행하고 있으며, 시스템의 요구사항이 단방향 데이터 수집 및 로깅에 국한되어 있다면 IoT
미들웨어를 거치지 않고 MQTT 브로커에서 Kafka로 직결하는 아키텍처가 유리하다12. EMQX와
같은 고성능 분산 MQTT 브로커는 내부 규칙 엔진(Rule Engine)과 내장 Kafka 프로듀서 커넥터를
제공하여, 중간 변환 오버헤드 없이 수십만 TPS의 데이터를 Kafka 토픽으로 즉각 분배할 수
있다12.
그러나 설비 제어 명령을 하향 전파해야 하거나, 장비의 인가 권한을 동적으로 제어해야 하는
SCADA 본연의 기능을 수행해야 한다면 IoT 미들웨어를 진입점에 배치하고, 정제된 이벤트
스트림만을 Kafka로 토출시키는 다계층 구조를 유지하는 것이 아키텍처적 결함을 방지하는
유일한 방안이다4.

데이터 무결성 보장을 위한 신뢰성 수집 체계 및 결측치
보간 전략
무손실 데이터 수집을 위한 전송 계층 신뢰성 메커니즘
무선 센서 네트워크나 광역 공장망은 통신 간섭, 전원 노이즈, 스위치 리부팅 등으로 인한 간헐적
네트워크 단절에 취약하다30. 센서 패킷의 누락 없는 수집을 위해서는 프로토콜과 에지 노드
양단에서 다중 안전장치가 가동되어야 한다.
MQTT 프로토콜 수준에서는 신뢰성 보장을 위해 QoS(Quality of Service) 레벨 관리가
필수적이다. 산업 현장에서는 네트워크 오버헤드가 과도한 QoS 2(정확히 1회)보다는 고유
시퀀스 번호와 타임스탬프를 페이로드에 포함한 QoS 1(최소 1회 전달) 모드를 채택하고, 중복
수신 문제는 스트림 처리 계층의 멱등성(Idempotency) 로직으로 해소하는 것이 표준적이다5.
이와 함께 브로커와 센서 클라이언트 간의 세션 영속성(Persistent Session)을 활성화하여,
일시적인 물리 계층 단절 시에도 브로커가 해당 클라이언트를 위한 미전송 메시지를 인메모리
또는 디스크 큐에 보존하도록 설정해야 한다11.
보다 근본적인 유실 방지 대책은 에지 게이트웨이 레벨의 로컬 역단절(Store-and-Forward)
메커니즘 구축이다9. 광역 네트워크가 완전히 차단되면 브로커의 세션 버퍼는 곧 한계에
도달하므로, 현장 게이트웨이는 인입되는 센서 프레임을 로컬 SQLite, RocksDB, 또는 플래시
메모리 파일 시스템에 트랜잭션 단위로 선기록(Store)해야 한다9. 중앙 서버와의 연결이
재수립되면 에지 에이전트는 로컬 큐에 보관된 이력 데이터를 타임스탬프 순서대로 순차
재전송(Forward)하여 통신 단절 기간의 데이터 공백을 무손실 복구한다32.
센서 결측치 발생 특성과 머신러닝 연동 시의 전처리 필수성
센서 데이터의 결측치는 패킷 드롭뿐만 아니라 센서 하드웨어 결함, 급격한 전압 강하, 센서 헤드
캘리브레이션 지연 등 복합적인 요인에 의해 유발된다30.
머신러닝이나 딥러닝 기반 분석을 수행하지 않고 단순 모니터링 및 시각화 대시보드 운영만을
목표로 하는 경우, 데이터 파이프라인 내부에서 결측치를 인위적으로 보간할 당위성은 낮다.
InfluxDB나 TimescaleDB 같은 시계열 데이터베이스 엔진은 쿼리 실행 시점에 직전 값
유지(LOCF)나 선형 보간 함수를 자체적으로 수행하여 공백을 메우는 기능을 지원한다19. 원천
데이터 레벨에서 인위적으로 계산된 가공치를 덮어쓰게 되면 실제 물리 계측치와 추정치 간의
경계가 모호해져 향후 사고 발생 시 감사 추적(Audit Trail)의 법적·기술적 신뢰성을 훼손할 수
있기 때문이다.
반면 Autoencoder, LSTM, Isolation Forest 등 실시간 다변량 센서 데이터를 기반으로 작동하는
머신러닝 모델을 파이프라인에 통합할 경우, 결측치 보간은 반드시 거쳐야 하는 필수 전처리
공정이 된다15. 딥러닝 모델의 신경망 레이어는 입력 데이터가 고정된 차원의 완전한
텐서(Tensor) 행렬 형태로 연속 유입될 것을 전제한다. 만약 입력 벡터에 결측을 의미하는
$\text{NaN}$이나 공백 타임스탬프가 유입되면 부동소수점 연산 오류가 발생하거나, 비정상
패턴이 아님에도 불구하고 모델의 복원 손실률(Reconstruction Loss)이 폭증하여 시스템 전반에
치명적인 오탐(False Positive)을 유발하기 때문이다36.

결측치 보간을 실행하기 위한 가장 적합한 위치는 Kafka와 시계열 데이터베이스 사이에
배치되는 분산 스트림 처리 계층(Apache Flink)이다36. 에지 게이트웨이는 수백 개 센서의 다변량
상관 회귀나 슬라이딩 윈도우 상태를 유지하기에 메모리와 연산 능력이 제한적이며, TSDB에
일단 적재된 이후에 보간을 수행하는 방식은 실시간 이상 탐지가 요구하는 수십 밀리초 단위의
종단 간 지연시간(End-to-End Latency) 요건을 충족할 수 없다.
복합 이벤트 처리(CEP) 엔진 분석: Esper/EQL vs ksqlDB
vs Apache Flink
센서 데이터 스트림 내에서 단순 수치 비교를 넘어, 특정 이벤트의 발생 순서나 시간적
상관관계를 규명하기 위해 복합 이벤트 처리(Complex Event Processing, CEP) 엔진의 도입이
검토된다17. 과거 임베디드 아키텍처에서 널리 활용된 Esper(EQL 기반)와 현대 분산 스트리밍
생태계의 기술적 상관관계를 면밀히 평가해야 한다.
Esper는 이벤트 구동 아키텍처(EDA)를 구축하기 위해 개발된 고성능 인메모리 CEP 엔진으로,
SQL과 유사한 이벤트 쿼리 언어(EQL)를 사용하여 시간 윈도우, 패턴 매칭(예: "A 이벤트 발생 후
3분 이내에 B가 발생하지 않는 상황"), 인과관계 필터링을 직관적으로 선언할 수 있다17. 그러나
Esper는 태생적으로 단일 프로세스 JVM 내에 임베디드 라이브러리 형태로 내장되어
구동되도록 설계되었다17. 이로 인해 초당 수십만 건의 대규모 트래픽이 집중되거나 고가용성
클러스터링이 요구되는 엔터프라이즈 환경에서는 노드 장애 시 상태 복구와 수평적
확장(Scale-out)에 치명적인 한계를 드러낸다.
현재의 대규모 분산 파이프라인에서는 Esper를 독립 컴포넌트로 유지하기보다는, Kafka
생태계와 네이티브하게 통합되는 ksqlDB나 Apache Flink를 사용하는 것이 표준적이다5.
ksqlDB는 Kafka 상단에서 직관적인 스트림 조인, 필터링, 윈도우 집계를 순수 SQL 문법으로
처리할 수 있어 시스템 도입 장벽이 매우 낮다17. 반면 다중 이벤트 간의 정합적 순서 패턴을
감지하는 순수 CEP 작업이나 커스텀 텐서 조작에는 구조적 한계가 존재한다.
Apache Flink는 Flink CEP 라이브러리를 통해 Esper의 EQL 수준에 필적하는 고도의 비결정적
유한 오토마타(NFA) 기반 패턴 매칭 기능을 분산 환경에서 제공한다5. 더욱이 Flink는 RocksDB
기반의 분산 상태 저장소와 Chandy-Lamport 알고리즘 기반의 비동기 체크포인팅을 지원하여
노드 장애 시에도 '정확히 한 번(Exactly-once)' 상태 복구를 완벽히 보장한다5.
따라서 현대적인 아키텍처 관점에서 Esper를 별도로 배치하여 파이프라인의 복잡도를 가중시킬
필요가 없으며, Apache Flink(또는 상대적으로 단순한 SQL 윈도우 연산일 경우 ksqlDB)를
Kafka에 직접 컨슈머로 결합하여 결측치 보간, 스트림 정제, 복합 이벤트 탐지를 단일 분산
계층에서 통합 수행하는 구성이 가장 합리적이다16.

시계열 저장소 및 메트릭 모니터링 체계: InfluxDB와
Prometheus의 역할 분리
파이프라인 설계에서 가장 심각한 병목과 장애를 초래하는 원인 중 하나는 Prometheus와
InfluxDB의 기능적 중복 및 역할 혼선이다. 두 시스템은 모두 시간에 따라 변화하는 메트릭을
다루지만, 아키텍처 설계 철학과 데이터 모델, 쓰기/읽기 패턴이 근본적으로 다르다18.
Prometheus는 분산 IT 인프라, 컨테이너, 마이크로서비스의 가용성 감시 및 알림을 위해 특화된
시스템이다20. 대상 시스템의 엔드포인트(/metrics)를 정기적으로 폴링하는 주기적 HTTP
Pull(Scraping) 방식을 강제하며, 저장 가능한 데이터 형태 역시 고정된 단일 Float64 수치로 극히
제한된다20. 무엇보다 Prometheus의 로컬 시계열 데이터베이스는 시계열의 식별 태그 조합 수가
기하급수적으로 증가하는 고 카디널리티(High Cardinality) 환경에 노출될 경우 인덱스 크기가
RAM 용량을 초과하여 프로세스 충돌(OOM Crash)을 일으킨다20.
반면 산업 현장의 센서 데이터는 공정 상황에 따라 밀리초 단위로 자율 푸시(Push)되는 불규칙한
이벤트 스트림이며, 부동소수점 외에도 장비 에러 코드, 운전 모드 문자열, 다차원 JSON
페이로드 등 다양한 데이터 타입을 포함한다20. 또한 센서 시리얼 넘버, 공정 라인 번호, 설비
태그 등 수백만 개 이상의 조합을 갖는 극단적인 고 카디널리티 구조를 형성한다19.

랙(Consumer Lag), Flink 잡매니저의 체크포인트 소요 시간, InfluxDB의 디스크 I/O 등을
모니터링하고, 파이프라인 자체에 장애가 발생했을 때 Alertmanager를 통해 운영진에게
즉각적인 경보를 발송하는 역할에 국한되어야 한다21.

스트리밍 파이프라인 내 머신러닝 모델 서빙 표준 구현 방식
머신러닝 알고리즘을 실시간 스트리밍 데이터 파이프라인에 탑재할 때, 모델의 오프라인 학습
주기와 온라인 추론 주기는 철저히 분리되어야 한다48.
오프라인 학습 단계에서는 InfluxDB 또는 장기 데이터 레이크에 누적된 정상 운전 이력 데이터를
Python(PyTorch, TensorFlow, Scikit-learn) 기반 분산 학습 클러스터로 로드하여 Autoencoder
모델을 훈련시킨다49. 학습이 완료된 딥러닝 신경망은 오픈 표준 바이너리 포맷인 ONNX(Open
Neural Network Exchange) 파일로 익스포트되어 중앙 모델 레지스트리에 배포된다50.
실시간 온라인 추론 단계에서는 외부 REST/gRPC API 서버를 호출하는 방식(RPC Callout)을
지양해야 한다. 네트워크 홉으로 인한 지연시간 증가와 API 서버 병목 현상을 방지하기 위해,
Apache Flink 태스크 매니저 프로세스 내부에 C++ 기반의 고성능 ONNX Runtime 엔진을
임베디드(In-Stream Embedded Serving) 형태로 직접 로드한다48.
Flink는 Kafka로부터 센서 스트림을 실시간 소비하면서 결측치를 보간하고 텐서 슬라이딩
윈도우를 형성한 직후, 로컬 인메모리 상에서 ONNX 모델을 직접 호출하여 수 밀리초 이내에
이상 점수를 판출한다48. 이상으로 판정된 이벤트는 Kafka의 별도 알림 토픽(sensor.alerts)으로
재발행되어 운영자 대시보드로 즉시 전파된다54.

SCADA 시각화 레이어의 실체적 분석: Grafana의 기능적
한계와 오픈소스 웹 SCADA
Grafana의 명확한 한계와 오적용 분석
Grafana는 시계열 데이터베이스를 조회하여 다차원 메트릭을 동적으로 표출하고 트렌드를
분석하는 시각화 도구로서는 최고의 성능을 발휘한다22. 그러나 전통적인 산업 플랜트 제어
관점에서 Grafana만을 단독 배치하고 이를 "완전한 SCADA 시스템"으로 정의하는 것은 중대한
아키텍처적 결함을 내포한다22.
SCADA의 본질은 감시(Supervisory)뿐만 아니라 제어(Control)에 있다. Grafana는 기본적으로
시계열 저장소의 데이터를 읽어오는 단방향 읽기 전용(Read-only) 대시보드 구조를 지향한다22.
버튼 클릭을 통해 특정 PLC의 코일 레지스터를 조작하거나 밸브 개도율을 변경하는 양방향 명령
하달(Write-back) 기능이 네이티브로 제공되지 않는다. 외부 API를 호출하는 비공식 플러그인을
적용할 수 있으나, 산업용 제어에서 필수적인 물리적 안전 인터록(Interlock), 쓰기 확인(Echo
Check), 명령 실행 감사 로깅 등의 결정론적 안전 메커니즘을 보장할 수 없다.
또한 Grafana의 패널 체계는 시간 축 기반의 꺾은선 그래프, 바 차트, 게이지 표현에 고착되어
있다. 실제 플랜트 운영자가 필요로 하는 공정 계장 도면(P&ID), 배관 내 유체 흐름 애니메이션,
펌프 및 밸브의 물리적 레이아웃 기반 동적 상태 점멸(Mimic Diagram)을 엔지니어링 표준에
맞추어 시각화하는 데 심각한 제약이 따른다22.
진정한 오픈소스 웹 SCADA 아키텍처와의 결합
이러한 한계를 극복하고 완전한 오픈소스 감시 제어 시스템을 완성하기 위해서는 Grafana와
함께 전문 웹 SCADA 엔진을 병행 배치하는 하이브리드 구성이 요구된다57.
FUXA는 순수 웹 브라우저 환경에서 동작하는 차세대 오픈소스 SCADA/HMI 플랫폼이다22.
엔지니어는 웹 GUI 상에서 드래그 앤 드롭 방식으로 산업용 SVG 심볼과 P&ID 도면을 배치하고,
모터 회전이나 배관 흐름 애니메이션을 직관적으로 바인딩할 수 있다22. 더욱이 FUXA는
Modbus, OPC-UA, MQTT 프로토콜 클라이언트를 자체 엔진에 탑재하고 있어, 공정 감시
도면에서 운영자가 버튼을 클릭하면 현장 게이트웨이나 PLC의 특정 주소 번지로 제어 명령을
직접 하향 전송하는 양방향 SCADA 루프를 완벽히 구현한다22.
ThingsBoard 역시 자체적인 웹 HMI 대시보드 빌더를 내장하고 있으며, 슬라이더, 토글스위치,
제어 노브 등 양방향 RPC(Remote Procedure Call) 위젯을 통해 센서 및 구동기(Actuator)로
즉각적인 제어 페이로드를 전달하는 기능을 안정적으로 제공한다27.
결과적으로, 현장 설비의 실시간 상태 확인 및 양방향 기기 제어는 FUXA 또는 ThingsBoard
대시보드에 일임하고, 장기 시계열 히스토리안 트렌드 분석, 설비 종합 효율(OEE) 통계, 그리고
전체 데이터 파이프라인의 인프라 건전성 모니터링은 Grafana가 담당하도록 이원화하는 것이
엔지니어링 관점에서 가장 이상적인 구성이다22.

기 구축된 오픈소스 IoT 플랫폼 평가 및 사용자 스택 비교
센서 수집부터 엔터프라이즈 백본, 스트림 처리, 분석에 이르는 전 주기를 밑바닥부터(From
Scratch) 독자 구현할 수도 있으나, 검증된 오픈소스 IIoT 플랫폼들의 기능적 특성을 이해하고
요구사항에 맞추어 선별적으로 결합하는 것이 개발 및 유지보수 비용을 획기적으로
절감시킨다24.
ThingsBoard는 장치 관리, MQTT/CoAP/HTTP 전송 엔드포인트, 드래그 앤 드롭 룰 엔진(Rule
Engine), 대시보드를 단일 솔루션으로 제공하는 종합 IoT 플랫폼이다10. 별도의 외부 분석 엔진을
구성하지 않고도 수집된 데이터를 즉시 필터링하거나 경보를 발생시킬 수 있으며, Rule Engine
내에 내장된 Apache Kafka 노드를 통해 특정 조건의 텔레메트리를 엔터프라이즈 Kafka
토픽으로 쉽게 바이패스할 수 있다13. 그러나 플랫폼의 모놀리식/마이크로서비스 구조 자체가
무겁고, 초당 수십만 건 이상의 초고빈도 스트림이 유입될 경우 플랫폼 내부 메시지 큐의
오버헤드가 발생할 수 있다6.
EdgeX Foundry는 리눅스 재단(LF Edge) 산하의 마이크로서비스 기반 에지 컴퓨팅 플랫폼이다4.
상위 시각화보다는 현장 에지 컴퓨터 내에서의 사우스바운드 프로토콜 통합에 특화되어 있다26.
Modbus, OPC-UA 등 산업용 장비의 데이터를 완벽하게 정규화하여 로컬 코어 서비스로 수집한
후, eKuiper와 같은 초경량 룰 엔진을 거쳐 클라우드나 엔터프라이즈의 Apache Kafka, EMQX로
데이터를 안전하게 릴레이하는 '에지 수집 게이트웨이'로서 독보적인 완성도를 갖는다12.
Apache StreamPipes는 산업용 IoT 데이터 스트림의 분석을 노코드(No-code) 환경으로
구축하기 위해 탄생한 오픈소스 플랫폼이다62. 센서 데이터 어댑터, 윈도우 변환 필터, 이상 탐지
알고리즘 등을 웹 파이프라인 에디터 상에서 그래픽 블록 조립 형태로 구성할 수 있어 현장
도메인 엔지니어의 접근성이 매우 높다62. 그러나 고성능 분산 분기 연산이나 복잡한 딥러닝
텐서 처리에는 제약이 따른다.

종합적으로 검토할 때, 사용자가 구상한 기술 조합(MQTT -> 수집 미들웨어 -> Kafka ->
Flink/ksqlDB -> InfluxDB -> Grafana/FUXA)은 특정 상용 프레임워크에 종속되지 않으면서도,
시스템 처리 용량을 무제한으로 수평 확장하고 머신러닝 추론을 초저지연으로 결합할 수 있는
엔터프라이즈급 최상위 아키텍처에 해당한다3.

엔터프라이즈급 최종 권장 아키텍처 및 단계별 구현 로드맵
사용자의 아이디어를 실제 운영 가능한 고신뢰성 시스템으로 구체화하기 위한 엔드투엔드
파이프라인의 물리적 데이터 흐름과 계층별 구현 세부 명세는 다음과 같다.
현장 에지 계층(Tier 1)에서는 공장 라인의 PLC 및 센서가 Modbus나 OPC-UA 프로토콜을 통해
에지 게이트웨이로 물리적 신호를 전송한다3. 게이트웨이에 설치된 EdgeX Foundry는 장비
드라이버를 통해 수집된 바이너리 데이터를 단일 JSON 스키마로 파싱한다26. 만약 외부
네트워크가 단절되면 로컬 SQLite 기반의 Store-and-Forward 모듈이 활성화되어 데이터를
디스크에 누적하고, 통신 복구 시 MQTT QoS 1 및 세션 유지를 적용하여 상위 브로커로 무손실
재전송한다9.
엔터프라이즈 수집 및 백본 계층(Tier 2)에서는 클러스터링된 EMQX 브로커가 수천 대의 에지
게이트웨이로부터 암호화된(TLS) MQTT 스트림을 종단 수신한다12. EMQX의 데이터 통합
브리지를 통해 수신된 센서 텔레메트리는 지체 없이 Apache Kafka 클러스터의
sensor.telemetry.raw 토픽으로 적재된다12. 이로써 전사 차원의 완충 큐가 확보되고 하위
시스템과의 물리적 의존성이 완전히 분리된다8.
실시간 분산 스트림 처리 및 머신러닝 계층(Tier 3)에서는 분산 Apache Flink 클러스터가 Kafka의
원천 데이터를 고속 소비한다5. Flink는 RocksDB 기반의 상태 윈도우를 열어 센서 타임스탬프를
검사하며, 패킷 유실로 인한 결측 구간을 슬라이딩 윈도우 선형 보간 또는 LOCF 알고리즘으로
실시간 채워 넣는다5. 보간이 완료된 완전한 데이터 벡터는 Flink 태스크 매니저에 내장된 C++
ONNX Runtime으로 전달된다48. 사전 학습된 Autoencoder 딥러닝 신경망은 1밀리초 미만의

지연시간으로 재구성 오차             를 계산하여 이상 점수를 도출한다48. 정제된 센서 스트림은
sensor.telemetry.clean 토픽으로, 임계치를 초과한 비정상 이벤트는 sensor.alerts 토픽으로 각각
분기되어 Kafka에 재발행된다54.
저장 및 SCADA 시각화 계층(Tier 4)에서는 두 갈래의 가시화 및 제어 파이프라인이 동시에
작동한다. 정제된 공정 텔레메트리는 Kafka Connect 또는 Telegraf 컨슈머를 통해 InfluxDB(또는
TimescaleDB)로 배치 단위 고속 적재되어 장기 공정 히스토리안을 구축한다18.
현장 공정 운전원은 FUXA 웹 SCADA를 통해 P&ID 도면 상에서 밸브, 펌프의 실시간 상태를 동적
애니메이션으로 확인하고, 필요 시 Modbus/TCP 또는 OPC-UA를 통해 PLC에 직접 양방향 제어
신호를 인가한다22. 공장 관리자와 데이터 사이언티스트는 Grafana를 통해 InfluxDB에 축적된
장기 트렌드와 Flink가 토출한 머신러닝 이상 징후 이력을 교차 분석하며, 동시에 Prometheus를
통해 Kafka의 컨슈머 랙 및 Flink 클러스터의 인프라 건전성을 통합 감시한다20.

종합 결론
검토 결과, 사용자가 제안한 데이터 파이프라인의 기본 구상은 최신 분산 엔터프라이즈 IIoT
아키텍처의 핵심 원칙을 정확히 관통하고 있다3. 시스템의 안정적인 상용화를 위한 핵심
의사결정 권고사항은 다음과 같이 집약된다.
 1.​ IoT 미들웨어의 존치: 센서 네트워크와 Kafka 사이에 EdgeX Foundry나 고성능
     브로커(EMQX)를 반드시 유지하여 프로토콜 정규화와 에지 Store-and-Forward 유실 방지
     체계를 수립해야 한다4.
 2.​ Esper의 현대적 대체: 레거시 단일 JVM 엔진인 Esper/EQL 대신, Kafka와 완벽히 결합하여
     수평 확장과 무손실 상태 복구를 보장하는 Apache Flink(Flink CEP)를 스트림 처리의 핵심
     코어로 채택해야 한다5.
 3.​ 선택적 결측치 보간: 단순 시각화용 데이터는 무결성을 위해 결측 상태를 그대로
     보존하되, 실시간 머신러닝 모델이 개입하는 분석 경로에 한하여 Flink 스트림 내부에서
     선형 또는 회귀 보간을 선행시켜야 한다19.
 4.​ 인라인 머신러닝 추론 서빙: 딥러닝 이상 탐지 모델(Autoencoder)은 Python 환경에서
     사전 학습 후 ONNX로 직렬화하여, Flink 내부에서 임베디드 라이브러리(ONNX Runtime)
     형태로 초저지연 구동해야 한다48.
 5.​ 저장소 및 SCADA 인터페이스의 이원화: 시계열 센서 데이터 히스토리안은 InfluxDB에
     위임하고 Prometheus는 순수 파이프라인 인프라 모니터링으로 격리해야 하며, 시각화
     역시 장기 트렌드 분석의 Grafana와 양방향 공정 제어 및 P&ID 계장을 지원하는 FUXA 웹
    SCADA로 역할을 엄격히 분담해야 한다18.
