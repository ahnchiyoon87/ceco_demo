## ADR-001 · EMQX Kafka Sink 대신 Telegraf 브리지

**맥락**
PDF p.10 은 EMQX 의 데이터 통합 브리지로 Kafka 에 적재하는 구조를 전제한다.
실사 결과 이 기능은 EMQX Enterprise 전용이며 OSS 5.x 에는 Kafka 프로듀서
커넥터 자체가 없다.

**결정**
Telegraf 를 MQTT→Kafka 브리지로 배치한다 (`mqtt_consumer` in → `kafka` out).

**근거**
- TOML 설정만으로 동작 → "설정만으로 동작" 목표 부합
- Apache 2.0, 공식 도커 이미지, arm64 지원
- PDF 가 Tier 4 에서 이미 Telegraf 를 언급 → 새 기술 도입이 아님
- `json_transformation`(JSONata)으로 출력 스키마를 정확히 제어 가능

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| EMQX Enterprise | 상용 라이선스. "오픈소스 예제" 목표와 정면 충돌 |
| Kafka Connect + MQTT 소스 커넥터 | Confluent 판은 독점 라이선스. 대안 커넥터는 설정 복잡도가 Telegraf 보다 높음 |
| 자체 브리지 코드 작성 | 코드가 늘어 "설정만으로" 목표 위반. 유지보수 부담 |

**결과**
동작 확인. 스키마 정확도 100%, 처리량 12건/초에서 지연 관측되지 않음.
단, 컴포넌트가 하나 늘었고 Telegraf 의 `json_v2` 파서에 함정이 있었다
([사례 7-2](07-troubleshooting.md)).

**토론거리**
대규모(수십만 TPS) 환경에서도 Telegraf 가 적절한가? Kafka Connect 의
분산 워커 모델과 비교하면 어떤가?

## ADR-002 · PyFlink 대신 Java Flink Job

**맥락**
PDF p.10 은 "Flink 태스크 매니저 프로세스 내부에 C++ 기반 ONNX Runtime 엔진을
임베디드 형태로 직접 로드" 를 권고한다. 구현 환경은 Apple Silicon(linux/arm64).

**결정**
Java Flink Job + `com.microsoft.onnxruntime` (JNI → 네이티브 C++).

**근거**
- PyPI 의 `apache-flink` 에 **linux-aarch64 휠이 없음** (macosx_arm64 / manylinux_x86_64 만 존재)
- onnxruntime Java JAR 은 `linux-aarch64` / `linux-x64` 네이티브를 모두 번들 (확인 완료)
- JNI 는 C++ 네이티브를 감싸므로 PDF 원문 의도에 오히려 더 정확히 부합
- Maven 빌드를 Dockerfile builder stage 에 넣으면 사용자는 여전히 `docker compose up` 한 번

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| PyFlink | arm64 휠 부재. 소스 빌드는 비현실적 |
| 별도 Python 추론 사이드카 (REST/gRPC) | PDF p.10 이 명시적으로 "RPC Callout 지양" 을 권고. 네트워크 홉 추가 |
| amd64 에뮬레이션(QEMU) | 성능 저하가 심하고 추론 지연 측정이 무의미해짐 |

**결과**
추론 지연 **0.13~0.18 ms** 측정. 외부 서버 호출 대비 압도적.
대신 Jackson 의존성 충돌([사례 5](07-troubleshooting.md))과
Maven 빌드 시간(최초 3분)이 비용으로 발생.

**토론거리**
Python 생태계(scikit-learn, PyTorch)의 편의를 포기하고 Java 로 가는 것이
항상 옳은가? 학습은 Python, 추론은 Java 로 나누는 이 구조의 유지보수 비용은?

## ADR-003 · EdgeX 를 기본 경로로, lite 를 우회 경로로

**맥락**
EdgeX Foundry 는 컨테이너 8~9개를 추가하고 부트스트랩이 복잡하다.
프로토콜 정규화·Southbound·Store-and-Forward 를 실증하지만 비용이 크다.

**결정**
EdgeX 경유를 기본(`make up`)으로 하되, 우회 경로(`make lite`)를 프로파일로 함께 제공.

**근거**
- PDF 결론 1 이 IoT 미들웨어 존치를 명시적으로 권고
- Store-and-Forward 시나리오는 EdgeX 없이는 실증 불가
- 두 경로가 **Kafka 진입 스키마를 동일하게** 맞추면 하위 계층은 무영향
- EdgeX 가 막혀도 데모는 항상 동작 → 교육 현장의 리스크 완화

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| EdgeX 만 | 부트스트랩 실패 시 전체 데모 불가 |
| lite 만 | 프로토콜 정규화·Store-and-Forward 미실증. PDF 결론 1 미반영 |
| ThingsBoard 로 대체 | EdgeX(디바이스 관리) + FUXA(HMI) 와 역할 100% 중복 |

**결과**
`make up` 29개 컨테이너, `make lite` 19개.
정규화는 Telegraf 브리지에서 수행하므로 두 경로의 Kafka 스키마가 동일함을 확인.

## ADR-004 · 원본 토픽과 정제 토픽의 분리

**맥락**
PDF p.5 는 "원천 데이터 레벨에서 인위적으로 계산된 가공치를 덮어쓰면
감사 추적의 신뢰성을 훼손" 한다고 경고한다.

**결정**
`sensor.telemetry.raw`(무손실 원본)와 `sensor.telemetry.clean`(보간 완료)를
분리하고, 보간값에는 `quality` 태그를 붙인다. 두 토픽 모두 InfluxDB 에 적재.

**근거**
- 무결성 원칙을 **토폴로지로 강제** — 규약 문서가 아니라 구조로 보장
- `quality` 가 InfluxDB 태그로 남아 사후 조사에서 실측/추정 구분 가능
- 저장 비용은 2배지만 시계열 압축으로 실질 부담이 작음

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 단일 토픽에 덮어쓰기 | PDF 경고 정면 위반. 감사 추적 불가 |
| 보간을 TSDB 쿼리 시점에만 | ML 경로의 실시간 요건(수십 ms) 충족 불가 |
| 별도 필드로 원본 병기 | 스키마 복잡도 증가, 보간 없는 구간에서 낭비 |

**결과**
InfluxDB 실측: `GOOD` 15,858건 / `INTERPOLATED_LINEAR` 42건.
감사 추적이 히스토리안까지 성립함을 확인.

## ADR-005 · 보간 방식을 목적별로 다르게

**맥락**
PDF p.5 표는 LOCF 와 선형 보간의 트레이드오프를 제시한다
(LOCF: 지연 0 / 추세 단절, 선형: 물리적 타당 / 지연 발생).

**결정**
- 기록용(`clean` 토픽) → **선형 보간** (정확성 우선)
- 추론용(ONNX 텐서 조립) → **LOCF** (지연 0 우선)

**근거**
딥러닝 입력은 고정 차원의 완전한 행렬이어야 하며, 공백이 닫히기를 기다리면
실시간 이상 탐지의 지연 요건을 충족할 수 없다. 반면 히스토리안에 남는 값은
물리적으로 타당해야 사후 분석에 쓸 수 있다.

**기각한 대안**
전 구간에 단일 정책 적용 → 둘 중 하나가 반드시 망가진다.

**결과**
`interpolation.mode` 설정으로 노출(`linear`/`locf`).
`max-gap-ms` 초과 시 선형을 포기하고 LOCF 로 대체해 장시간 단절 시 폭주 방지.

## ADR-006 · Z-Score 에 지속성 요건 추가

**맥락**
1차 구현(`z > 3.0`)에서 정상 운전 중 오탐이 2분간 8건 발생.
autopilot 램프 구간에서 이동평균이 뒤처지는 구조적 문제.

**결정**
임계치를 3.5 로 올리고, "최근 5샘플 중 3회 이상 위반" 지속성 요건 추가.

**근거**
- 램프에 의한 순간 위반과 실제 이상을 구분하는 산업 현장의 표준 대응
- 추세 제거(detrending)보다 SQL 로 표현하기 단순
- 지연은 최대 5샘플(5초)로 허용 범위

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 임계치만 상향(z>4, 5) | 실제 이상의 민감도까지 함께 떨어짐 |
| 추세 제거 후 잔차에 Z-Score | SQL 복잡도 급증. 교육 자료로 부적합 |
| 윈도우 확대(60→300) | 램프가 길면 동일 문제 반복. 반응 지연 증가 |

**결과**
정상 운전 **90초간 오탐 0건**. `noise` 시나리오 탐지는 유지.

## ADR-007 · 학습 데이터에 운전 변동 주입 (autopilot)

**맥락**
설정치 고정 상태의 정상 데이터로 학습하니 태그 간 상관이 ≈0 이었고,
오토인코더가 단일 태그 Z-Score 와 구별되지 않았다.

**결정**
시뮬레이터에 autopilot(4분 주기 설정치 변동)을 추가하고, 이를 학습 데이터에 반영.

**근거**
- 오토인코더의 가치는 **다변량 상관 구조** 학습에 있음
- 실제 플랜트도 생산 스케줄에 따라 설정치가 변함 → 물리적으로 타당
- 변동 결과 corr(FT-101,IT-101)=+0.99, corr(pH-101,CT-101)=−0.93 등 형성

**위험과 완화**
변동을 너무 크게 주면 고장 신호가 정상 변동에 묻힌다. 실제로 1차 시도에서
정상 오탐 49% 가 나왔다(별도 원인도 있었음). 이를 막기 위해
**학습 직후 판별력 자가검증을 파이프라인에 포함**시켰다.

**결과**
정상 오탐 0.5%, drift 탐지 100%.

**토론거리**
운전 변동 폭을 어떻게 정해야 하는가? 실제 이력 데이터가 있다면
그 분포를 그대로 쓰면 되는가?

## ADR-008 · 검증을 텍스트가 아닌 상태로

**맥락**
잡 제출 스크립트가 "성공" 을 보고했으나 실제 잡은 0개였다
(ANSI 색상코드로 grep 실패).

**결정**
모든 자동화의 성공 판정을 **부작용 확인**으로 전환.
- Flink: `/jobs/overview` 의 RUNNING 개수
- 모델: 학습 후 판별력 자가검증
- 파이프라인: Kafka 오프셋 증가, InfluxDB 쿼리 결과

**근거**
로그 텍스트는 포맷·색상·로케일에 따라 깨진다. 상태는 깨지지 않는다.

**결과**
이후 잡 제출 실패(SQL 오류, Connection refused, JVM 모듈 옵션 누락)를
전부 즉시 포착. 조용한 실패가 사라짐.

## ADR-009 · plant.yaml 을 단일 출처로

**맥락**
태그 정의가 시뮬레이터·EdgeX 프로파일·FUXA 화면·Flink 규격 CSV 네 곳에 필요하다.

**결정**
`simulator/plant.yaml` 을 단일 출처로 삼고 나머지를 생성.

```
plant.yaml ─┬─ edgex/gen_profile.py  → EdgeX 프로파일 + 디바이스 정의
            ├─ fuxa/build_project.py → P&ID 화면 + 태그 바인딩
            ├─ (스크립트)            → flink/sql/tag_limits.csv
            └─ ml/Dockerfile         → 학습기가 물리모델을 직접 참조
```

**근거**
네 곳을 손으로 맞추면 반드시 어긋난다. 특히 주소 체계가 다르면
(Modbus 0-based vs FUXA 1-based) 조용히 틀린 값을 읽게 된다.

**결과**
`make regen-edgex`, `make regen-fuxa` 로 재생성.
ML 학습기는 빌드 컨텍스트를 프로젝트 루트로 올려 `simulator/plant.py` 를
복사본이 아니라 원본에서 가져온다(학습/운영 분포 불일치 방지).

## ADR-010 · Flink 재시작 전략 활성화

**맥락**
TaskManager 하트비트 타임아웃으로 ONNX 잡이 죽고 **복구되지 않았다.**
Flink 기본값은 `NoRestartBackoffTimeStrategy`.

**결정**
지수 백오프 재시작 전략 활성화 + TaskManager 메모리 상향(3072→4608m) +
하트비트 타임아웃 완화(50s→120s).

**근거**
체크포인트가 있어도 **재시작 전략이 없으면 복구가 일어나지 않는다.**
PDF p.6 의 "정확히 한 번 상태 복구" 는 두 가지가 모두 있어야 성립한다.

**결과**
잡 4개 안정 가동 확인.

**토론거리**
운영 환경에서 무한 재시작이 항상 옳은가? 재시작 폭주를 막는 방법은?
