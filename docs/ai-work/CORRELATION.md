# 알람과 대응 사건의 구분

원본 SCADA 알람을 변경하지 않는다. Kafka topic/partition/offset과 원문 bytes는 manufacturing_inbox에 보존하고, 각 고유 알람은 manufacturing_alarm_links 및 manufacturing_events로 사건에 연결한다. 동일 원문 재수신은 새로운 사건/이력을 만들지 않는다.

## 초기 명시 정책 v1

- site=AR-100, device=reactor-line-01, tag=IT-102 또는 VT-101이며 CEP_BEARING/THRESHOLD_USL/ZSCORE인 경우 `mixer-current-vibration-v1` 묶음 후보.
- 그 외는 site/device/tag/alert_type이 모두 같은 경우에만 묶음 후보. MULTIVARIATE ML 알람을 교반기 고장으로 추정해 합치지 않는다.
- 같은 묶음 후보의 이벤트 시간 간격이 30초 이내이면 열린 사건에 연결. 지연 도착도 사건 시간 구간과 비교한다. 종료/반려 사건에는 새 알람을 붙이지 않는다.
- 30초는 교육용 quiet-gap 설정이며 제조사 한계·물리 원인·최적 운영값이라고 주장하지 않는다. 추가 데이터 검증을 통해 조정할 수 있다.
- 알람별 원문을 보존하며 새 관측마다 revision을 올린다. review_revision은 별도로 관리한다. 처음 등장한 tag/alert_type/detector/severity 조합, 더 이른 사건 시작 시각, 승인·반려·결과 상태 변화는 검토 버전을 바꾼다. 같은 경보 조합의 반복 수치는 수신 기록/관측 번호만 증가시킨다. 현재 관측 품질·문서·대상·명령·인터록 검사는 별도로 유지한다.
- 초기 버전에서 생성된 단일 알람 사건은 소급 병합하지 않는다. 기존 기록을 보존하고 신규 수신부터 적용한다.
- 이는 증상 기반 업무 정리이지 원인 확정이 아니다. 작업 완료/고장 해소는 quiet-gap만으로 자동 결정하지 않는다.

## 확인한 범위

실제 PostgreSQL 통합 검증: 동일 알람 8건 동시 수신의 단일 생성, 전류→진동의 교차 유형 묶음, 지연 도착, ML 별도 사건, 60초 간격의 별도 사건, 다른 device 분리, 원문 이벤트 보존. 테스트의 입력은 검증용 가상 이벤트다. 실제 SCADA 고장 주입 후 상관 결과는 별도 실행 증거로 기록한다.

## 연속 알람 실제 루나 실패 재현 — 다음 우선 작업

실제 bearing_wear 70초 주입, 사건 1c1f0b3e-c8e7-48c5-9a00-e62d44a5a34c. 첫 분석 6d218385-1a5a-47d0-941d-6338597f081f는 사건 revision 변경으로 실패했다. 이후 경보 종류가 안정된 상태에서 d9db2f5d-b563-4f73-b0d4-5b98ecb2302b를 실행했으며 동일 경보 서명(tag/type/detector/severity)인데 revision 125→155로 변경되어 다시 실패했다. live-continuous-alarm-*.json 및 live-stable-alarm-*.json에 원문/모델 실행/전후 서명을 보존했다. 현 코드는 새 관측마다 revision을 증가시키고 분석/승인에서 완전 일치를 요구하므로 진행 중 이상 대응에 사용성 결함이 있다.

수정은 아직 하지 않았다. 다음 설계는 원본 이벤트/관측 revision을 보존하면서 검토 기준 변화를 별도로 판정해야 한다. 단순히 revision 검사를 삭제하거나 현재 측정 품질·문서 변경·대상·인터록 검사를 약화하면 안 된다. 새로운 태그/경보 종류/심각도, 관측 구간 확장/지연 도착, 정상 복귀·재발, 명령/인터록 변화와 반복 관측을 구분하고 실제 루나 정상·변경 거절 경로를 함께 검증해야 한다. 현재 정지 제어는 정상 autopilot 설정치 변화에도 전체 지문이 바뀌는 별도 문제가 남아 있다.

고장 주입 해제 완료, 교반기 운전 true 확인(live-continuous-alarm-cleanup.json). 정지·승인을 실행하지 않았다. 이전 점검 요청 성공을 실제 정지 완주로 확대하지 않는다.
