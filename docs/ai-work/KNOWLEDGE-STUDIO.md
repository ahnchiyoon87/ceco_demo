# 지식 스튜디오의 실제 작업 흐름

## 준비와 실행

원본 Ontology Studio의 업로드/작업 공간 API를 재사용한다. 실제로 plant.yaml과 교육용 문서 3종을 `/workspace/uploads`에 등록했다. 선택한 네 파일의 `/api/knowledge/prepare` 응답은 33개 노드, 29개 관계, 미확인 사항 6개였다.

이 추출은 결정적 파싱이다. YAML의 명시된 센서·제어점·주소·단위와 문서 ID/버전/본문/절을 구조화한다. 센서 이름을 보고 설비 소속을 추정하거나 문서가 승인되었다고 간주하지 않는다. 원본 SHA-256과 파일/절 위치를 보존한다.

## 검토자가 설계하는 내용

설비 추가로 Asset을 만들고 HAS_SENSOR, INSTALLED_IN, HAS_PROCEDURE, GOVERNED_BY, DESCRIBED_BY 관계를 연결한다. 기존 완료된 AR-100 후보 JSON도 불러올 수 있다. 이 관계가 사건의 센서 태그에서 자산과 적용 문서를 찾는 경로가 된다.

노드 속성·원문·관계를 읽고 미확인 사항과 검토 의견을 남긴다. 후보 변경마다 서버가 다시 검증하고 해시를 계산한다. 검토 확인과 의견을 입력해야 게시 버튼이 활성화된다. 서버는 검토 해시가 다르면 거절한다.

게시 API는 한 Neo4j 트랜잭션으로 원문과 관계를 저장하고 검토 내용 전체를 게시 이력에 보존한다. 동일 내용의 재전송은 중복 적재하지 않는다. 동일 ID의 속성은 갱신하고 관계는 병합한다. 후보에서 빠진 기존 노드/관계를 삭제하는 전체 교체 방식은 아니다.

수동 설비 추가 시 상위 Device를 사용자가 직접 선택한다. 첫 Device로 자동 연결하지 않는다. 동일 설비 ID/관계의 중복 추가를 화면에서 안내하며 서버 검증도 유지한다. 수동 관계의 연결 사유를 속성으로 보존하고, 관계 후보 상세에서 AI/수동 생성 방식과 원본 인용·출처 속성을 확인할 수 있다. 출처 속성이 없는 관계는 그 상태를 표시한다. 게시의 병합 의미도 검토 단계에 표시한다. 이 UI 수정의 빌드는 통과했으나 실제 브라우저 조작 검수는 아직 남았다.

게시된 관계의 클래스 구조는 `/api/knowledge/structure`에서 실제 DB를 집계한다. 이는 외부 제조 표준이나 LLM 추론 결과가 아니다. 그래프 탐색 화면은 원본 Cytoscape 컴포넌트를 재사용한다.

인접 탐색은 APOC 실패 후 한 단계로 축소하던 원본 fallback을 제거하고 일반 Cypher로 양방향 1~3단계를 조회한다. 500개 경로 한도를 넘으면 `truncated`로 알리며 실패는 503으로 반환하고 UI에 표시한다. 실제 게시 그래프의 독립 BFS 계산과 조회 결과를 대조해 1/2/3단계에서 각각 7/27/35개 노드가 일치했다(`live-neighbor-verification.json`). 없는 노드의 정상 빈 결과도 확인했다. API 경계 관련 테스트는 추가 검사 포함 24개 통과. 브라우저에서 오류·확장 결과를 직접 확인하는 검수는 남아 있다.

## 검증과 남은 작업

- prepare 테스트 5개: 명시 구조/원문/버전/해시 보존, 미지원 입력, 잘못된 YAML, 중복 문서 ID, 경로 이탈 거절.
- Neo4j review 테스트 4개: 원문 보존과 재전송, 오래된 검토 해시, 잘못된 관계 끝점, 내부 라벨 주입 차단, 트랜잭션 실패 롤백.
- 실제 등록 파일 네 개의 API 추출 응답을 확인했다. UI 빌드도 통과했다.
- 실제 브라우저에서 파일 선택·관계 편집·게시·그래프 탐색을 조작하는 검증과 캡처는 아직 남았다.
- 원본 Studio의 세 가지 소스 패턴과 모델 클라이언트를 재사용한 의미 후보 생성 경로를 구현했다. 선택 원본 스냅샷·구조를 모두 조회한 뒤 추가 노드/관계와 인용·이유를 제안하고, 원문에 없는 인용을 거절한다. PostgreSQL에 실행·실패·후보를 보존하며 직접 게시하지 않는다. UI에서 질문 입력→생성 실행→후보 검토로 연결한다. 실제 모델 연결은 없어 의미 추론 품질은 미검증이다. 현재 지원 범위를 자동 범용 PDF/레거시 분석으로 표현하지 않는다.

후속 검증: meaning_build 6개와 review 5개, 총 11개 통과. 원문 일치/미선택 출처/중복 ID/없는 끝점 검사와 실패 추적, 실제 Neo4j 원자적 게시 및 구버전 덮어쓰기 거절을 포함한다. 실제 모델 추론을 대체한 성공 주장에는 사용하지 않는다.

설정 추출 로직 정본은 `ai-layer/knowledge/backend/src/modules/ontology/inventory.py`다. 기존 `ai-layer/export_inventory.py`는 같은 구현을 호출하는 CLI 래퍼다.

## 2026-09-21 그래프 후보 식별자 검토 후속

사용자는 전시용 UI와 관계 그래프의 시각적 완성도를 최우선으로 강조했다. Ontology Studio의 탐색 기능을 활용하되 실제 설비·센서·문서·절차 연결, 출처 탐색, 종류별 구분과 선택 강조를 구현·시각 검수해야 한다. 노드 수를 인위적으로 늘리는 것은 요구가 아니다. 현재 브라우저 재확인도 apps/browsers 빈 목록이어서 화면 검수는 미완료다.

실제 루나 후보의 M-101 ID는 AR-100/M-101, 기존 게시는 AR-100/reactor-line-01/asset/M-101로 중복 가능성을 확인했다. review.py에 명시된 site/device/name과 상위 Device만 사용하는 reconcile-assets API를 추가했고 UI에서 식별자 정리→변경 확인→재검토가 가능하다. 이전 ID·원문 인용을 보존하고 관계 끝점도 함께 변경한다. 미확인 소속은 추정하지 않는다. 게시 시 자연 식별자(site/device/name) 중복을 원자적으로 차단한다. 실제 Neo4j 동시 게시 시험에서 초기 제약 생성 데드락을 발견했고 해당 멱등 DDL을 관리 트랜잭션으로 옮겼다. 관련 14개 테스트 통과(1.37초).

아직 실제 모델 후보의 정리 결과 검토·게시·조회 증거는 남겨야 한다. 원본 후보는 live-luna-build-result.json에 보존돼 있다. 최신 소스 이미지 재빌드 후 API를 이용해 이어간다. 이 변경의 테스트 통과를 화면 품질 검수나 전체 완료로 확대하지 않는다.

실제 모델 후보 게시 완료: live-luna-reviewed-publish-result.json, 해시 939242462fafa0b51e62c06850f931930a5f4628add8c056fe729bc8443a8e8f. M-101 식별자 정리 후 데이터 장치 소속을 EXPOSES_ASSET으로 검토 수정했다. 원본 후보·수정 내역을 보존했다. live-luna-published-retrieval.json에서 전체 35노드 유지, M-101 하나, 문서 3종 및 정책 v2 조회를 확인했다. UI 조작·시각 검수는 별도 미완료다.


## 정책·대응 절차 버전 갱신

정책 v3와 대응 절차 v2를 등록 원본→구조 추출→적용 관계 검토→게시 순서로 갱신했다. 게시 해시 `a875341a46e01bf07f2ea7a10d9263416d9a75c05e0a97ca305beebd30e30c4d`, 11노드/10관계 갱신, 전체 35노드 유지. 기존 M-101 적용 인용문이 새 문서에도 존재함을 확인했으며 관계의 이전 문서 버전·해시를 보존했다. 사건 근거 조회에서도 정책 3·절차 2를 확인했다. 근거: `live-policy-v3-verification.json`, `live-policy-v3-reviewed-candidate.json`, `live-policy-v3-retrieval.json`. 새 문서를 사용하는 실제 모델 정지 완주는 별도 재검증이 필요하다.
