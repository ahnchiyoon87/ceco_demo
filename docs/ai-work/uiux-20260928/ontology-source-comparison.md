# Ontology Studio 원본과 제조용 구현 — 소스 대조 (2026-09-28)

원본 범위: `_references/manufacturing-ai/ontology-studio`에 보관된 소스. 최신 upstream 전체와 동일하다는 주장은 하지 않는다. 원본을 실행해 품질을 비교한 결과가 아니라 현재 두 소스의 기능 연결을 대조한 기록이다.

| 기능 | 보관된 원본 | 현재 제조용 구현 | 판단 |
|---|---|---|---|
| 화면 구조 | AppShell의 구축/질문 응답 대화 세션, 파일 패널, 오른쪽 그래프/정보 패널 | App의 공정/이상 대응/지식 메뉴, 지식 안의 자료·검토/그래프/연결현황 | 전체 복제 아님. 제조 업무에 맞게 재구성 |
| 그래프 탐색 | OntologyGraphPanel의 Cytoscape, 종류 필터, 배치, 이웃 탐색 | 같은 컴포넌트 기반, 제조 단계 배치·선택 관계 목록·근거 보기 보강 | 재사용 후 수정. NVL로 전환하지 않음 |
| 스키마/직접 편집 | 스키마 편집과 클래스·관계 저장/삭제 이벤트 연결 | 게시된 그래프는 read-only; KnowledgeReview에서 후보를 편집·검토·게시 | 공개 그래프의 즉시 수정을 노출하지 않는 의도된 차이 |
| 파일과 원본 | FilePanel 및 업로드/작업 공간 | 원본 API 재사용, prepare.py/inventory.py에서 명시된 YAML·Markdown/TXT 구조 추출 | 범용 PDF 자동 분석 기능으로 설명하면 안 됨 |
| AI 관계 제안 | 구축 질문/의도/대상 스키마 입력과 Agent 대화 | build.py가 원본의 세 가지 패턴과 모델 클라이언트를 재사용. 선택 원본 스냅샷과 추출 구조 조회 후 후보 반환 | 자동 후보 생성 존재. 직접 게시와 분리 |
| 근거 검증 | 원본의 구축 프롬프트/도구 흐름 | merge_meaning이 선택 원문과 인용의 정확한 일치를 확인. 출처 파일·해시·인용·사유 보존 | 관계 수를 늘리는 것보다 원문 근거와 검토가 우선 |
| 사람 검토/게시 | 대화·그래프 편집 중심 | 후보 검토 해시, 검토 의견·확인, 원자적 게시·재전송 중복 방지·게시 이력 | 제조용으로 별도 강화 |
| 질문 응답 | 독립 answer 모드와 대화 세션 목록 | 독립 범용 Q&A 화면 없음. 사건 Agent가 설비/문서/센서 근거 조회 | 동일 기능으로 주장하지 않음 |
| 처리 상태 | 대화 스트림과 TODO 패널 | 관계 생성은 저장 실행/도구 기록 조회, 사건 Agent는 SSE 실행 스트림 | 지식 생성과 사건 처리가 같은 스트리밍 구현은 아님 |

## 직접 대조한 위치
- 원본 `frontend/src/host/AppShell.vue`: 구축·질문응답·파일·스키마·그래프 연결.
- 현재 `ai-web/src/App.vue`, `features/ontology/KnowledgeReview.vue`, `OntologyGraphPanel.vue`, `GraphEvidence.vue`.
- 현재 `ai-layer/knowledge/backend/src/host/app.py`: 실제 등록한 라우터.
- 현재 `modules/ontology/build.py`: 원본 패턴 재사용, 선택원본 도구, 후보 병합/인용 검증.

## 현재 검증 범위
실제 원본4개로 생성·검토·게시한 기록과 37노드/47관계 조회는 `uiux-20260928`의 기존 실행 증거를 참조한다. 이 대조 작업에서 모델 생성·게시를 재실행하지 않았다. 최근 브라우저에서는 메뉴 이동 중 질문 보존, 구조/실체 선택, 연결 관계 표시와 390/1600px 가로 넘침을 확인했다.

미완: 후보 편집의 모든 오류·키보드·장문 경로, 지식 생성 진행 화면의 전체 실시간성, 원본 질문응답 기능을 추가할 필요의 범위 판단. 기존 저장된 관계의 출처가 존재한다는 사실만으로 의미 정확성 전체를 인증하지 않는다.
