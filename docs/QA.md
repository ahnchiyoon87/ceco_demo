**Q. 이 작업의 기준이 뭔가?**
2026년 제조 현업에서 주로 쓰는 구조와 스택이다. 학생이 배운 구조가 현장에서 그대로 통해야 한다. 우선순위는 ① 현업 주류 ② 비용 0·라이선스·도커 적합성·제품 계열 유지 ③ 경량화다.

**Q. 경량화가 최우선 아닌가?**
아니다. 경량화는 세 번째다. 경량화는 현업 수준(구조·기능·주류 제품)을 그대로 두고 효율적으로 가볍게 하는 것이다. 방법은 같은 제품 안 가벼운 판, 설정을 실제 사용량에 맞추기, 선택 기능은 프로필로, 같은 역할의 중복 합치기다. 층을 빼거나 비주류 제품으로 바꾸지 않는다. 성능·안정성이 원본(V1)보다 나빠지면 그 경량화는 쓰지 않는다.

**Q. 누가 쓰나? 시험은 얼마나 하나?**
경남대 제조 AI 과정 학생의 개인 실습용이다. 학생마다 같은 패키지를 자기 PC 한 대(Docker 메모리 약 7.6 GB)에서 띄운다. 각자 똑같이 받아 잘 돌아가면 된다. 과부하·장시간 시험은 하지 않는다.

**Q. "현업에서 주로 쓴다"는 채택률 같은 수치가 있어야 하나?**
아니다. "주로 이걸 쓴다"를 알면 된다. 채택률은 대부분 유료 시장 보고서에만 있어 알기 어렵다. 구조와 트렌드는 표준 문서·독립 분석·설문으로 확인했다.

**Q. 현업 2026 트렌드는 조사됐나?**
됐다. UNS(MQTT 허브)와 Kafka·NATS 결합, DataOps(설비 모델·맥락화)가 산업 연결성 1위 추세, 에이전트형 AI 시연 시작(IoT Analytics 2026-01), AI는 OT 밖에서 읽고 추천만(CISA 등 9개 기관 2025-12), 외부 쓰기 요청은 검증 통로를 거치고 받을지는 공장 안에서 정한다(NAMUR NE 178 공개 요약: 요청 검증 절차·요청자와 공장 소유자의 분리, OPC UA ISA-95 Job Control: 받는 쪽이 받을지·언제 할지 정하고 거부 가능), SCADA 표준 ISA-112 발행(2026-02), 제조사 절반가량이 데이터·아키텍처 표준화(Deloitte 2025). 없는 것은 이름 있는 공장의 내부 구성과 채택 통계다(공개 자료 없음).

**Q. 이 시스템을 피지컬 AI에도 쓰나?**
쓴다. 피지컬 AI는 AI가 현실의 설비·로봇을 보고 판단해 움직이게 하는 것이다. 베이스 작업에서 이를 위해 따로 조사하거나 더하지 않는다. 확정 구조의 작업 요청 경로(사람 승인 → DMZ 게이트웨이 → OT 수신기 → PLC의 물리적 가능 여부 검사)와 설비 등록부가 이 확장의 받침이다.

**Q. 내가(사용자) 골라야 하는 게 있나?**
없다. 사용자는 전문가가 아니므로 에이전트가 근거로 정하고 이유를 쉬운 말로 설명한다. 사용자가 바꾸라고 하면 바꾼다. 구조·스택은 조사와 대화로 이미 확정됐으므로 다시 확인받지 않는다.

## 2. 구조

**Q. OT가 뭔가?**
OT(운영 기술)는 공장에서 기계를 실제로 움직이는 쪽(센서·PLC·SCADA 화면)이다. 멈추면 기계가 서므로 안전과 계속 도는 것이 먼저다. IT(정보 기술)는 사무실 쪽(저장·분석·AI·업무)이고, DMZ는 둘 사이 완충지대다. 데이터는 OT가 밀어서 내보내고, IT에서 기계로 바로 가는 명령 길은 없으며, IT가 멈춰도 공장은 돈다. 우리 그림에서 L1~L4가 OT, L5가 DMZ, L6~L10이 IT다(`REPORT_base_plan_근거상세.html` 6장).

**Q. IoT-SCADA 층은 어디까지이고, 어디부터 우리가 맞춰 설계한 것인가?**
"IoT-SCADA"는 표준 층 이름이 아니다. 표준 층은 Purdue 모델(L0 장치, L1 PLC, L2 SCADA·HMI, L3 히스토리언, L3.5 DMZ, L4~5 기업망)이다. 우리 L1~L4(설비·PLC·엣지·허브·화면)와 L5 DMZ의 "OT가 밀어냄"은 표준 근거가 강하다. L6 Kafka부터 위는 IT 쪽 데이터·AI 영역으로, 제품·배치는 업계 동향과 우리 설계가 섞여 있다. 현업과 다른 곳은 이상 탐지(Flink)를 IT에 둔 것이다(CISA는 ML 탐지를 주로 L1~L3에 둔다고 씀). 이력은 현업 배치대로 OT 이력(FUXA DAQ) + DMZ 사본으로 바꿨고, IT가 만든 분석 결과는 IT에 둔다. 층별 표는 `REPORT_base_plan_근거상세.html` 3장·6장.

**Q. IoT-SCADA에서 밖으로 보낼 때 MQTT → Kafka 패턴을 써야 하나? 그냥 좋아서 고른 건가?**
써야 하는 것은 아니다. 공공 지침이 이름을 들어 권하는 기본형은 "OT 히스토리언 → DMZ 히스토리언 단방향 복제 → IT는 DMZ 조회"이고, MQTT·OPC UA를 TLS로 DMZ에서 중개하는 것도 허용한다(「Secure connectivity principles for OT」(NCSC-UK·CISA·FBI·BSI 등 여러 나라 기관 공동, 2026-01-14) p.19). MQTT 허브 뒤에 Kafka를 붙이는 방식은 독립 분석 기관 IoT Analytics(2026-01)가 현업 추세로 적은 것이고 사용 비율 통계는 없다. 그래서 지침의 기본형(OT 이력 + DMZ 사본)을 따르고, Kafka는 IT에서 DMZ 브로커를 구독해 받는 분석용 흐름으로 둔다. Kafka 위치를 정한 규칙은 없고(현업은 사이트·중앙·클라우드에 모두 둔다), 우리는 교육용으로 IT에만 둔다(HANDOFF §2-1 외부 시스템 연결 ②⑨, 17번 D20).

**Q. 외부 시스템이 FUXA 같은 공장 안 화면을 직접 보면 안 되나? 이건 법인가, 무조건인가?**
안 된다. 공공 지침이 권하고 있어 따른다(규칙: HANDOFF §3-0). NIST SP 800-82r3: 기업망과 OT망 사이에 트래픽이 직접 지나가지 않게 한다. CISA 2016: 기업이 접근하는 구성요소는 DMZ에 두고 모든 경로는 DMZ에서 끝난다. 「Secure connectivity principles for OT」(NCSC-UK·CISA·FBI·BSI 등 여러 나라 기관 공동, 2026-01-14): IT 시스템은 OT에 직접 접근하지 말고 DMZ의 사본(히스토리언)을 조회한다(p.19). 외부 시스템은 DMZ에 나온 데이터만 본다. 구체 구성은 HANDOFF §2-1 "외부 시스템 연결", 조사 16번.

**Q. 외부 연결 방식은 표준이 정한 것인가, 판단인가?**
적용되는 규칙이 정한 것은 따르고, 규칙이 정하지 않은 곳만 설계 판단이다. 규칙이 정한 것: 연결은 OT가 먼저 연다, DMZ로 중개하고 보안 프로토콜을 쓴다, 운영 데이터는 OT 히스토리언 → DMZ 히스토리언 단방향 복제 후 IT가 DMZ를 조회한다, 분석·업무 시스템은 명령하지 않는다(「Secure connectivity principles for OT」(NCSC-UK·CISA·FBI·BSI 등 여러 나라 기관 공동, 2026-01-14) p.11·p.19·p.25, 원문 확인). 규칙이 정하지 않은 것(IT 쪽에서 Kafka·Flink를 붙이는 방식, 요청을 전하는 방식·제품, 시간 값, 보존 기간 등)은 16·17번에서 현업 사례·제품 문서로 정하거나, 근거가 정말 없으면 이유를 붙인 추천으로 정했다. 어느 것이 근거이고 어느 것이 추천인지는 `REPORT_base_plan_근거상세.html` 8장과 아래 "조사 17번" 답.

**Q. 우리 시스템의 외부 시스템은 무엇인가? AI만 보고 조사해도 되나?**
우리 시스템의 외부 시스템은 **우리 AI**(AI 업무 도우미 + 담당자 승인 화면)다. 조사는 AI만이 아니라 현업의 외부 시스템 전반(MES·ERP·정비·기업 히스토리언·클라우드·AI)을 넓게 했고(16번), 그 모범을 우리 AI에 적용했다. 16번 §7~8의 "요청 출처 넓히기·업무 흉내 앱·Odoo"는 외부 시스템이 여럿이라는 전제의 제안이라 쓰지 않는다.

**Q. 에이전트가 조치하고 그 결과를 사용자에게 보여 주는 것은 되나?**
된다. 담당자가 보고 승인하며 책임도 담당자에게 있다(원본 V1과 같다). 달라지는 것은 조치가 설비로 가는 **길**뿐이다: V1은 조치 코드가 설비에 Modbus로 직접 썼고, 새 설계는 승인된 조치가 "작업 요청"이 되어 DMZ 게이트웨이 → 공장이 연 연결 → 공장 안 수신기(받을지 결정) → PLC(물리적으로 되는지 마지막 검사)로 가며, "받음·거절"과 "결과·새 상태"가 화면에 돌아온다. 근거: 2026 공동 지침 p.25 "분석·업무 시스템은 관찰·분석만 하고 명령하거나 운전을 바꾸지 않는다".

**Q. 표준(지침)에 그렇게 되어 있으면 지켜야 하나? 법이 아니면 안 지켜도 되나?**
적용되는 규칙(법령·표준·공공 지침)이 있으면 따른다. "법은 아니다", "권고일 뿐이다"로 빠져나가지 않는다. 먼저 그 규칙이 우리에게 적용되는지 보고, 관계없는 분야 규칙(예: 제약 전용 21 CFR Part 11)으로 새지 않는다. 적용 규칙이 없으면 현업이 흔히 하는 방식을 따른다(HANDOFF §3-0). 적용되는 법령은 산업안전보건기준에 관한 규칙 제92조·제224조(정비 때 정지·잠금)이고, 공장망–외부 연결 구조를 직접 정한 국내 법 조문은 일반 공장에는 찾지 못했다(16번 §6).

**Q. 외부로 보낼 때 사본을 반드시 떠야 하나?**
공공 지침이 권하므로 따른다: 운영 데이터를 나눌 때는 공장(OT) 기록을 DMZ 기록으로 단방향 복제하고, 외부는 공장이 아니라 DMZ 사본을 조회한다(2026 공동 지침 p.19, CISA 2016). 그래서 공장 안 기록은 FUXA 내장 기록, 외부용 사본은 DMZ의 InfluxDB(공장 원시값 사본 전용)로 둔다. IT가 만든 분석 결과는 DMZ 사본에 되쓰지 않고 IT에 둔다(17번 D15). 연결은 항상 공장이 먼저 연다(p.11).

**Q. 어디까지가 규칙(표준)이고 어디부터 우리 판단인가? 맨땅에 새 길을 여는 수준인가?**
큰 규칙은 모두 문서에 있다: 공장이 먼저 연결을 연다, 외부는 사본만 본다, 외부(AI)는 명령하지 않고 요청한다, 경계에서 검사한다, 끊겨도 공장은 돈다, 정비 때 멈추고 잠근다. 우리는 그 규칙에 들어갈 **재료**(Mosquitto 브리지, InfluxDB 사본, FUXA 기록, 엣지, 게이트웨이 코드 등)를 조사 추천대로 끼웠다. 전수 검사(161개 결정)에서 근거가 없거나 약한 판단 46개·과장 7개가 나와 조사 17번으로 근거를 찾고, 정말 없으면 추천과 그 이유로 정했다(`17_판단근거확인_결과.md`). 결과는 근거로 해소 56, 추천으로 해소 14, 미해소 0이다. 맨땅은 아니다: 길은 표준이 그렸고 부품은 기존 제품을 원래 용도로 쓴다. 처음인 것은 "이 전부를 PC 한 대에 묶은 조합"뿐이며 조립 때 실측으로 확인한다.

**Q. Odoo, 암호화(TLS), 일회용 비밀번호(TOTP)는 왜 들어갔다가 빠졌나?**
Odoo는 16번이 외부 시스템이 여럿이라는 전제로 낸 선택 제안이었고, TLS·TOTP는 에이전트가 지침의 모든 줄에 기계적으로 규칙을 적용해 넣은 것이다. 외부 시스템은 우리 AI이고, TLS·다중 인증은 16번도 "교육용 축소, 현업은 켠다고 설명"을 권했으므로 빼고 설명만 한다. 브로커 계정·ACL은 켠다.

**Q. 조사는 몇 건을 했나? 보고서는 어떻게 되어 있나?**
조사 다섯 건: 구조(12), 세부(13), 스택(14), 무료 대체품(15), 외부 시스템 연결(16). 여기에 설계 판단의 근거를 확인한 17번(판단 근거)을 더했다. 보고서는 세 파일이다: 화면 공유용 요약 `docs/REPORT_base_plan.html`(조사 → 현업 구조 그림 → 스택·경쟁 칸만 이유 → 아키텍처 그림 → 검증 → 남은 것), 읽으면서 설명할 대본 `docs/REPORT_base_plan_대본.md`(블록 순서와 같음, 끝에 요소 풀이), 근거 전부를 담은 `docs/REPORT_base_plan_근거상세.html`(근거 문서 19개, 판단 70개의 근거·추천 표, 조립 중 정한 것 등). 사용자용 쉬운 설명서는 `docs/쉬운설명_새_베이스_아키텍처.html`.

**Q. 조사 17번은 무엇을 했고 결과는? 근거로 해소된 것과 추천으로 대체된 것은?**
전수 검사(161개 결정)에서 근거가 없거나(46) 약하거나(17) 과장된(7) 판단 70개를 현업 사례·표준·규칙으로 다시 확인했다. **근거로 해소 56, 추천으로 해소 14, 미해소 0.** 근거는 규칙 원문·여러 독립 근거·공개 사례로 판단이 정해진 것이고, 추천은 근거가 정말 없어 원리·인접 분야·벤더 기본값에 이유를 붙여 권한 것이다. 추천 14개: E12 발송기→게이트웨이 HTTP(S) POST, E24 세 겹 검사 배분, E20 수신기를 엣지 전용 흐름으로, E18 만료 30/60 s, E38 ACK 5 s·재관측 10 s, E37 승인 두 종류, E13 PostgreSQL 정본·Kafka 사본, D13 IT가 DMZ 구독, D2 신호별 수집 값, D10 끊김 버퍼, H2 AI DB 합침, H3 보존 기간, A16 엣지 비교값, K4 설비 시각 기준 창. 근거와 추천이 섞인 것(구성은 근거, 구현은 추천): E11 Bento 게이트웨이, B8 라우터 컨테이너, H1 스키마 분리, G5 감시 방향. 전체 표는 `17_판단근거확인_결과.md` 21~98줄과 `REPORT_base_plan_근거상세.html` 8장, 반영 위치는 HANDOFF §2-1~§3-6(괄호의 "17번 E16" 등).

**Q. 17번으로 크게 바뀐 것은?**
① 망 방향을 문서가 아니라 라우터 컨테이너 규칙으로 강제한다(여러 망에 붙는 것은 라우터 하나뿐). ② Flink 결과는 DMZ 사본에 되쓰지 않고 IT에 둔다(DMZ InfluxDB는 공장 원시값 사본 전용). ③ 요청·승인·감사의 정본은 PostgreSQL 추가 전용 표, Kafka는 통로·사본, 보존 기간은 정책(21 CFR 11·"무기한"은 뺐다). ④ 분석 경고를 FUXA에 보이는 것은 선택(보일 때도 공장이 연 연결). ⑤ 감시는 공장 쪽 agent → DMZ → IT, 장치 상태는 엣지가 대신 알린다(시뮬레이터 MQTT Will 삭제). ⑥ 요청 필드는 Job Control 이름, 만료는 두 겹, 시간 값 30/60/5/10 s, 게이트웨이는 모드를 보지 않고 PLC는 "물리적으로 되는지 마지막 검사". ⑦ "SIS" → "기계 안전 기능", "정비 잠금" → "정비 모드(물리 잠금을 대신하지 않음)". ⑧ 사실 정정: OpenPLC는 ST를 REST로 못 넣는다(CLI·zip), EdgeX 내부 버스는 엣지 안에만, BaSyx Go 정식판이 있다. ⑨ "현업 1위", "ISO 14224 기준" 같은 과장 표현을 고쳤다.

**Q. 추천으로 정한 것은 믿어도 되나?**
추천마다 이유와 기댄 자료(벤더 기본값, 다른 분야 수치, 원리 문헌)를 적었고, 근거가 없다는 사실도 함께 적었다. 설정값(시간·수집 주기·보존)은 설정 파일 한 곳에서 바꿀 수 있게 둔다. 실행해야 알 수 있는 9개(라우터·mqttv50 만료·브리지 큐 한도·브리지 in 로컬 ACL·openplc-cli·Bento 게이트웨이·AI 층 PG18·Prometheus 셋 메모리·FUXA DAQ 보존)는 조립에서 먼저 재고, 안 되면 항목마다 HANDOFF 단계 4 ⑨에 적힌 조치로 간다. 조립 순서는 HANDOFF §0 4번.

**Q. 권한이나 효율도 조사하거나 확인받나?**
아니다. 권한(서비스마다 필요한 만큼만: 계정·ACL·최소 권한)과 효율(가볍게, 중복 없이)은 상식적인 기본값으로 적용한다(HANDOFF §3-0).

**Q. 현업은 어떤 구조로 되어 있나?**
망은 OT(공장)·DMZ(완충지대)·IT(분석) 세 구역이다. 층은 설비 → PLC(제어기: 인터록·운전 모드·물리적으로 되는지 마지막 검사) → SCADA 화면 → 엣지 연결(프로토콜 변환, 끊기면 저장 후 전송) → MQTT 허브(UNS) → 설비 모델 → 히스토리언 → DMZ 중계 → Kafka형 장부 → 탐지 → 플랫폼 감시 → AI(읽기 전용) → MES·ERP다. 설비가 늘어도 층은 그대로이고, 설비 이름 체계·토픽 규칙·설비 종류별 모델·엣지 노드로 흡수한다. 자세한 것은 HANDOFF §2-1, 조사 원문 `docs/research/현업조사_2026-09/12_조사1_현업구조.md`.

**Q. 참조 설계서 v3가 정답인가? 우리가 억지로 고치는 건가?**
v3는 다른 팀이 실제로 구축·실행한 구조이고, 우리 구조도와 함께 **비교 대상**이다. 판단은 현업 조사로 한다. v3는 망 분리·명령 게이트웨이·경보 분리가 현업과 맞고, OT 이력 저장·설비 모델 층·알람 수명주기가 없다. 원본(V1)의 뼈대도 현업과 대부분 같다. 억지로 고친 것은 경량화를 앞세워 층을 뺀 V2였고, V2는 쓰지 않는다.

**Q. 흐름(데이터·명령·알람) 길은 하나로 통일해야 하나, 여러 방향이 맞나?**
둘 다다. **같은 종류의 흐름은 길 하나**로 모은다(읽기 하나, 명령 하나, 알람 전달 하나). 방향이 여러 개인 것은 정상이다: 데이터는 올라가고, 명령은 내려가고, 알람은 화면과 분석 쪽으로 간다. 원본의 문제는 같은 흐름이 여러 길로 간 것이다(FUXA와 EdgeX가 같은 설비를 따로 읽음, 쓰기 길 3개).

**Q. 여러 단계를 타고 흐르는 게 필요한가? 알람이 되돌아 내려가는 건 결함 아닌가?**
망을 나누면 경유가 생기는 것이 현업 모양이다. 분석 경고(alert)를 IT에서 OT 화면으로 보이는 것은 "현업 패턴"이 아니라 선택이다(현업은 분석 경고를 주로 정비·신뢰성 담당과 IT 화면으로 보낸다, 17번 F9). 우리는 V1 기능 보존을 위해 켜되, 공장 허브 브리지가 읽기 전용 alert 토픽을 가져와 FUXA의 "분석 경고(참고)" 칸에 소리·조작 없이 보인다(공장이 연 연결). 없애는 것은 같은 데이터를 두 번 옮기는 길이다.

**Q. 층을 빼거나 두 개를 하나로 합칠 수 있나?**
현업 구조에 그 층이 없을 때만 뺀다. 같은 역할이 중복된 것만 합친다(예: 원본의 MQTT 브로커 2개(EMQX·EdgeX 전용) → 구역마다 하나(OT 허브 + DMZ 브로커, 역할이 다름. 엣지를 EdgeX로 정하면 EdgeX 내부 버스용 브로커가 엣지 안에 하나 더 있다), Telegraf 3개 → Bento 1종).

**Q. Kafka는 필수인가? MQTT로 바로 받으면 안 되나?**
Kafka형 장부는 현업 구조의 한 층이다. MQTT 허브는 "지금 상태"를 모으는 곳이고, 이력 보관·다시 읽기·여러 소비자는 Kafka가 맡는다. 현업은 둘을 이어 붙인다(MQTT → 커넥터 → Kafka). 그래서 둔다.

**Q. Redpanda는?**
Kafka와 호환되지만 라이선스가 BSL이라 관문에서 제외한다.

**Q. 설비는 몇 대인가?**
설비 7대(TK-101·P-101·R-101·M-101·HX-101·HX-102·CV-101), 센서 12개, Modbus 연결 1개다. "설비 1대"는 틀린 말이다. 현업 가정은 설비 다수·통신 혼재로 고정한다.

**Q. EdgeX(통역사 역할)는 필요 없나? V2에서 EdgeX·MQTT를 빼도 상관없나?**
상관있다. 엣지 연결 층은 현업 구조에 있는 층이고, 원본의 기능(장치 등록부·명령 API)과 수업 자료(`edgex/telemetry`)가 걸려 있다. 그래서 층을 뺀 V2는 쓰지 않는다. 엣지 칸에 어떤 제품을 쓸지는 아래 §3의 EdgeX·Node-RED 답을 따른다.

**Q. EdgeX와 Telegraf는 기능이 같고 Telegraf가 가벼운 것인가?**
아니다. EdgeX는 장치 등록부·명령 API·UI가 있고, Telegraf는 읽기 전용 수집기라 명령(쓰기) 길이 없다.

## 3. 스택

**Q. 현업은 어떤 스택을 쓰고, 우리는 무엇을 쓰나?** (HANDOFF §2-3 칸별 표)
현업에서 널리 쓰는 오픈소스 본체: Kafka, Flink, Grafana, Prometheus, Neo4j, PostgreSQL(제조 한정 순위 자료는 없어 "1위"라고 하지 않는다, 17번 J15). MQTT 브로커 Mosquitto는 현업에서 EMQX·HiveMQ와 함께 널리 쓰이는 제품이다(EMQX 5.9+는 BSL, HiveMQ는 쓰기 기능 유료라 무료 정식판인 Mosquitto). 현업 주류가 상용이라 무료로 대신: PLC(→ OpenPLC v4), 엣지(→ Node-RED 또는 EdgeX), 이력 저장(→ InfluxDB), 화면(→ FUXA), 설비 등록부·승인 흐름·알람 관리(→ 자체 + PostgreSQL). 보고서는 칸마다 "현업은 주로 무엇 → 우리는 무엇 → 왜"로 쓴다.

**Q. 현업에서 쓰는 건 다 유료인가?**
아니다. Kafka·Flink·Grafana·Prometheus·PostgreSQL·Mosquitto는 현업도 무료 오픈소스 본체를 쓴다. 상용이 주류인 칸은 PLC·화면·히스토리언·엣지 등 몇 개다.

**Q. 무료로 써도 된다는 근거가 있나?**
있다. 칸마다 라이선스 원문 근거가 있다(Apache-2.0, MIT, EPL, AGPL 등). 상용을 못 쓰는 근거도 있다: CODESYS는 라이선스 없이 2시간 데모(검색 요약), Ignition 무료판은 비상업·개인 교육용만(공식 원문), HiveMQ Edge는 설비 쓰기가 유료(공식 원문), ThingsBoard는 4.4부터 BUSL, EMQX는 5.9부터 BSL, TimescaleDB 압축·연속 집계는 TSL.

**Q. "무료 중 1위"는 근거가 있나?** (조사 원문 15번)
다운로드 수만이 아니라 논문 수(OpenAlex)·대학 수업·재단·개발자 수·소스 확인 기능으로 비교했다.
- PLC — OpenPLC v4: 공식 배포 이미지가 있는 유일한 후보(4diac는 공식 Dockerfile로 직접 빌드), IEC 61131-3 다섯 언어, 논문 138편, Western Carolina 대학 PLC 과목. 약점: 근거 대부분이 v3 계보, v4는 한 회사 개발, 공장 사례 없음.
- 화면 — FUXA: 무료로 MQTT·OPC UA·Modbus를 모두 갖춘 유일한 공정 HMI, 가장 활발히 개발 중. 약점: 재단·공장 사례 없음, 알람 보류(shelving) 없음. 2안 Rapid SCADA 6.
- 엣지 — 아래 EdgeX·Node-RED 답.
무료 제품끼리의 점유율 설문은 없다.

**Q. Kepware는 유료인가?**
유료다(PTC 상용 제품, 드라이버별 라이선스). 체험판 조건(시간 제한)은 공식 문서로 확인하지 않았다. 비용 0 관문에 걸리므로 설명용이다.

**Q. EdgeX와 Node-RED 중 무엇을 쓰나?**
**둘 다 해 보고 더 좋은 쪽을 고른다(사용자 결정 2026-09-30 "일단 둘다 해보고 더 좋은걸 고른다"). 우선안은 없다.** 문서만으로는 막상막하다.
- Node-RED: 블록을 이어 만드는 범용 도구. 산업 제어기 제조사 여러 곳이 탑재·지원한다(Siemens IOT2050·WAGO PFC200·Opto 22·Bosch Rexroth ctrlX), OpenJS 재단, 산업 논문 486편(EdgeX 33편). 공장 사용률 설문은 없다(17번 A17). 컨테이너 1개, 학생이 이해하기 쉽다. 장치 등록·명령 받기·끊김 시 저장은 흐름으로 만들어야 한다.
- EdgeX: 공장용 엣지 플랫폼. 장치 등록·명령 창구·끊김 시 저장이 기본으로 있다. 컨테이너 약 10개. 원본이 이미 쓴다. 내부 메시지 버스는 엣지 안에만 두고, UNS로는 `mqtt-export`로 내보내며 요청은 `ExternalMqtt`로 받는다(공식 문서, 17번 A18).
- 합격 조건: 12태그 누락 0 / 화면 명령이 PLC까지 가고 확인 응답이 돌아옴 / 10초 단절 뒤 복구·유실이 원본(7.3초·120 태그·초)보다 나쁘지 않음 / 설비 추가를 등록부에서 자동 생성 / 외부 요청을 공장 안에서 받아 검사하고 수용·거부로 답하는 수신기를 얼마나 잘 받쳐 주나. 비교값으로 메모리, 재시작 뒤 사람 손 없이 복귀하는지·유실 개수, p95 지연을 함께 본다(17번 A16).
- Node-RED는 읽기 경로를 전에 잰 기록이 있다(1,356/1,356, p95 2.51 ms). 쓰기·단절 복구·등록부 생성은 미측정이다.
- 규칙: 측정값을 나란히 놓고 더 좋은 쪽. 한쪽만 합격 기준을 넘으면 그쪽. 숫자와 고른 이유를 남긴다.
- 피지컬 AI를 이유로 EdgeX를 정한 적은 없다(피지컬 AI는 조사하지 않았다. 한때 "EdgeX 쪽 무게가 커진다"는 말은 에이전트의 조사되지 않은 일반 지식이었다).

**Q. EdgeX는 공장에 맞게 만들어졌는데 왜 덜 쓰이나?**
공개 지표(논문 33편, 다운로드 약 6만)가 작고 추세는 "정체~유지"다. 이유는 판단이다(확인한 사실 아님): 이 기능이 필요한 공장은 Kepware 같은 상용을 사고, EdgeX는 다른 제품의 뼈대로 쓰여 공개 지표에 덜 잡히며, 무겁다. Node-RED 숫자에는 스마트홈·시제품 같은 비산업 사용이 섞여 있다. 실제 공장 사용량은 둘 다 공개 자료로 알 수 없다.

**Q. "2027년 3월 지원 종료"는 무슨 뜻인가? 그때부터 못 쓰나?**
아니다. 그 판(EdgeX 4.0)에 보안 패치·버그 수정이 더 나오지 않는다는 뜻일 뿐, 프로그램도 프로젝트도 계속된다. **판별 지원 종료일은 제품을 빼는 이유가 아니다.** 학기마다 같은 메이저 안 최신 부 버전으로 올리고, 지원이 끝나는 판은 다음 판으로 올린다. 제품을 빼는 경우는 ① 개발이 멈춘 제품(예: 저장소가 archived된 OpenPLC v3) ② 라이선스가 유료·제한형으로 바뀐 판(예: EMQX 5.9+, ThingsBoard 4.4+) 두 가지뿐이다.

**Q. Flink 2.2.1은 예외인가?**
예외가 아니다. 2.2.1로 시작하고, 2.3용 Kafka 커넥터가 나오면 2.3으로 올린다. Flink는 대표 스트림 처리 엔진 중 하나이고(점유율은 Spark가 큼), 원본과 같은 판정(70/70)과 재시작 자동 복구를 실측했다.

**Q. 무조건 새 버전이 좋은가? "지원판으로 올린다"는 무슨 말인가?**
무조건은 아니다. 같은 메이저 안에서 지원이 계속되는(보안 패치가 나오는) 최신 부 버전을 쓰고, 같은 판 안에서 가벼운 이미지(alpine 등)를 고른다. 원본의 Kafka 3.9, InfluxDB 2.7, Grafana 11.4 같은 옛 판은 최신 부 버전으로 올린다.

**Q. "중계기"는 무엇인가? 우리가 만든 건가?**
"중계기"라는 말은 쓰지 않고 실제 이름으로 부른다. MQTT → Kafka로 옮기는 부품은 오픈소스 커넥터다(원본은 Telegraf, 새 베이스는 Bento). 우리가 직접 만드는 것은 IT 발송기, OT 작업 요청 수신기(엣지 흐름), 설비 등록부, 승인 흐름, 분석 경고의 상태표(ISA-18.2), 라우터 규칙이다(맞는 무료 제품이 없어서). DMZ 요청 게이트웨이는 Bento 파이프라인 설정으로 만드는 안을 먼저 실측하고, 안 되면 자체 코드로 한다(17번 E11). PLC 프로그램도 우리가 쓰지만 이는 PLC에 넣는 제어 논리다.

**Q. Telegraf와 Mosquitto는 무엇인가?**
Telegraf는 데이터를 모아 다른 곳으로 보내는 수집·전달 에이전트다(InfluxData, MIT). Mosquitto는 MQTT 메시지를 받아 구독자에게 나눠 주는 브로커다(Eclipse 재단).

**Q. Vector는 왜 안 쓰나?**
Kafka 재조정(재시작) 뒤 소비를 멈추는 버그(#22006)가 있고 수정판이 없다.

**Q. 임베딩(문서·온톨로지 벡터)은 어디서 만드나? PC에 Ollama를 깔아야 하나?**
아니다(사용자 결정 2026-09-30). 모든 AI 호출은 GCP의 LiteLLM(`knu-litellm`)으로 간다. 분석은 모델 `coding`, 임베딩은 모델 `embedding`(text-embedding-3-small, 1536차원). 온톨로지 개체와 매뉴얼 절 검색이 같은 임베딩을 쓴다. 기동 때 graph-seed가 빠진 벡터·0 벡터를 세어 하나라도 있으면 실패로 끝난다(실측: 절 26·개체 113, 빠진 0·0 벡터 0). 이상 주입 → AI 조치 제안 20.54 s(목표 1분).

**Q. 수집기(Bento)는 문제없나?**
결함 셋이 확인됐다(STABILITY S31·S32·S36): ① DMZ → Kafka MQTT 입력이 지속 세션으로 다시 붙을 때 처리기를 늦게 등록해 11회 중 1회 조용히 멈춤(paho README가 경고하는 조건, V1 Telegraf S2와 같은 부류), ② 출력이 막히면 MQTT 연결 유지가 막혀 DMZ 복구 35 s, ③ Kafka 재시작 뒤 소비자 그룹에 새 구성원으로 들어와 옛 구성원의 45 s 세션 만료를 기다려 IT 복구 약 60 s(고정 구성원 ID·세션 시간을 Bento가 설정으로 열지 않음). Bento 최신판·Redpanda Connect도 같은 코드다. 해결안(A 한계로 기록 / B Bento 수정 빌드 / C 이 구간을 작은 자체 코드로)은 사용자 결정 대기.

**Q. 컨테이너 메모리를 기능·안정성 유지한 채 줄일 수 있나?**
줄였다: 조립 직후 5,588 → 4,675 MiB(30개, 3분 중앙). Flink TaskManager·JobManager 메모리 크기, Neo4j 힙·페이지 캐시, cAdvisor 수집 지표, Grafana 기본 플러그인을 쓰는 만큼만 두었고, 줄인 뒤 힙 여유(TaskManager 22 %·JobManager 42 %·Neo4j 16 % 사용)를 쟀다. Kafka 힙은 256 MB로 줄이자 GC 뒤 82 %가 차서 512 MB로 되돌렸다(S35). 쓰지 않는 개발·시험 이미지·볼륨을 지워 이미지 37.0 → 24.9 GB, 볼륨 29.8 → 24.0 GB. CPU 합계는 경량화 뒤 더 높게 나왔지만 설정을 바꾸지 않은 컨테이너도 고르게 올라 원인 미확인이다.

## 4. 탐지

**Q. Z-Score는 원본(V1)에서도 잡음 고장을 못 잡았나?**

**Q. 오토인코더를 배속 설비로 다시 학습하면 안 되나?**
배속 600 데이터로 학습하면 안 된다. 드리프트·베어링 탐지율이 100 %에서 0 %로 떨어진다(결함 S6). "V1 모델 유지"의 뜻: 학습기가 기동 때 모델을 다시 만들되, 학습 데이터는 V1과 같이 설비 시간 그대로(`physics_time_scale: 1`)로 만든다. 운영 가상설비는 배속 600 그대로다. 옛 모델 볼륨(`rot-iiot_model-store`)을 그대로 가져다 쓰는 것이 아니다(단계 4 ⑥). 배속 600 운영에서 정상 오경보가 느는 문제의 근본 해결은 표본에 설비 시각을 싣고 ML 입력 창·Flink 창을 설비 시각 기준으로 자르는 것이다(17번 K4 추천, 단계 4 ⑥에서 구현하고 오경보 기준으로 판정).

**Q. 인터록은 어떻게 동작하나? V1과 같나?**
다르다(사용자 결정 2026-09-30, 현업 방식). PLC가 6.5 barg에서 트립하면 펌프 운전 명령을 끄고 트립을 기억한다. 압력이 5.2 barg 아래일 때 운전원 리셋(FUXA "인터록 리셋")이나 현장 패널 리셋으로만 풀리고, 펌프는 운전원이 다시 켜야 돈다. 외부 요청(AI)으로는 리셋할 수 없다. V1은 압력이 내려오면 저절로 풀렸다(FUNCTION_MAP CAP-12). 실측: PLC 계약 60/60, 제어 S16 통과, 2 s 짧은 과압도 FUXA 공정 알람에 인터록이 뜨고 리셋까지 켜져 있음(3/3).

## 5. 진행 방식

**Q. 돌려 봐야 아나, 조사로 알 수 있나?**
무엇을 쓸지는 조사로 정한다. 우리 설비·PC에서 되는지(고장→알람 10초, 복구, 메모리)는 돌려 봐야 안다. 그래서 조사로 고르고, 한 번에 조립하고, 한 번에 검증한다.

**Q. 후보마다 다 시험해 봤나?**
층마다 후보를 따로 시험하는 방식은 쓰지 않는다(이중 작업). 조사로 고르고 한 번에 조립·검증한다. 예외는 엣지 한 칸(EdgeX·Node-RED 나란히 실측)이다.

**Q. 딥리서치를 여러 개 돌려야 하나?**
의뢰서 하나로 넓게 한 번에 한다. 우리 구조를 정답으로 두지 않고 "우리는 이렇다, 현업은 어떻냐"로 묻고, 구조와 스택을 함께 묻는다. 질문 목록은 띄우기 전에 사용자에게 보여 준다.

**Q. 조사가 죽은 건 아닌가? 왜 WebFetch 허용 창이 뜨나?**
살아 있는지는 결과 파일 수정 시각으로 확인한다. 웹 읽기 창은 백그라운드 조사자가 웹 페이지를 여는 것이다. 사용자가 다른 명령을 끊거나 창을 거부하면 조사가 같이 멈출 수 있다. 멈추면 묻지 않고 같은 의뢰서로 다시 띄운다.

**Q. 원본보다 나아지고 있나? 메모리·CPU·복잡성은 어떻게 달라졌나?**
새 베이스는 아직 조립 전이라 잰 값이 없다. 비교 기준은 V1 실측(HANDOFF §5: 메모리 5,918 MiB(SCADA 24 + AI 5), CPU 51.2 %, 컨테이너 29, 알람→화면 p95 FUXA 1.84 s, 브로커 2개·Telegraf 3개)이다. 새 베이스의 전후 비교는 조립 뒤 §3-5 검증에서 같은 방법으로 잰다.

**Q. Prometheus·Grafana는 실제로 쓰이나?**
쓴다. Prometheus는 서버·컨테이너 같은 플랫폼 감시와 경보(Alertmanager)를, Grafana는 공정 이력 추세와 감시 화면을 맡는다. Prometheus는 클라우드 네이티브 감시의 표준급, Grafana는 널리 쓰는 대시보드다(17번 J10·J11). 감시 지표는 공장 쪽 Prometheus agent가 DMZ로 보내고 IT 본 Prometheus가 DMZ에서 가져간다(17번 G5). 공정 알람과는 분리하며, 새 베이스에서 기본으로 켠다(V1 기능 보존).

**Q. v3 설계서 구조는 실제로 도는가?**
v3는 보이스리 측이 실제로 구축해 실행했고 사용자가 직접 봤다. 그래서 비교 대상으로 무게가 있지만, 판단은 현업 조사로 한다. 보이스리 쪽 코드(compose·설정)를 받으면 칸별로 재사용을 검토할 수 있다.

**Q. 다른 세션이 같은 도커를 건드리면? 다른 프로젝트 자원은?**
같은 PC에서 다른 Claude 세션이나 다른 프로젝트가 도커를 쓸 수 있다. 측정 전에 `docker ps -a`로 확인하고, 측정은 이 프로젝트(`rot-*`) 합계로 센다. 다른 프로젝트 자원은 평소에는 건드리지 않고, 사용자가 정리하라고 하면 정리한다(자동 권한 판정기가 막으면 사용자가 수동으로 승인한다).

**Q. 리서치에 필요한 것이 다 나왔나?**
구조(12)·세부(13)·스택(14)·무료 대체품 비교(15)·외부 시스템 연결(16)로 요청한 항목이 모두 나왔고, 설계 판단의 근거는 17번에서 다시 확인했다(근거 56·추천 14·미해소 0). 근거 강도는 다르다: 구조는 표준 원문 중심, 세부는 검색 요약만 본 곳이 많고, 스택의 버전·라이선스는 공식 자료 중심이다. 실제 공장 구성과 채택 통계는 공개 자료에 없다.

**Q. 수정은 땜빵인가 근본 수정인가? 기반은 어느 정도여야 하나?**
근본 수정만 한다. 수동 재시작·sleep으로 순서 맞추기·검사 건너뛰기·실패를 통과로 세기 같은 땜빵은 금지하고, 원인을 찾아 설정·코드에서 고친다. 고칠 때마다 같은 원인의 땜빵이 남았는지 같이 본다. 기반은 깨끗하고 원활하게 돌아야 한다: 명령 한 번에 모든 컨테이너가 healthy(사람 손 0), 재시작 반복·설명 못 하는 오류 로그 0, 재시작 뒤 스스로 회복, 쓰지 않는 서비스·파일·중복 설정 0, 새로 받은 패키지로도 똑같이 뜸(HANDOFF §3-7). "됐다"는 이것을 실제로 돌려 확인한 뒤에만 말한다.

**Q. 모든 걸 버리고 다시 시작하나? V1을 안정화한 건 아깝지 않나?**
방향·계획 문서는 새로 썼다. 사실·도구·원본 코드는 유지한다. 원본 V1에 같은 제품 수정 다섯 가지(Flink HA, ONNX 체크포인트, Kafka 데이터 위치, InfluxDB 설정 볼륨, FUXA 판 고정)를 얹은 `docker-compose.stable.yml`이 있고, 흐름·Kafka 데이터 위치·탐지기 재시작 복구를 확인했다. 결측 주입 관련 verify 3개 실패는 미결이다.

**Q. 현업에는 AI 층이 없을 텐데, Kafka·MQTT와 AI의 연결은 현업에서 어떻게 조사했나?**
맞다, 현업에 "AI 층"이라는 층은 따로 없다(층은 Purdue L0~L5). AI는 종류별로 자리가 다르다: ML 예측·이상 탐지는 주로 L1~L3(PLC·엣지·SCADA 쪽), LLM·에이전트는 L4~5(OT 밖)에서 OT가 브로커·감사되는 중간 버퍼로 밀어낸(push) 데이터를 읽기 전용으로 쓴다(CISA 등 9개 기관 AI-OT 지침 2025-12 표1·p.15·p.19, 12번 §4-3). "Kafka를 거쳐 AI로"는 이 브로커·버퍼 원칙과 UNS+Kafka 트렌드를 합친 구성이며 표준이 제품을 지목하지는 않는다. 지식 그래프·LLM 에이전트의 현장 운영 비율은 설문 수치가 없다(연구 증가·공정 산업 제품 단계). 우리는 교육용으로 이상 탐지(Flink)를 IT에 둔다 — 현업은 OT 가까이에도 흔하다는 차이를 보고서·수업에서 알린다(12번 표 "실시간 이상 탐지의 위치"). 명령은 AI 제안 → 담당자 승인 → 작업 요청(OPC UA ISA-95 Job Control 필드) → IT 발송기 → DMZ 게이트웨이 → 공장 안 수신기가 받을지 결정 → 제어기가 물리적으로 되는지 마지막 검사다(NAMUR NE 178은 공개 요약 수준으로만 인용: 요청 검증 절차, "최종 권한" 문장은 요약에 없음). 층 전체를 한 번에 담은 오픈소스 참조 구현은 찾지 못했다(13번).

**Q. AI 코드는 고치나?**
AI의 판단 로직(에이전트·온톨로지·매뉴얼 검색)은 고치지 않는다. AI가 설비에 닿는 연결 부분만 바꾼다: 조치 실행의 Modbus 직접 쓰기를 "작업 요청" 길로(승인 → IT 발송기 → DMZ 게이트웨이 → 브리지 → OT 수신기 → PLC → 두 겹 응답, HANDOFF §2-1 외부 시스템 연결 ④~⑥), 결과 확인을 PLC ACK·상태 토픽으로, 접속 주소를 새 망으로. 그래야 AI가 설비에 직접 쓰지 않는 현업 구조가 성립한다.

## 6. ceco_demo 와 설계검증 반영 (2026-09-30)

**Q. 이 저장소는 이제 무엇인가?**
CECO 학회에 올리는 학생 수준 산출물 예시다. 실제 강의는 새 래퍼로 따로 만든다. IoT-SCADA 층과 AI 층은 설계검증 2차 결과를 반영한 뒤로 더 고치지 않는다. 원본(V1) 대신 이 저장소가 원본 베이스다. 원본 폴더 삭제는 사용자가 확인한 뒤에 한다.

**Q. 직접 만든 것이 또 있나? 리서치대로 무엇을 바꿨나?**
리서치 표대로 했다. ① 업무 서비스의 알림 묶기·억제 → Alertmanager(ISA-18.2 억제 규칙), 기록만 PostgreSQL ② DMZ 게이트웨이 자체 코드 → Node-RED(같은 계약 시험 15건을 두 구현에 돌려 Node-RED 전부 통과, 자체 코드는 브로커 무응답에서 8 s 동안 답 없음) ③ IT 발송기 자체 코드 → Kafka 승인 토픽 + Bento http 처리기(IT 수집기 안 스트림) ④ 요청자 종류 필드(ai/mes)와 MES 흉내 요청자 ⑤ 엣지 Node-RED 편집기 읽기 전용, 게이트웨이는 편집기 없음, 둘 다 최신 판 ⑥ FUXA 손님 읽기 → Caddy 계정 관문 ⑦ Bento 수집기 입력 멈춤 경보 ⑧ 리서치 문서 오류 4곳 정정. 남은 직접 코드는 리서치가 "정당"으로 본 것(라우터 규칙, OT 수신기, 등록부 생성기, FUXA 화면 생성, PLC 프로그램, Flink 규칙, 학습 코드, 가상설비)과 업무 서비스의 시간 판정이다.

**Q. 수집기(Bento)는 문제가 있어서 바꿔야 하나?**
바꾸지 않는다. 멈춤 원인(지속 세션 재연결 때 처리기 등록 순서)은 지속 세션을 끄고 메모리 버퍼를 둬서 없앴고, 리서치도 "유지 + 입력 멈춤 감시 경보"를 권했다. Telegraf·직접 코드로 바꾸지 않는다. Kafka 재시작 뒤 IT 결과 약 1분 지연은 Kafka 소비자 그룹 동작이라 다른 수집기로 바꿔도 생긴다(알려진 한계, 유실 0).

**Q. 메모리는 더 줄일 수 있나?**
여기까지로 정했다(사용자 "뭐 일단 여기까지"). 후보(Flink TaskManager 768m, Neo4j 힙 512m 등)는 HANDOFF 이전 판에 적어 두었다. 게이트웨이를 Node-RED로 바꾸며 39 → 62 MiB, 발송기 컨테이너를 없애며 그만큼 줄었다.
