V1 프로토타입을 가볍고 안정적인 V2로 — 어디까지 왔나

흐름(설비 → 수집 → 전달 → 탐지 → 저장 → 화면 → AI)과 기능은 그대로 두고, 돌아가는 길·중복·지원 끝난 부품·숨은 오류를 걷어내는 작업입니다. 모든 숫자는 실제로 돌려서 잰 값이며, 안 잰 것은 "미측정"으로 표시했습니다.

요약한 화면으로 보면

  • 좋아짐 구조가 단순해졌습니다. 알람이 화면까지 가는 단계 12 → 8, 항상 떠 있는 컨테이너 24 → 11.
  • 좋아짐 장애에 강해졌습니다. 브로커 재시작 뒤 V1은 3번 중 2번 수집이 멈췄는데, V2는 3번 모두 스스로 복구(유실 0).
  • 좋아짐 메모리를 줄였습니다. 경량화 설정 뒤 SCADA 4,593 MiB → 3,039 MiB(같은 기준으로 약 34% 감소, 1회 측정).
  • 좋아짐 V1부터 숨어 있던 오류를 찾아 고쳤습니다. Kafka 데이터가 재시작 때 사라짐, 탐지 모델 잡이 복구 저장을 안 함 등 7건.
  • 남은 문제 Kafka 커넥터(Vector)가 Kafka가 오래 멈추면 다시 붙지 못하는 알려진 버그(수정판 없음). 같은 일을 하는 Bento로 교체 예정.
  • 확인 중 정상 운전인데 Z-Score 이상 알람이 3분에 68~83건. V1의 조용한 60초 기록은 0건이지만 V2는 고장 시험 직후에 잰 것이라, 같은 조건으로 다시 재는 중.

진행어디까지 했나

완료V1 해부·리서치데이터 갈래 16개를 코드로 추적해 "누가 받아 쓰는가" 판정. 리서치 10건(현업 참조 구조, 부품 수명·라이선스, 경량화, 버그).
완료V2 구조 재설계·조립쓰는 곳 없는 갈래 4개 제거, Telegraf 연결 3대 → Kafka 커넥터 1대, 브로커 2개 → 1개, 감시는 선택 모듈로.
진행 중V2 경량화·검증메모리 설정 적용 완료. Kafka 커넥터 교체와 Z-Score 원인 확인 뒤 최종 확인 1회.
예정V3 부품 교체 경량화Kafka → 더 가벼운 백본(NATS·Tansu), 수집기 비교(benthos-umh). 가벼워지고 나빠지지 않을 때만 채택.

구조데이터가 가는 길, 전과 후

읽는 법 · 줄 그은 칸 = V2에서 없앤 부품 · 색 칸 = V2에서 새로 들어간 부품 · 알람이 화면까지 가는 길만 그렸습니다(V1의 저장용 Telegraf는 V2에서 Kafka 커넥터가 함께 맡음)
V1 · 설비 값이 Kafka에 들어가기까지 6단계, 알람이 화면까지 12단계 설비→EdgeX(10개)→EdgeX 내부 브로커→내보내기→EMQX→Telegraf 브리지(MQTT→Kafka)→Kafka→Flink 탐지→Kafka→Telegraf 알람 재발행(Kafka→MQTT)→EMQX(다시)→FUXA 화면
V2 · 수집기 1개가 설비를 읽어 Kafka에 바로, 알람이 화면까지 8단계 설비→수집기(Telegraf)→Kafka→Flink 탐지→Kafka→Kafka 커넥터(Vector)→Mosquitto→FUXA 화면

남긴 이유가 있는 것: FUXA가 설비를 직접 읽는 길(수집·브로커가 죽어도 운전 화면은 살아 있어야 함), Kafka(탐지기 Flink가 Kafka로만 읽고 씀·재처리), InfluxDB(PostgreSQL로 합치면 디스크 35~58배).

남은 문제지금 막고 있는 것

Kafka 커넥터(Vector)가 가끔 멈춤

Kafka가 수십 초 멈췄다 돌아오면 Vector가 다시 붙지 못하고 저장을 멈춥니다. 공식 이슈 #22006으로 알려진 버그이고 아직 고친 판이 없습니다. 연결 유지 시간을 늘려 짧은 재시작은 막았지만 긴 중단은 못 막습니다.

조치: 같은 일을 하는 Bento로 교체합니다. 이전 실측에서 결과가 V1과 같았고(85 MiB), Kafka 연결 부품이 달라 이 버그가 없습니다. 교체 뒤 Kafka를 길게 멈추는 시험으로 확인합니다.

정상인데 Z-Score 알람이 많음

Z-Score 문제는 두 가지입니다. ① 잡음 고장을 못 잡는 것은 원본 V1도 같습니다(규칙 설계 한계). ② 정상 운전인데 울리는 것은 V2에서 3분에 68~83건 나왔고, V1의 조용한 60초 기록은 0건이었습니다. 다만 V2 값은 고장 시험 직후(설비 회복 중)에 잰 것이라 조건이 다릅니다.

조치: 고장을 넣지 않은 조용한 구간을 다시 재고, 알람 원값과 원시 데이터를 대조합니다.

다음다음 할 일

  1. Kafka 커넥터 Vector → Bento 교체, Kafka 장시간 중단 시험.
  2. Z-Score 알람 원인 확정 후 수정.
  3. 경량화된 V2에서 최종 확인 1회: 흐름·탐지 정확도(70건)·제어 안전·재시작·메모리·CPU.
  4. V3: 더 가벼운 부품 실측(NATS·Tansu, benthos-umh). 기능·성능이 그대로일 때만 채택.
  5. 최종 보고서와 학생용 쉬운 설명서.

용어부품 한 줄 설명

가상설비
한 생산 라인(원료탱크·펌프·반응기·교반기·히터·냉각기·배출밸브, 설비 7대)을 흉내 내는 프로그램. 센서 12개 값을 1초마다 Modbus로 내고, 고장을 일부러 넣을 수 있음(시간 600배속).
EdgeX V2에서 뺌
통신 방식이 서로 다른 장비를 한 틀로 모으는 수집 플랫폼. 우리 라인은 설비 7대·센서 12개를 Modbus 연결 하나로 읽어 그 강점을 쓰지 않았고, 컨테이너 10개에 지원이 2027년 3월 끝남. PLC가 늘어나도 Telegraf 설정 추가로 읽을 수 있음.
Telegraf 수집기
설비에서 값을 읽어 다른 곳으로 보내는 수집 에이전트. V1은 연결용 3대(MQTT→Kafka 브리지, Kafka→InfluxDB 저장, Kafka→MQTT 알람 재발행), V2는 설비를 직접 읽는 수집용 1대.
MQTT 브로커
짧은 메시지를 구독자에게 나눠 주는 우체국. V1 EMQX(무료판 지원 종료) → V2 Mosquitto(약 8 MiB).
Kafka
데이터를 순서대로 쌓아 두고 여러 프로그램이 각자 읽게 하는 대형 게시판. 지난 데이터 다시 읽기(재처리) 가능.
Flink
흘러오는 데이터를 실시간으로 검사하는 탐지 엔진. 한계값·Z-Score·순서 패턴·AI 모델(ONNX) 4가지 탐지.
ZooKeeper
Flink가 재시작해도 탐지 잡을 되살리도록 상태를 기억해 두는 관리자.
Kafka 커넥터 Vector · Bento
Kafka에 모인 결과를 InfluxDB(저장)와 Mosquitto(화면)로 옮겨 주는 연결 프로그램. V1에서는 Telegraf 2대가 하던 역할을 V2에서 1대로 합침. 둘 다 공개 오픈소스 제품이고 우리는 설정 파일만 작성. Vector는 버그로 교체 예정, Bento가 대안.
InfluxDB
시간 순서 데이터 전용 저장소(히스토리안). 24시간분이 약 19 MB로 가장 작음.
FUXA
운전원이 보는 공정 화면(HMI). 설비를 직접 읽고 조작.
Grafana
저장된 이력을 그래프로 보여 주는 화면.
Prometheus 등 감시 4종 선택 모듈
프로그램들이 살아 있는지 보는 운영 감시. 알림 받는 곳이 설정돼 있지 않고 수업은 개념 설명만이라 기본은 꺼 둠(명령 한 줄로 켬).
NATS / Tansu V3 후보
Kafka보다 가벼운 게시판 역할 후보. Tansu는 Kafka와 같은 방식으로 붙음.

정리PC 도커 정리

시험용으로 받았던 후보 이미지, 다른 프로젝트 자원, 빌드 임시 파일을 지워 도커 사용량을 약 174 GB → 약 30 GB로 줄였습니다. 남은 것은 지금 작업 중인 V1(비교 기준)·V2·AI 층입니다.
