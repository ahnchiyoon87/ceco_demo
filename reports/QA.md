## 2. 구조

**Q. OT가 뭔가?**
OT(운영 기술)는 공장에서 기계를 실제로 움직이는 쪽(센서·PLC·SCADA 화면)이다. 멈추면 기계가 서므로 안전과 계속 도는 것이 먼저다. IT(정보 기술)는 사무실 쪽(저장·분석·AI·업무)이고, DMZ는 둘 사이 완충지대다. 데이터는 OT가 밀어서 내보내고, IT에서 기계로 바로 가는 명령 길은 없으며, IT가 멈춰도 공장은 돈다. 우리 그림에서 L1~L4가 OT, L5가 DMZ, L6~L10이 IT다(보고서 5장).

**Q. IoT-SCADA 층은 어디까지이고, 어디부터 우리가 맞춰 설계한 것인가?**
"IoT-SCADA"는 표준 층 이름이 아니다. 표준 층은 Purdue 모델(L0 장치, L1 PLC, L2 SCADA·HMI, L3 히스토리언, L3.5 DMZ, L4~5 기업망)이다. 우리 L1~L4(설비·PLC·엣지·허브·화면)와 L5 DMZ의 "OT가 밀어냄"은 표준 근거가 강하다. L6 Kafka부터 위는 IT 쪽 데이터·AI 영역으로, 제품·배치는 업계 동향과 우리 설계가 섞여 있다. 현업과 다른 곳은 둘이다: 이상 탐지(Flink)를 IT에 둠(CISA는 ML 탐지를 주로 L1~L3에 둔다고 씀), 이력 정본을 IT 한 곳에만 둠(현업 표준 배치는 OT 사이트 히스토리언 + DMZ 복제). 층별 표는 보고서 6장.

**Q. IoT-SCADA에서 밖으로 보낼 때 MQTT → Kafka 패턴을 써야 하나? 그냥 좋아서 고른 건가?**
규칙(표준, 근거 강함)은 DMZ를 거치고 OT가 밀어내며 IT→OT 직접 길이 없다는 것이다(NIST SP 800-82r3, CISA 2016·2025). 방법은 표준이 하나로 정하지 않았다: ① 히스토리언 복제(사이트 히스토리언 OT L3 → DMZ 복제 → 기업, CISA 2016이 예로 드는 기본 배치) ② 데이터 다이오드(NIST가 방화벽 대안으로 언급) ③ 엣지 → MQTT 허브(UNS) → DMZ 중계 → Kafka(독립 분석 기관 IoT Analytics 2026-01이 현업 추세로 적음, HiveMQ·Waehner 등 벤더 문서, 사용 비율 통계 없음). 우리는 규칙을 지키고 방법은 ③을 쓴다(원본 V1 뼈대가 ③이고 12번이 규칙을 지키면 현업과 맞다고 판단, 무료로 구성 가능). ③을 "현업 주류"라고 쓰지 않고 "현업 추세, 표준 기본 배치는 ①"이라고 쓴다. "UNS는 히스토리언을 대체하지 않는다"(IT/OT Insider). 즉 근거 없이 고른 것은 아니지만, "주류"라는 사실 확인이 아니라 근거 있는 설계 판단이다(조사 12번 권장안, 사용자와 따로 비교해 정한 것은 아님).

**Q. 외부 시스템이 FUXA 같은 공장 안 화면을 직접 보면 안 되나? 이건 법인가, 무조건인가?**
법이 아니라 표준·지침의 권고다. CISA 2016: "기업이 접근하는 구성요소를 DMZ에 두면 기업망에서 제어망으로 가는 직접 경로가 필요 없다. 모든 경로는 DMZ에서 끝난다", "DMZ 없는 2구역 구성은 겨우 허용되는 수준". NIST SP 800-82r3도 기업망과 OT망 사이에 트래픽이 직접 지나가지 않게 하라고 한다. ISA-112 초안 그림은 외부 앱의 SCADA 직결을 강하게 말린다. 그래서 외부 시스템이 공장 안 FUXA에 직접 붙는 것은 권고에 어긋나지만 "무조건 금지"는 아니다. "사본을 떠야 한다"도 방법 중 하나다(원칙은 외부 접근이 DMZ에서 끝나고 OT가 밀어내는 것). 조사한 기준 중 법령은 21 CFR Part 11(미국 연방 규정, 감사 기록) 하나이고, 한국 법규는 조사하지 않았다. 기준 전체는 보고서 2장 "근거 기준 목록". 외부 시스템과 주고받는 구체적 방법과 사용 정도는 조사 16번(`docs/research/deep-2026-09-29/16-external-integration.md`, 의뢰서 §9)에서 본다.

**Q. 외부 연결 방식은 표준이 정한 것인가, 판단인가?**
표준 문서에 적힌 것(권고, 법은 아님): 기업망과 OT망 사이에 트래픽이 직접 지나가지 않게 DMZ와 방화벽을 둔다(NIST SP 800-82r3 §1), 기업이 접근하는 구성요소는 DMZ에 두고 모든 경로는 DMZ에서 끝나며 공장망 장치가 먼저 연 연결만 허용한다(CISA 2016 §2.4.2), 바깥의 설비 쓰기 요청은 검증 후 최종 권한은 제어 쪽(NAMUR NE 178), 사람 없는 AI 제어 제한(CISA 2025). 표준에 없는 것(조사 12·13번의 판단이자 우리 설계): 사본(히스토리언 복제)으로 할지 MQTT 허브 → DMZ 중계 → Kafka로 할지, 명령을 Kafka로 보내는 것, 게이트웨이 자체 코드, 이력을 IT 한 곳에만 두는 것. "사본을 떠야 한다"는 표준 요구가 아니다(CISA 2016이 DMZ 구성요소의 예로 히스토리언 복제를 들 뿐). 조사 범위 밖(한국 법규, 유료 표준 본문)에 "반드시" 조항이 있는지는 모른다. 보고서 6장.

**Q. 현업은 어떤 구조로 되어 있나?**
망은 OT(공장)·DMZ(완충지대)·IT(분석) 세 구역이다. 층은 설비 → PLC(제어기: 인터록·운전 모드·명령 최종 판단) → SCADA 화면 → 엣지 연결(프로토콜 변환, 끊기면 저장 후 전송) → MQTT 허브(UNS) → 설비 모델 → 히스토리언 → DMZ 중계 → Kafka형 장부 → 탐지 → 플랫폼 감시 → AI(읽기 전용) → MES·ERP다. 설비가 늘어도 층은 그대로이고, 설비 이름 체계·토픽 규칙·설비 종류별 모델·엣지 노드로 흡수한다. 자세한 것은 HANDOFF §2-1, 조사 원문 `docs/research/deep-2026-09-29/12`.

**Q. 참조 설계서 v3가 정답인가? 우리가 억지로 고치는 건가?**
v3는 다른 팀이 실제로 구축·실행한 구조이고, 우리 구조도와 함께 **비교 대상**이다. 판단은 현업 조사로 한다. v3는 망 분리·명령 게이트웨이·경보 분리가 현업과 맞고, OT 이력 저장·설비 모델 층·알람 수명주기가 없다. 원본(V1)의 뼈대도 현업과 대부분 같다. 억지로 고친 것은 경량화를 앞세워 층을 뺀 V2였고, V2는 쓰지 않는다.

**Q. 흐름(데이터·명령·알람) 길은 하나로 통일해야 하나, 여러 방향이 맞나?**
둘 다다. **같은 종류의 흐름은 길 하나**로 모은다(읽기 하나, 명령 하나, 알람 전달 하나). 방향이 여러 개인 것은 정상이다: 데이터는 올라가고, 명령은 내려가고, 알람은 화면과 분석 쪽으로 간다. 원본의 문제는 같은 흐름이 여러 길로 간 것이다(FUXA와 EdgeX가 같은 설비를 따로 읽음, 쓰기 길 3개).

**Q. 여러 단계를 타고 흐르는 게 필요한가? 알람이 되돌아 내려가는 건 결함 아닌가?**
망을 나누면 경유가 생기는 것이 현업 모양이다. 알람이 IT에서 OT 화면으로 내려가는 길도 v3와 같은 현업 패턴이다. 없애는 것은 같은 데이터를 두 번 옮기는 길이다.

**Q. 층을 빼거나 두 개를 하나로 합칠 수 있나?**
현업 구조에 그 층이 없을 때만 뺀다. 같은 역할이 중복된 것만 합친다(예: 원본의 MQTT 브로커 2개 → OT 허브 1개(조립 때 정하는 DMZ 중계 방식에 따라 구역마다 하나가 될 수 있다), Telegraf 3개 → 커넥터 1종).

**Q. Kafka는 필수인가? MQTT로 바로 받으면 안 되나?**
Kafka형 장부는 현업 구조의 한 층이다. MQTT 허브는 "지금 상태"를 모으는 곳이고, 이력 보관·다시 읽기·여러 소비자는 Kafka가 맡는다. 현업은 둘을 이어 붙인다(MQTT → 커넥터 → Kafka). 그래서 둔다.

**Q. Redpanda는?**
Kafka와 호환되지만 라이선스가 BSL이라 관문에서 제외한다.

**Q. 설비는 몇 대인가?**
설비 7대(TK-101·P-101·R-101·M-101·HX-101·HX-102·CV-101), 센서 12개, Modbus 연결 1개다. "설비 1대"는 틀린 말이다. 현업 가정은 설비 다수·통신 혼재로 고정한다.

**Q. EdgeX(통역사 역할)는 필요 없나? V2에서 EdgeX·MQTT를 빼도 상관없나?**
상관있다. 엣지 연결 층은 현업 구조에 있는 층이고, 원본의 기능(장치 등록부·명령 API)과 수업 자료(`edgex/telemetry`)가 걸려 있다. 그래서 층을 뺀 V2는 쓰지 않는다. 엣지 칸에 어떤 제품을 쓸지는 아래 §3의 EdgeX·Node-RED 답을 따른다.

**Q. EdgeX와 Telegraf는 기능이 같고 Telegraf가 가벼운 것인가?**
아니다. EdgeX는 장치 등록부·명령 API·UI가 있고, Telegraf는 읽기 전용 수집기라 명령(쓰기) 길이 없다.

## 3. 스택

**Q. 현업은 어떤 스택을 쓰고, 우리는 무엇을 쓰나?** (HANDOFF §2-3 칸별 표)
현업과 같은 제품: Kafka, Flink, Grafana, Prometheus, Neo4j, PostgreSQL. MQTT 브로커 Mosquitto는 현업에서 EMQX·HiveMQ와 함께 널리 쓰이는 제품이다(EMQX 5.9+는 BSL, HiveMQ는 쓰기 기능 유료라 무료 정식판인 Mosquitto). 현업 주류가 상용이라 무료로 대신: PLC(→ OpenPLC v4), 엣지(→ Node-RED 또는 EdgeX), 이력 저장(→ InfluxDB), 화면(→ FUXA), 설비 등록부·승인 흐름·알람 관리(→ 자체 + PostgreSQL). 보고서는 칸마다 "현업은 주로 무엇 → 우리는 무엇 → 왜"로 쓴다.

**Q. 현업에서 쓰는 건 다 유료인가?**
아니다. Kafka·Flink·Grafana·Prometheus·PostgreSQL·Mosquitto는 현업도 무료 오픈소스 본체를 쓴다. 상용이 주류인 칸은 PLC·화면·히스토리언·엣지 등 몇 개다.

**Q. 무료로 써도 된다는 근거가 있나?**
있다. 칸마다 라이선스 원문 근거가 있다(Apache-2.0, MIT, EPL, AGPL 등). 상용을 못 쓰는 근거도 있다: CODESYS는 라이선스 없이 2시간 데모(검색 요약), Ignition 무료판은 비상업·개인 교육용만(공식 원문), HiveMQ Edge는 설비 쓰기가 유료(공식 원문), ThingsBoard는 4.4부터 BUSL, EMQX는 5.9부터 BSL, TimescaleDB 압축·연속 집계는 TSL.

**Q. "무료 중 1위"는 근거가 있나?** (조사 원문 15번)
다운로드 수만이 아니라 논문 수(OpenAlex)·대학 수업·재단·개발자 수·소스 확인 기능으로 비교했다.
- PLC — OpenPLC v4: 공식 도커 이미지가 있는 유일한 후보, IEC 61131-3 다섯 언어, 논문 138편, Western Carolina 대학 PLC 과목. 약점: 근거 대부분이 v3 계보, v4는 한 회사 개발.
- 화면 — FUXA: 무료로 MQTT·OPC UA·Modbus를 모두 갖춘 유일한 공정 HMI, 가장 활발히 개발 중. 약점: 재단·공장 사례 없음, 알람 보류(shelving) 없음. 2안 Rapid SCADA 6.
- 엣지 — 아래 EdgeX·Node-RED 답.
무료 제품끼리의 점유율 설문은 없다.

**Q. Kepware는 유료인가?**
유료다(PTC 상용 제품, 드라이버별 라이선스). 체험판 조건(시간 제한)은 공식 문서로 확인하지 않았다. 비용 0 관문에 걸리므로 설명용이다.

**Q. EdgeX와 Node-RED 중 무엇을 쓰나?**
**조립 단계에서 둘을 같은 가상설비·PLC에 붙여 나란히 재서 정한다.** 문서만으로는 막상막하다.
- Node-RED: 블록을 이어 만드는 범용 도구. 무료 중 사용 근거가 더 많다(산업 논문 486편 대 EdgeX 33편, OpenJS 재단, Opto 22 산업 제어기 기본 탑재). 컨테이너 1개, 학생이 이해하기 쉽다. 장치 등록·명령 받기·끊김 시 저장은 흐름으로 만들어야 한다.
- EdgeX: 공장용 엣지 플랫폼. 장치 등록·명령 창구·끊김 시 저장이 기본으로 있다. 컨테이너 약 10개. 원본이 이미 쓴다.
- 합격 조건: 12태그 누락 0 / 화면 명령이 PLC까지 가고 확인 응답이 돌아옴 / 10초 단절 뒤 복구·유실이 원본(7.3초·120 태그·초)보다 나쁘지 않음 / 설비 추가를 등록부에서 자동 생성. 메모리는 둘 다 합격했을 때의 비교값이다.
- Node-RED는 읽기 경로를 전에 잰 기록이 있다(1,356/1,356, p95 2.51 ms). 쓰기·단절 복구·등록부 생성은 미측정이다.
- 규칙: 둘 다 합격하면 Node-RED(가볍고 더 많이 쓰임). 하나만 합격하면 그쪽.

**Q. EdgeX는 공장에 맞게 만들어졌는데 왜 덜 쓰이나?**
공개 지표(논문 33편, 다운로드 약 6만)가 작고 추세는 "정체~유지"다. 이유는 판단이다(확인한 사실 아님): 이 기능이 필요한 공장은 Kepware 같은 상용을 사고, EdgeX는 다른 제품의 뼈대로 쓰여 공개 지표에 덜 잡히며, 무겁다. Node-RED 숫자에는 스마트홈·시제품 같은 비산업 사용이 섞여 있다. 실제 공장 사용량은 둘 다 공개 자료로 알 수 없다.

**Q. "2027년 3월 지원 종료"는 무슨 뜻인가? 그때부터 못 쓰나?**
아니다. 그 판(EdgeX 4.0)에 보안 패치·버그 수정이 더 나오지 않는다는 뜻일 뿐, 프로그램도 프로젝트도 계속된다. **판별 지원 종료일은 제품을 빼는 이유가 아니다.** 학기마다 같은 메이저 안 최신 부 버전으로 올리고, 지원이 끝나는 판은 다음 판으로 올린다. 제품을 빼는 경우는 ① 개발이 멈춘 제품(예: 저장소가 archived된 OpenPLC v3) ② 라이선스가 유료·제한형으로 바뀐 판(예: EMQX 5.9+, ThingsBoard 4.4+) 두 가지뿐이다.

**Q. Flink 2.2.1은 예외인가?**
예외가 아니다. 2.2.1로 시작하고, 2.3용 Kafka 커넥터가 나오면 2.3으로 올린다. Flink는 실시간 탐지의 현업 1위이고, 원본과 같은 판정(70/70)과 재시작 자동 복구를 실측했다.

**Q. 무조건 새 버전이 좋은가? "지원판으로 올린다"는 무슨 말인가?**
무조건은 아니다. 같은 메이저 안에서 지원이 계속되는(보안 패치가 나오는) 최신 부 버전을 쓰고, 같은 판 안에서 가벼운 이미지(alpine 등)를 고른다. 원본의 Kafka 3.9, InfluxDB 2.7, Grafana 11.4 같은 옛 판은 최신 부 버전으로 올린다.

**Q. "중계기"는 무엇인가? 우리가 만든 건가?**
"중계기"라는 말은 쓰지 않고 실제 이름으로 부른다. MQTT → Kafka로 옮기는 부품은 오픈소스 커넥터다(원본은 Telegraf, 새 베이스는 Bento). 우리가 직접 만드는 것은 명령 게이트웨이(명령 검증 통로)·설비 등록부·승인 흐름·분석 경고의 상태표(ISA-18.2)뿐이다(맞는 무료 제품이 없어서). PLC 프로그램도 우리가 쓰지만 이는 PLC에 넣는 제어 논리다.

**Q. Telegraf와 Mosquitto는 무엇인가?**
Telegraf는 데이터를 모아 다른 곳으로 보내는 수집·전달 에이전트다(InfluxData, MIT). Mosquitto는 MQTT 메시지를 받아 구독자에게 나눠 주는 브로커다(Eclipse 재단).

**Q. Vector는 왜 안 쓰나?**
Kafka 재조정(재시작) 뒤 소비를 멈추는 버그(#22006)가 있고 수정판이 없다.

## 4. 탐지

**Q. Z-Score는 원본(V1)에서도 잡음 고장을 못 잡았나?**
원본도 잡음 주입은 확률적으로만, 약 10.8초에 잡는다(결함 S10). 그래서 합격선은 "모든 고장 10초 안, 단 잡음 고장은 V1보다 나빠지지 않으면 합격"이다(HANDOFF §3-5). 워터마크 5초 + 연속 조건 + 창 안 잡음 때문이며 원본과 새 판이 같은 규칙 특성이다.

**Q. 오토인코더를 배속 설비로 다시 학습하면 안 되나?**
배속 600 데이터로 학습하면 안 된다. 드리프트·베어링 탐지율이 100 %에서 0 %로 떨어진다(결함 S6). "V1 모델 유지"의 뜻: 학습기가 기동 때 모델을 다시 만들되, 학습 데이터는 V1과 같이 설비 시간 그대로(`physics_time_scale: 1`)로 만든다. 운영 가상설비는 배속 600 그대로다. 옛 모델 볼륨(`rot-iiot_model-store`)을 그대로 가져다 쓰는 것이 아니다(단계 4 ⑥). 배속 600 운영에서 정상 오경보가 느는 문제의 근본 해결(ML이 보는 표본 간격을 설비 시간에 맞춤)도 단계 4에서 정한다.

## 5. 진행 방식

**Q. 돌려 봐야 아나, 조사로 알 수 있나?**
무엇을 쓸지는 조사로 정한다. 우리 설비·PC에서 되는지(고장→알람 10초, 복구, 메모리)는 돌려 봐야 안다. 그래서 조사로 고르고, 한 번에 조립하고, 한 번에 검증한다.

**Q. 후보마다 다 시험해 봤나?**
층마다 후보를 따로 시험하는 방식은 쓰지 않는다(이중 작업). 조사로 고르고 한 번에 조립·검증한다. 예외는 엣지 한 칸(EdgeX·Node-RED 나란히 실측)이다.

**Q. 딥리서치를 여러 개 돌려야 하나?**
의뢰서 하나로 넓게 한 번에 한다. 우리 구조를 정답으로 두지 않고 "우리는 이렇다, 현업은 어떻냐"로 묻고, 구조와 스택을 함께 묻는다. 질문 목록은 띄우기 전에 사용자에게 보여 준다.

**Q. 조사가 죽은 건 아닌가? 왜 WebFetch 허용 창이 뜨나?**
살아 있는지는 결과 파일 수정 시각으로 확인한다. 웹 읽기 창은 백그라운드 조사자가 웹 페이지를 여는 것이다. 사용자가 다른 명령을 끊거나 창을 거부하면 조사가 같이 멈출 수 있다. 멈추면 묻지 않고 같은 의뢰서로 다시 띄운다.

**Q. 원본보다 나아지고 있나? 메모리·CPU·복잡성은 어떻게 달라졌나?**
새 베이스는 아직 조립 전이라 잰 값이 없다. 비교 기준은 V1 실측(HANDOFF §5: 메모리 5,918 MiB(SCADA 24 + AI 5), CPU 51.2 %, 컨테이너 29, 알람→화면 p95 FUXA 1.84 s, 브로커 2개·Telegraf 3개)이다. 새 베이스의 전후 비교는 조립 뒤 §3-5 검증에서 같은 방법으로 잰다.

**Q. Prometheus·Grafana는 실제로 쓰이나?**
쓴다. Prometheus는 서버·컨테이너 같은 플랫폼 감시와 경보(Alertmanager)를, Grafana는 공정 이력 추세와 감시 화면을 맡는다. 둘 다 현업 1위 제품이다(14번 파일). 공정 알람과는 분리하며, 새 베이스에서 기본으로 켠다(V1 기능 보존).

**Q. v3 설계서 구조는 실제로 도는가?**
v3는 보이스리 측이 실제로 구축해 실행했고 사용자가 직접 봤다. 그래서 비교 대상으로 무게가 있지만, 판단은 현업 조사로 한다. 보이스리 쪽 코드(compose·설정)를 받으면 칸별로 재사용을 검토할 수 있다.

**Q. 다른 세션이 같은 도커를 건드리면? 다른 프로젝트 자원은?**
같은 PC에서 다른 Claude 세션이나 다른 프로젝트가 도커를 쓸 수 있다. 측정 전에 `docker ps -a`로 확인하고, 측정은 이 프로젝트(`rot-*`) 합계로 센다. 다른 프로젝트 자원은 평소에는 건드리지 않고, 사용자가 정리하라고 하면 정리한다(자동 권한 판정기가 막으면 사용자가 수동으로 승인한다).

**Q. 리서치에 필요한 것이 다 나왔나?**
구조(12)·세부(13)·스택(14)·무료 대체품 비교(15)로 요청한 항목이 모두 나왔다. 근거 강도는 다르다: 구조는 표준 원문 중심, 세부는 검색 요약만 본 곳이 많고, 스택의 버전·라이선스는 공식 자료 중심이다. 실제 공장 구성과 채택 통계는 공개 자료에 없다.

**Q. 수정은 땜빵인가 근본 수정인가? 기반은 어느 정도여야 하나?**
근본 수정만 한다. 수동 재시작·sleep으로 순서 맞추기·검사 건너뛰기·실패를 통과로 세기 같은 땜빵은 금지하고, 원인을 찾아 설정·코드에서 고친다. 고칠 때마다 같은 원인의 땜빵이 남았는지 같이 본다. 기반은 깨끗하고 원활하게 돌아야 한다: 명령 한 번에 모든 컨테이너가 healthy(사람 손 0), 재시작 반복·설명 못 하는 오류 로그 0, 재시작 뒤 스스로 회복, 쓰지 않는 서비스·파일·중복 설정 0, 새로 받은 패키지로도 똑같이 뜸(HANDOFF §3-7). "됐다"는 이것을 실제로 돌려 확인한 뒤에만 말한다.

**Q. 모든 걸 버리고 다시 시작하나? V1을 안정화한 건 아깝지 않나?**

**Q. 현업에는 AI 층이 없을 텐데, Kafka·MQTT와 AI의 연결은 현업에서 어떻게 조사했나?**
맞다, 현업에 "AI 층"이라는 층은 따로 없다(층은 Purdue L0~L5). AI는 종류별로 자리가 다르다: ML 예측·이상 탐지는 주로 L1~L3(PLC·엣지·SCADA 쪽), LLM·에이전트는 L4~5(OT 밖)에서 OT가 브로커·감사되는 중간 버퍼로 밀어낸(push) 데이터를 읽기 전용으로 쓴다(CISA 등 9개 기관 AI-OT 지침 2025-12 표1·p.15·p.19, 12번 §4-3). "Kafka를 거쳐 AI로"는 이 브로커·버퍼 원칙과 UNS+Kafka 트렌드를 합친 구성이며 표준이 제품을 지목하지는 않는다. 지식 그래프·LLM 에이전트의 현장 운영 비율은 설문 수치가 없다(연구 증가·공정 산업 제품 단계). 우리는 교육용으로 이상 탐지(Flink)를 IT에 둔다 — 현업은 OT 가까이에도 흔하다는 차이를 보고서·수업에서 알린다(12번 표 "실시간 이상 탐지의 위치"). 명령은 AI 제안 → 정비 요청 → 사람 승인 → 작업지시(ISA-95 Part 3, 13번 #23) → 검증 통로 → 제어기 최종 판단(NAMUR NE 178)이다. 층 전체를 한 번에 담은 오픈소스 참조 구현은 찾지 못했다(13번).

**Q. AI 코드는 고치나?**
AI의 판단 로직(에이전트·온톨로지·매뉴얼 검색)은 고치지 않는다. AI가 설비에 닿는 연결 부분만 바꾼다: 조치 실행의 Modbus 직접 쓰기를 "명령 요청(Kafka) → 게이트웨이 → PLC → ACK"로, 결과 확인을 PLC 상태로, 접속 주소를 새 망으로. 그래야 AI가 설비에 직접 쓰지 않는 현업 구조가 성립한다.
